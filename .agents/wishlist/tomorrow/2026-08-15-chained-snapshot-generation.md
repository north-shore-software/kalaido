**Scope**: design agreed in conversation, not yet broken into implementation steps. Backend mechanism (Go/PocketBase) plus one dashboard control. Open questions are called out in §7 and should be settled before this becomes a build plan.

## Context

Approving a wave of staleness means, for each entity in turn: generate a candidate (a model call, tens of seconds), read it, approve it. The generation sits *between* the approvals, so the run is mostly waiting. `Approve & next` made the sequence work but didn't remove the wait — it moved it to a spinner on the review page.

The wanted behaviour: press one button, let every candidate get generated up front / in the background, then click through and approve without a pause between items.

The trade is explicit and accepted: **most of the time the snapshot is approved as generated**, so candidates are worth generating speculatively. Some will be discarded — refined instead, or superseded — and that wasted model spend is the price of never waiting.

## 1. Why there is no queue

The plan is already derived. `GET /api/rotation` recomputes the whole graph per request (`internal/status/status.go`) and returns it in topological order; "what's next" is just its first actionable entry. A queue table would be a second answer to a question that already has one, and would need its own ordering, invalidation, and repair when it disagreed with the graph.

So: nothing enumerates the work. The chain re-asks the same evaluator each time it advances.

## 2. The mechanism: the chain mark rides on the snapshot

A snapshot generated as part of a chain is **marked** as such. The hook that fires when a snapshot record is written looks at the mark on that record:

- **Marked** → re-evaluate, find what needs generating now, generate it *carrying the same mark*.
- **Unmarked** → do nothing.

"Generate all" creates the first candidate with the mark. Every subsequent link is generated by the hook, also marked. The chain propagates itself and dies the moment a link isn't marked.

This is deliberately **not** a workspace-level "sweep is active" flag. Causality lives on the record that caused it: nothing to arm or disarm, no lifecycle to manage, no stale flag left armed a week later, and the chain is inspectable after the fact — you can see which snapshots a run produced.

It also means the system stays **not self-starting**, which the model requires (`.agents/spec/overview.md` §Staleness — *"nothing self-starts... An idle workspace stays idle"*). A detail-page Refresh, or an ordinary approve, writes an unmarked snapshot, so it propagates nothing. Only the button starts a chain.

### Why the mark survives into approval

Generating a candidate for A does **not** unblock anything downstream — staleness clears on *approval*, not generation. So the cascade has to continue across approvals, and this is the part that makes the design work:

**Approving doesn't create a row, it mutates the existing one** (`engine.ApproveSnapshot` sets `status`/`approval_sequence_number` on the candidate). So approving a chain-marked candidate is itself a write of a chain-marked record. The hook fires, sees the mark, re-evaluates, finds whatever that approval just unblocked, and generates it — still marked.

No session state is needed to span the approve run. The two behaviours fall out of one hook:

| Write | Re-evaluation finds | Effect |
|---|---|---|
| Marked candidate created | Rest of the current unblocked frontier, still without candidates | Fan-out: the frontier gets candidated, one at a time |
| Marked candidate approved | Whatever that approval unblocked | Cascade: the graph advances a layer |

## 3. Termination

The predicate for "needs generating" is:

> **actionable** (has a delta, `blockedBy` empty) **and has no pending candidate**

Both halves matter. Generating a candidate for X does *not* settle X — X stays stale until approved — so the pending candidate is the only thing that stops the fan-out revisiting it. Get that wrong and it regenerates X forever at model speed.

Because that predicate is the only thing between us and a token-burning loop, it is **not** the only guard:

- **Hop cap.** The mark carries a remaining-hops count, decremented on each generation, refusing to propagate at zero. Ceiling it at the workspace's entity count — a legitimate chain cannot need more hops than there are nodes. A bug in the predicate then burns a bounded number of calls, not an unbounded one.
- **In-flight guard.** Two hook firings can both decide to generate X. Generation must be de-duplicated per entity, in-process (precedent: `internal/colour`'s background worker).
- **Concurrency of one.** Serial generation, not a fan-out burst — the provider will rate-limit a wide parallel spray, and serial keeps the failure modes simple.
- **Quota exhaustion ends the chain** rather than retrying (`usage.ErrExhausted` is already distinguished at the generate handler).

Chain generation only ever targets unblocked entities, so it never trips the `409` blocked-upstream guard added alongside the bug fixes — and never produces a candidate that is stale on arrival.

## 4. Where it lives

- **Schema** — a chain field on `projection_snapshot` (and its reflection twin), holding the remaining-hops count; zero/absent means unmarked. Kalaido is pre-launch, so this is edited directly into `migrations/1748000000_init_schema.go` rather than added as a new migration file.
- **Request** — `api.GenerateSnapshotRequest` gains the field, so the button can start a chain and the hook can continue one.
- **Hook** — on snapshot write (create and update, since approval is an update), gated on the mark. Runs the work in the background, off the write's transaction.
- **UI** — a "Generate all" control at the top of the dashboard's Needs action section, plus some indication that a chain is running and a way to stop it.

## 5. What this does not change

The existing single-item paths stay exactly as they are: detail-page Refresh, dashboard row Refresh, Approve, Approve & next. All of them write unmarked snapshots and propagate nothing.

## 6. Interaction with refinement

Committing a refinement does not mutate the candidate — it writes a **new** snapshot (`engine.CommitRefinement` → `AppendSnapshot`). That new row won't carry the mark, so refining a candidate mid-run silently ends the chain: you'd approve your refined version and nothing downstream would generate.

Recommendation: **propagate the mark from the source snapshot on commit.** Refining one item is not a request to stop the run.

## 7. Open questions

1. **Do reflections participate?** They have no review gate, so a chain-marked reflection generation publishes live output directly and the cascade continues from an approved snapshot nobody looked at. That may be the point of a "generate everything" sweep, but it is the one place the chain does something irreversible without the user seeing it first. *Undecided.*
2. **Cancelling a running chain.** The chain has no central handle to cancel — that is the cost of not having a sweep flag. Stopping it means either refusing to propagate at the next hop (needs somewhere to record "stop"), or letting it finish. *Undecided.*
3. **Surfacing progress.** With no queue and no sweep row, "a chain is running" has to be inferred — e.g. from marked pending candidates. Enough for a dashboard indicator, but worth confirming before building the control.
