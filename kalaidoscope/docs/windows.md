## 1. The window spec

`api.WindowSpec` has five string fields, wire names `mode` (omitempty), `startTime`, `endTime` (omitempty), `period`, `duration`. The window code reads **three**: `period` — a Go duration string (`"24h"`, `"168h"`); empty, unparseable or non-positive means *no schedule*; `duration` — a Go duration; empty, unparseable or non-positive means **tumbling** (`duration = period`, via `parseDurationOr`); `startTime` — RFC3339, the grid origin (§ 3); unparseable is treated as absent (`parseRFC3339` returns the zero time for an empty or unparseable string). `mode` and `endTime` are read by no Go code: they are stored inside the version entry, round-tripped, and never evaluated.

Validation is `WindowSpec.Validate()` on the wire type, called by `reflections.Create` and `reflections.Update` only when the request carries a `windowSpec` (`lifecycle-reflection.md` § 2, § 3). A spec whose `period`, `duration` and `startTime` are all empty is valid (unscheduled) — `mode` and `endTime` are not examined, so a spec carrying only `mode` and/or `endTime` is valid and unscheduled. Otherwise `period` must parse as a positive duration (so a spec carrying only `duration` or only `startTime` fails here), `duration` if non-empty must parse as a positive duration, and `startTime` if non-empty must parse as RFC3339; the errors are `windowSpec.period must be a positive duration such as "168h"`, `windowSpec.duration must be a positive duration such as "168h"`, and `windowSpec.startTime must be RFC3339`. `Create`/`Update` wrap the failure as `ErrInvalidWindowSpec` (`invalid window spec: <message>`), which both handlers turn into a `400` carrying that wrapped text; `Update` loads the live reflection first, so a missing or soft-deleted reflection is `404 reflection not found` before any validation. The projection create/update request types have no `windowSpec` field (`lifecycle-projection.md` § 2, § 7).

Discover builds specs through `BuildReflectionSpec(cadence, startTime, now)` in `cadence.go` (`discover.md` § 6.1): the cadence word is trimmed and lower-cased and looked up in `CadencePeriods` — `daily`→`24h`, `weekly`→`168h`, `monthly`→`720h`, `quarterly`→`2160h` (`CadenceNames()` lists the four in that order for the rejection text); an unknown word is rejected with `prompts.DiscoverUnknownCadence`. The start is `ParseStartDate`: trimmed, tried as `2006-01-02`, RFC3339, then `2006-01`, and floored to midnight UTC of that date; unparseable is `prompts.DiscoverBadStartTime`. A start after `now` is `prompts.DiscoverStartInFuture`; a start whose elapsed span holds strictly more than `MaxGridWindows` (1000) whole periods (`int(now − start / period)`) is `prompts.DiscoverTooManyWindows`. The result is `{startTime: start RFC3339, period, duration = period}` — `mode` and `endTime` are never set — returned together with the floored start, which discover uses as the version's `effectiveFrom` (§ 2). The messages are the model-facing rejection strings of `prompts.md` § 2.

## 2. Versioning

`window_spec_versions` on the reflection row is a JSON array of `api.WindowSpecVersion` — `{versionNumber, effectiveFrom, spec}`. `LoadWindowSpecVersions(rec)` unmarshals it and ignores any error, so an unparseable value reads as no versions (unscheduled). `AppendWindowSpecVersion(versions, spec, effectiveFrom)` returns the array with one entry added: `versionNumber` = highest existing number + 1 (1 when none), `effectiveFrom` = the given instant rendered UTC RFC3339. Nothing ever overwrites or removes an entry. Three sites append:

- **Create** (`reflections.Create`, `lifecycle-reflection.md` § 2) always writes version 1, with or without a `windowSpec` in the body (an absent spec is stored as an all-empty spec). `effectiveFrom` = now, except when `startTime` parses as RFC3339 *and* lies before now, in which case `effectiveFrom` = `startTime`.
- **Discover** proposals (`discover.md` § 6.1) write version 1 with `effectiveFrom` = the floored start date returned by `BuildReflectionSpec`.
- **Update** (`reflections.Update` with `WindowSpec` non-nil, `lifecycle-reflection.md` § 3) appends `versionNumber` max+1 with `effectiveFrom` = now. When the new spec's `startTime` is empty and a governing version exists at now, the governing version's `startTime` is copied into the new spec before it is appended (after validation, so the inherited value is never re-validated); an all-empty spec sent to unschedule therefore still carries the inherited `startTime` (and no `period`, so it is unscheduled). When no governing version exists the empty `startTime` stays empty. The update triggers no generation and no window enumeration itself.

**Governing version.** `GoverningVersion(versions, at)` returns the entry with the latest `effectiveFrom` that is not after `at`; entries whose `effectiveFrom` fails RFC3339 parsing are skipped; among equal `effectiveFrom` values the earliest in array order wins (the comparison is strictly-after). Every caller passes now: `CurrentGridWindows`, `DefaultRefinementWindow`, `MaterializeBackfill`, and `Update`'s `startTime` inheritance. No governing version (none, or all in the future) means unscheduled; so does a governing version whose `spec.period` is the empty string — all three window callers check `Period == ""` before enumerating anything.

**Lower bound.** `versionLowerBound(v)` is the later of `effectiveFrom` and `spec.startTime` (each parsed with `parseRFC3339`; unparseable is the zero time, which is never "later"): the instant from which that version produces windows.

## 3. Tiling: the grid and pending windows

`GridWindows(reflectionID, spec, lowerBound, now)`:

- `period` must parse positive, else nil. `duration` = `parseDurationOr(spec.duration, period)`.
- `origin` = `startTime`; when zero, `lowerBound`; when that is also zero, nil.
- Grid point *k* (k ≥ 1) falls at `origin + k·period`. The first *k* is 1, or, when `lowerBound` is after `origin`, `⌊(lowerBound − origin)/period⌋ + 1` — the smallest grid point strictly after `lowerBound`.
- Window *k* ends at grid point *k* and starts `duration` earlier, raised to `origin` when it would fall before it (first-window truncation). Enumeration stops at the first grid point after `now`, so only windows ending **after** `lowerBound` and **at or before** `now` are produced, oldest first.
- Whenever the list exceeds `MaxGridWindows` (1000) the oldest entry is dropped, so at most the 1000 newest windows are returned.

The three shapes follow from `duration` vs `period`: equal — tumbling, contiguous, one per elapsed period; longer — overlapping look-backs, truncated at the origin while it is inside them; shorter — gapped, the `duration` before each grid point with the remainder uncovered.

`CurrentGridWindows(rec, now)` = the grid of the version governing now, from that version's lower bound; nil when unscheduled. Because a later version is effective from the moment of its edit, a cadence change never re-enumerates history: an earlier version's windows stay in the series only through their approved snapshots (§ 6).

**Pending windows.** `PendingWindows(app, rec, now)` = the series (§ 6) filtered to windows with neither an approved snapshot nor a generation in flight, oldest first. It feeds the background pending-window pass (`RunPendingWindows` / `GeneratePendingWindows` in `backfill.go`, `lifecycle-reflection.md` § 5.3) and the windowless branch of the status evaluator (§ 6, `reconcile.md` § 2.1).

## 4. Window identity

A window on the wire is `api.Window{id, start, end}`. `newWindow(reflectionID, start, end)` renders both bounds UTC RFC3339 and sets `id` = `WindowID`.

- `WindowID(reflectionID, w)` = hex MD5 of `reflectionID + start + end` as strings. It is stable across evaluations and distinct per reflection for the same bounds. It is the `id` the API hands out (`windows[].id`, `currentWindowId`, `pendingWindows[].id`, `staleWindows[].id`) and accepts (`windowId` on generate, matched against the series' ids — § 7). Besides `newWindow`, it is computed in `SeriesWindows` for a window arriving with an empty `id`, and in refinement opening (`refinement.CreateReflectionRefinement`) for the window the session seeds — a client-supplied `window` is rebuilt as `{start, end}` from the client's strings as sent, without normalisation, and hashed over them; the default window's `id` is recomputed the same way, to the same value (`refinement.md` § 2).
- `WindowKey(w)` = `"{start}_{end}"`. It is the in-memory join key of `SeriesWindows`, is served as `key` on the windows route, and names the window in backfill log lines; it is stored nowhere.
- **On rows**, a window is its bounds: `window_start` / `window_end` DateFields on `reflection_snapshot` (both empty for a windowless snapshot) and on `reflection_window` (both required). `engine.WindowBounds(w)` parses each string with `types.ParseDateTime`, yielding zero values on a nil window or a parse failure; it also feeds the window bounds into the apply prompt (`engine.GenerateOutput`, `minimizeAgainstPrevious`, `refinement.ApplyDraftLens`). `engine.SetSnapshotWindow(rec, w)` writes the parsed bounds onto a row; a nil window leaves the row windowless. Reflections reach it through `Strategy.ApplySnapshotWindow` (the snapshot writer `applySnapshotSpec`, on every reflection snapshot row whether appended fresh or filled into a claim) and directly from the generation claim (`ClaimGeneration`, when the window is non-nil) and backfill materialisation (§ 6.1); the projection strategy's `ApplySnapshotWindow` is a no-op. Two readers turn a row back into a window, both nil when either bound is zero: `reflections.SnapshotWindow(rec)` goes through `newWindow` with the row's `reflection_id`, so it carries canonical bounds and the canonical `id`; `engine.SnapshotWindow(rec)` renders the bounds UTC RFC3339 and leaves `id` empty. The former is used by `SeriesWindows`; the latter by approval sequencing (`nextApprovalSequence`) and the post-approval discard, where only the bounds matter.
- **Per-window scoping of snapshot queries** goes through `Strategy.SnapshotWindowFilter(win)`, appended by `engine.statusSnapshotFilter` (and so `ApprovedSnapshotFilter`) to every status-scoped snapshot query — claims (`ClaimGeneration`, `AwaitGeneration`), the discard of other pending candidates, the pending-candidate lookup (`FindPendingCandidate`), the approval chain, the settle-in-place, the anchor lookup `latestApprovedOutput`, the refinement seed's approved-output lookup, and the evaluator's per-window lookup: a nil window adds `&& window_start = ''` (PocketBase's literal empty matches empty-or-null), a window adds `&& window_start = {:ws} && window_end = {:we}` with the `WindowBounds` values rendered by `types.DateTime.String()`. The projection strategy returns no clause. The uniqueness of an approval chain is `idx_reflection_snapshot_approval_seq` on `(reflection_id, window_start, window_end, approval_sequence_number)` where `status = 'approved'`; backfill rows are unique on `(reflection_id, window_start, window_end)` (`idx_reflection_window_bounds`).

Because row scoping goes through `WindowBounds` while `id`/`key` are string-derived, a client-formatted window with the same instant matches the same rows but is a different `id` and `key` in memory from the grid's rendering of it.

**Transcript windows.** A refinement conversation carries its target window as a `window` part on a system message (the seeded message at open, and any re-apply send). Readers: `llmcontext.LatestPinnedAndSpec` takes the newest `window` part that unmarshals (a part with an empty bound still ends the search) and yields nil when either bound is empty; `chat.ResolveContextSpecs` re-resolves pins whenever a new system message carries a `window` part (both bounds set → that window, otherwise the window is cleared to nil) — refinement and explore turns call it before persisting the new messages; `chat.HydrateDeltaHistory` renders `prompts.WindowNotice(start, end)` for every system message whose `window` part has both bounds; `refinement.ReapplyWindow` reads the part from a send holding no user turn, requiring both bounds, the last such part winning (`refinement.md` § 4) — the re-apply persists only `{start, end}` in its `data-window_reapply` marker part, no `id`. The drafting turn's apply leg and the regenerate-confirmed leg take their window from `LatestPinnedAndSpec`; the commit reads it and discards it (`refinement.md` § 5). `reflections.ParseWindowPart(w)` — nil when either bound is empty, else the window as given — is defined for this purpose and has no caller in the binary. `POST /api/llm/count-tokens` binds `TokenResolutionRequest`, whose `window` is nilled when either bound is empty, and passes it to every per-item resolution of the spec form or, in the conversation form, as a `window` part beside the `context_spec` part on the pending system message `estimate-spec` that `explore.EstimatePrompt` runs through `ResolveContextSpecs` (`explore.md` § 9). The window clause itself (`sourcedata.WindowClause`) is `context.md` § 2.1.

## 5. Consequences of the lower-bound rule

- A version whose `startTime` is later than its `effectiveFrom` produces nothing before `startTime`; one whose `startTime` is earlier produces windows only from `effectiveFrom` onward — except version 1 created with a past `startTime`, whose `effectiveFrom` *is* that start, so every grid window from then to now is pending ("summarize from <date>"). Discover's version 1 has the same shape (`effectiveFrom` = start).
- An edit that leaves `startTime` empty inherits the governing origin, so the new version's windows stay phase-aligned with those already generated; only a version that moves the origin can produce a first window truncated at the new origin.
- A version 2+ with an inherited past `startTime` starts at its `effectiveFrom`; a window that straddles that edit instant is produced (its end is after the lower bound) with its full `duration`, reaching back before the edit.
- A reflection with a valid spec whose first grid point after the lower bound has not yet passed has no grid windows: `PendingWindows` is empty, staleness reports nothing owed, and the default window falls back to the trailing window (§ 7). The reconcile wave additionally treats "scheduled but no grid windows" as not-yet-scheduled for its windowless fallback (§ 6, `reconcile.md` § 3.1).

## 6. The series

`SeriesWindows(app, rec, now)` returns `[]WindowState` — `api.Window` plus `Key`, `HasApproved`, `Generating`, `Backfilled`, `LensID` (and an unexported `approvedSeq`) — merged by `WindowKey` from three sources, in this order; the first occurrence of a key fixes the window (bounds and `id`, filled by `WindowID` when empty — every source below already carries an `id`, so the fill never fires for them), later occurrences only update flags:

1. `CurrentGridWindows` (§ 3), `Backfilled = false`.
2. Every `reflection_window` row for the reflection, ordered by `window_start`, `Backfilled = true` (OR'd onto a window the grid already produced).
3. Every `reflection_snapshot` row for the reflection with `window_start != ''` and `status` `approved` or `generating`, in unspecified order. An approved row sets `HasApproved` and, when its `approval_sequence_number` is ≥ the highest seen for that window, sets `LensID` to its `lens_id`. A generating row sets `Generating` — claim rows carry their bounds from insertion, and no age check is applied here (a claim past `GenerationClaimTTL` still counts). `pending_review` and `discarded` rows contribute nothing, and a snapshot from an older schedule version keeps its window in the series through its approved row.

Both lookups discard their errors: a failed query yields a series without that source. Output is sorted stably by `start` then `end` (string order of the UTC RFC3339 bounds).

The windows route (`GET /api/reflections/{id}/windows`, `lifecycle-reflection.md` § 9) loads the live reflection (`404 reflection not found`) and serves each state as `WindowInfo{id, start, end, key, hasApproved, generating, backfilled, stale, lensOutdated}` (the last two omitempty; `windows` is always an array): `lensOutdated` = `HasApproved && LensID != reflection.current_lens_id`, computed in the handler; `stale` = the window's `id` appears in `staleWindows` of a fresh full status evaluation (`reconcile.EvaluateEntity`) for this reflection — when that evaluation errors, or the reflection is not among the evaluated entities (it evaluates only `status = 'active'` live entities, returning a zero status otherwise), no window is marked stale. `currentWindowId` is § 7.

**Per-window staleness.** The status evaluator (`reconcile.evaluateReflectionWindows`, `reconcile.md` § 2.1) reads the same series. It is reached only for a reflection that has at least one approved snapshot of any kind, and applies only when some series window `HasApproved`; then every window with neither `HasApproved` nor `Generating` is appended to `pendingWindows`, and for each approved window the latest approved snapshot in that window's chain (`ApprovedSnapshotFilter`, highest `approval_sequence_number`) has its `resolved_context` diffed against the reflection's `current_context_spec` resolved inside that window (`llmcontext.ResolveSpecToIDs` with the window; `context.md` § 2.1, § 5) — only `FragmentIDs` of the diff count, upstream snapshot ids are not compared for windowed reflections; a window with any new fragment is appended to `staleWindows` and its new ids to `newFragmentIds` (deduplicated, sorted). A window whose chain lookup fails or returns nothing, or whose resolution errors, is skipped silently (neither pending nor stale). `upToDateSnapshotId` is the approved snapshot of the latest-ending approved window (string comparison of `end`, taken before the resolution step, so a window skipped for a resolution error still counts), set only when `newFragmentIds`, `staleWindows` and `pendingWindows` are all empty; the windowed path returns before the upstream checks, so `staleDependencies` and `blockedBy` are never set for a windowed reflection. A reflection whose approved snapshots are all windowless is evaluated the windowless way with `PendingWindows` appended, and is up to date only when that list is also empty. The wave generates exactly `pendingWindows` then `staleWindows` in that order; when both are empty and `CurrentGridWindows` is non-empty it generates nothing, and only a scheduled reflection with no grid windows (or an unscheduled one) falls through to the windowless currency check (`reconcile.md` § 3.1). A generate call with no `windowId` takes pending, lens-outdated and stale windows as candidates (§ 7).

### 6.1 Backfill materialisation

`MaterializeBackfill(app, rec, from, now)`, called only by `POST /api/reflections/{id}/backfill` (`lifecycle-reflection.md` § 9), whose handler binds `BackfillRequest{from}` (`400 invalid request body`) and parses `from` as RFC3339 (`400 from must be RFC3339`) before loading the live reflection (`404 reflection not found`):

- Requires a governing version at now with a non-empty `period` (else `reflection <id> is not scheduled`) that parses positive (else `reflection <id> has no period`); the handler turns both into `500 backfill failed`.
- `covered` = the version's lower bound; `from` must be strictly before it, else `ErrBackfillOutOfRange` (`backfill start must be before the windows already on the grid`, a `400`).
- The grid origin (`startTime`, else `covered`) is shifted back by `⌊(origin − from)/period⌋ + 1` whole periods — to an instant strictly before `from` and within one period of it — and `GridWindows` is enumerated with the shifted spec from `lowerBound = from` to `now = covered`. Backfilled windows are therefore phase-aligned with the grid, end strictly after `from` and at or before `covered`; the first one may begin before `from` (it is truncated only at the shifted origin), and a window ending exactly at `covered` belongs to the backfill, not the grid.
- No windows (a span shorter than one period) returns `nil, nil` — a `200` whose `windows` serialises as `null`, with no rows written.
- Each window is written as a `reflection_window` row: `reflection_id`, `window_start`, `window_end` (via `engine.SetSnapshotWindow`); no version number or key is stored. When a save fails, the row is looked up by `(reflection_id, window_start, window_end)`: found means already materialised and the window is kept in the result; not found returns `materialize window <key>: <save error>` (`500 backfill failed`). Re-running the same range is thus a no-op that still returns the windows.
- Materialisation is permanent and independent of generation: rows are removed only by the `reflection_id` cascade on hard delete; soft delete leaves them. The returned windows are what the route reports (`BackfillResponse{windows}`); generation of them is the pending pass the handler kicks afterwards (`RunPendingWindows`, `lifecycle-reflection.md` § 5.3).

## 7. Default refinement window

`DefaultRefinementWindow(rec, now)`: nil when unscheduled (no governing version at now, or `period` empty). Otherwise the **last** window of the governing version's grid from its lower bound — the most recently completed grid point. When that grid is empty (the first grid point after the lower bound has not passed, or `period` is non-empty but unparseable): a trailing window ending at `now` in UTC truncated to the minute and starting one `duration` earlier (`duration` = `parseDurationOr(spec.duration, parseDurationOr(spec.period, 0))`), raised to `startTime` when that is later; nil when the resulting start is not before the end, or when neither `duration` nor `period` parses positive. Its bounds and `id` come from `newWindow`.

It is used in three places: refinement opening when the request names no `window` or one with an empty bound (`refinement.md` § 2), the windows route's `currentWindowId` (omitted when nil), and the generate call's fallback below, where a nil result means a windowless generation.

**Windows for a generate call.** `WindowsToGenerate(app, rec, req, st)` picks the windows one generate request covers — `POST /api/reflections/{id}/snapshots` and `POST /api/reflections/{id}/generate-snapshot` share the handler (`lifecycle-reflection.md` § 5.1). The bound request is `GenerateReflectionSnapshotRequest`, whose window fields are `windowId` and `allWindows` (a legacy `all` key also sets `allWindows`); `Validate` rejects both together (`cannot specify both windowId and allWindows=true`, a `400`). `st` is the reflection's fresh status; when its evaluation failed the handler logs a warning and passes the zero status (a non-`active` reflection also yields a zero status without error), so `staleWindows` contribute nothing; a non-empty `blockedBy` is a `409` before any window is chosen.

- With `windowId`: the series window whose `id` matches, whatever its flags (a generating window is joined, `coordination.md` § 2.2); no match is `ErrWindowNotFound` (`window ID not found in this reflection's windows`, a `400`).
- Without: the candidates, deduplicated by `id` and in series order, are every series window that is not `Generating` and either has no approved snapshot or whose `LensID` differs from `current_lens_id`, followed by `st.StaleWindows` (which are not filtered on `Generating`). None → `[DefaultRefinementWindow]` (a single, possibly nil, window). Exactly one, or `allWindows` → all of them. Several without `allWindows` → `ErrMultiplePendingWindows` (`multiple windows are pending; pass allWindows=true to generate them all`, a `400`).

A single window goes through the join-aware single generation (`Manager.GenerateReflectionSnapshot` → `engine.GenerateOrJoin`; a failure is the generate error envelope); several go through `Manager.GenerateReflectionWindows` → `GenerateWindows(ctx, app, reflectionID, status, windows)`, which runs one goroutine per window (concurrency bounded only by the LLM queue's per-provider cap, `llm-queue-quota.md` § 2.2), retries a window whose call was pre-empted, and returns a `WindowResult{SnapshotID, Err}` per window in input order (`lifecycle-reflection.md` § 5.2). The handler answers `200 {snapshotIds}` with whichever windows produced a snapshot; only a total failure is an error (the first failure's envelope), and a partial failure is logged as a warning. The same function serves the background pass (`GeneratePendingWindows`, status `approved`, background priority), where `ErrLensNotReady` is logged as a warning, `ErrGenerationInFlight` is ignored, and any other failure is logged with the window's `WindowKey` and left pending for the next pass.
