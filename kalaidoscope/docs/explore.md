**Scope.** The explore conversation behind `POST /api/explore` (`internal/explore/`): request binding and error mapping, conversation and message persistence, how the transcript is turned into a prompt (including mention expansion), per-turn model resolution, the SSE stream shape, the size guard, and summaries mode — how it is selected, what seeds it, what stays in full, the two read tools it binds from the shared loop, and how reads persist and replay. It also covers the three routes under `/api/explore/conversations/{cid}` — bookmarking a turn, saving the bookmarks as fragments, and the projection brief — and the conversation form of the prompt estimate on `POST /api/llm/count-tokens`. Refinement conversations have their own routes and are `refinement.md`; they share only the persistence, hydration and stream helpers in `internal/chat/`. The loop mechanics and the map reader are `tool-loop.md`; resolution, hydration and flattening internals are `context.md`; prompt text is `prompts.md` § 2; the collections are `schema.md` § 2.12–2.13.

**Completeness anchor.** 4 routes under `/api/explore` registered in `server/server.go` (`POST /api/explore`, `PATCH /api/explore/conversations/{cid}/messages/{mid}/bookmark`, `POST /api/explore/conversations/{cid}/bookmarks/save`, `POST /api/explore/conversations/{cid}/brief`); 2 collections (`chat_conversation`, `chat_message`); 2 read tools bound in summaries mode by `mapreader.Reader.Registry` (`read_thing`, `read_fragment`) plus 1 brief tool (`propose_brief`); 11 SSE event types emitted by `internal/chat/sse.go` (`start`, `text-start`, `text-delta`, `text-end`, `tool-input-start`, `tool-input-delta`, `tool-input-available`, `tool-output-available`, `data-<name>`, `error`, `finish`) followed by the `[DONE]` sentinel; 6 message part kinds the explore flow reads or writes (`text`, `context_spec`, `window`, `pinned_ids`, `tool-read_thing`, `tool-read_fragment`).

## 1. Request and routing

Body is `api.ExploreRequest`: `{id, messages: [{id, role, parts: [{type, text?, data?}]}]}` (AI-SDK `UIMessage`s; `data` is raw JSON). A body that fails to bind → 400 `invalid explore request body`.

`HandleExplore` performs no lookup on `id` and never dispatches to a refinement: a refinement turn is posted to `POST /api/projections/{id}/refinements/{rid}/chat` or `POST /api/reflections/{id}/refinements/{rid}/chat` (`refinement.md`, the drafting-turn section). Every request on `/api/explore` is an explore turn, run by `explore.StreamTurn`. Its return value is mapped in this order: `ErrMessagesRequired` → 400 `messages required`; `ErrNoModel` → 500 `no model configured for chat`; `usage.ErrExhausted` → 402 (`llm-queue-quota.md` § 5); a classified provider error → its envelope (`llm-queue-quota.md` § 6); a `PromptTooLargeError` → 422 with the error's text; any other error → 500 `llm stream failed`; `nil` → nothing more is written (the SSE response has already been sent). Every one of these errors is returned before the SSE headers are written, so the status is real; once streaming has begun (§ 6), failures are only ever signalled in-band.

## 2. Persistence

- **Conversation**: `chat_conversation` found or created by `external_conversation_id = id` (`FindOrCreateConversation`; the column carries a unique index). A create that fails re-reads by the same filter and returns the winner if one exists; otherwise the error is logged (`explore persist: find or create conversation failed`) and the turn runs with **no persistence**. An empty `id` skips the lookup entirely — the turn still runs, nothing is stored. Stored messages are loaded once the row is known; a load failure is discarded, leaving the stored history empty for this turn. The row's `generate_with_model` field is the per-conversation model override, re-read every turn; no route sets it, and the collection is server-written (`DisableWriteOperations` → create/update/delete rules `nil`, list/view rule `@request.auth.id != ''`), so only a superuser or server code can set it.
- **Messages**: `chat_message` rows keyed by `chat_conversation_id` (the same table holds refinement transcripts under `projection_refinement_id` / `reflection_refinement_id`; `PersistMessage` picks the column from the owning record's collection name). `content` = the whole `UIMessage` as JSON; `generated_by_model` = the model that produced an assistant row, `""` for every incoming message; `bookmarked` and `fragment_id` are § 7. Rows load ordered by `created`; a row whose `content` fails to decode is skipped silently. `chat_conversation_id` cascades on delete (`schema.md` § 5).
- **New messages** = incoming messages whose `id` is not already stored (`ExtractNewMessages`; dedupe by id only, content is never compared). Before persisting, `ResolveContextSpecs` walks the new **system** messages: one carrying a decodable `context_spec` part and/or a decodable `window` part re-resolves the cumulative (spec, window) pair — seeded from the newest of each in the stored history, then carried forward across the new messages in order; a `window` with an empty `start` or `end` clears the window — through `ResolveSpecToIDs` (`context.md` § 2–3) and appends a `pinned_ids` part (`context.md` § 5) to that message. A part that does not decode is ignored and does not count as a change. A resolution error appends nothing and is not logged; the message persists without a receipt and later hydration sees no context change from it. New messages are then persisted one by one; a failure is logged (`explore persist message failed`) and the turn continues.

The client is expected to send the full transcript each turn; only the unknown ids are stored, so a client that re-sends an assistant message under a new id creates a duplicate row, and a turn whose stored history failed to load stores every incoming message again.

## 3. Prompt assembly

`PrepareLLMPrompt` → `chat.HydrateDeltaHistory` over stored + new messages. **Mode** is read by `ConversationSummaries`: `LatestPinnedAndSpec` scans system messages newest-first and takes, each independently, the newest decodable `pinned_ids`, `context_spec` and `window` part; summaries mode is the newest `context_spec`'s `wholeScope == "summaries"`, whichever message carries it; `"full"` and an absent `wholeScope` are both full mode. One `Hydrator` is built on the final `pinned_ids` and that mode (`context.md` § 4). The walk then visits every message in order: a system message contributes `WindowNotice(start, end)` when it carries a bounded `window` part, plus — only when it carries a decodable `pinned_ids` part — the hydrated delta between the previous `pinned_ids` and this one (`DiffPinnedIDs`; a delta error is discarded and renders as nothing); the message is emitted only if the resulting text is non-empty. Every other message is `Flatten`ed (`context.md` § 7): a message carrying a `data-window_reapply` part is skipped (only refinement writes one), each `text` part is passed through `ExpandMentions` — every `@[Kind:id|Label]` token (`Kind` ∈ Fragment, Projection, Reflection, Colour, Type; an empty label falls back to the id) is rewritten to its model-facing form (`@"Label" (Fragment ID: id)`, `@"Label" (Projection: id)`, `@"Label" (Reflection: id)`, `@"Label" (Colour — its tagged fragments are in the context)`, `@"type" (fragment type — those fragments are in the context)`) while the raw token is what persists — and persisted read-tool parts replay (§ 5). Because every delta renders against the final context, a fragment that has since left the context is omitted with a count rather than replayed, a conversation that switched modes re-renders its whole history in the new mode, a fragment in the receipt's `expandedIds` (pinned by id, type or colour) renders in full even in summaries mode, snapshots always render in full, and a fragment that left and came back is announced as restored rather than rendered twice. An empty hydrated transcript → `ErrMessagesRequired` (400); a transcript whose only content is a non-empty context delta is not empty and proceeds to the model.

The system prompt is prepended as message 0: `ChatSystemPrompt`, or in summaries mode `ChatSummariesSystemPrompt(digest)` = `ChatSystemPrompt` + `ChatSummariesLegend` + digest, blank-line separated. The digest is `SummariesMapDigest(doc, 2)` over the current map document (`sourcedata.LoadMapDocument`; an empty document when no map row exists): `What the workspace is about:` then the trimmed narrative or `(no narrative yet)`; the things with `fragments >= 2` (`SummariesThingFloor`) heaviest-first as `id · name · kind · fragments · span · blurb` (span = `first to last`, or `-` with no `firstSeen`), or `(nothing on the map reaches the floor yet)`; and, only when the document has relationships, a `Relationships:` block listing every one whose two ends resolve as `From (id) kind To (id)`. A map load failure yields an empty digest silently; the legend is still sent.

Model = `ResolveRoleFor(RoleChat, conversation.generate_with_model)`: a non-blank override is used verbatim (trimmed, unvalidated), else the chat role's default (`models.md` § 5); none → `ErrNoModel` (500). `CheckPromptFits(model, MessagesChars(prompt))` (`context.md` § 6) is unchecked when the provider reports no context window; otherwise `chars/4` above `PromptBudget` (window − window/8) → the guard's text `the context is about <N> tokens but <model> accepts about <limit> — narrow the window or the context`, logged at warn and returned as a `PromptTooLargeError` (422); in full mode the text is suffixed ` Switch the scope to "Summaries" in the context bar to chat over it through summaries instead.` The assistant message id is minted as `txt-<unix-nanos>`.

## 4. Full-mode turn

`usage.Stream(RoleChat, model, msgs, nil)` — no tools. Inside: the quota check (`Authorized`; exhausted → `ErrExhausted`, 402), scheduler admission at the chat role's default priority, Interactive (`llm-queue-quota.md` § 2.1; no override is set), then the provider call; a provider error is returned as its `ProviderError` (envelope per § 1), any other failure → 500 `llm stream failed`. All of this precedes the SSE headers. The response is then an SSE stream (§ 6) relaying the completion (`StreamAssistantResponse` = `BeginSSE`, `StreamTurn`, `Finish`); when it drains, and only when a conversation row exists, one assistant `chat_message` is persisted with `id` = the minted id and `generated_by_model` = the model: a `text` part if any text arrived and a `tool-<name>` part `{toolCallId, toolName, input}` per tool call the provider emitted (none is expected without tools); no parts → no row. A stream cut mid-way persists whatever text arrived — `StreamTurn` reads the event channel to its close and does not distinguish a completed stream from an aborted one.

## 5. Summaries mode

Selected per § 3. The model sees rows instead of bodies for everything in scope that the user did not pin; pinned fragments and upstream snapshots stay in full (`context.md` § 4). The turn binds the map reader's two tools from the shared loop (`tool-loop.md`): `mapreader.NewChatReader(app)` loads the map index once per turn — the things document, and every `fragment_annotation` row joined with the live fragments' event dates and indexed by thing — with a **12 fragment reads per turn** budget (`ChatFragmentReads`) and the chat wording for exhaustion; a load failure → `load map for summaries explore: …`, surfaced as 500 `llm stream failed`. `Reader.Registry()` binds `read_thing {ids: [string]}` and `read_fragment {ids: [string]}` (both `required: ["ids"]`, with the chat-specific descriptions `ChatReadThingToolDescription` / `ChatReadFragmentToolDescription`; `IDsArg` also accepts a single `id`). The first model call is `usage.Stream` with the two tools and maps errors exactly as § 4, still before any SSE output.

The turn is then an `agent.Runner` with `MaxRounds: 4` (`maxExploreToolRounds`) and `StopBeforeLastDispatch: true`, inside one SSE response (one assistant message on the client), round *r* = 0…3:

1. **Generate**: for *r* > 0 a new `usage.Stream` is opened with the tools, except that round 3 is opened **without tools** so the turn ends in text; an error opening it is logged, sent as an in-band SSE `error` with the raw error text (quota exhaustion and provider errors take this path too, not their § 4 envelopes) and stops the loop. The completion streams under the text id `<messageId>-r<r>`; non-empty text is appended to the parts; the round's tool calls are collected.
2. The runner appends to the model transcript an assistant message = the round's text + `\n\n[You called: <names>]` (nothing appended to the text when there were no calls).
3. No tool calls → the row is written (step 5) and the loop ends. Tool calls in round 3 → the row is written and the loop ends **without dispatching them** (their `tool-input-available` events were streamed, no output follows, and no part is persisted for them).
4. Otherwise each call is dispatched in order through the registry (an unknown name → `no tool named "<name>"`):
   - `read_thing`: more than **10** refs (`DiscoverReadThingLimit`) → the list is cut to the first 10 and the output opens with `read_thing takes at most 10 ids per call; the first 10 were read.`; each ref (trimmed) resolves by thing id, else by normalised name or alias (lower-cased, whitespace collapsed, trailing punctuation dropped), to a thing card — `id · name · kind [· aka aliases]`, blurb, `N fragments[, first to last]`, its relationships whose two ends resolve, then either `No annotated fragments cite it.` or a month-by-month `Timeline:` (`undated` for a row without a 7-character date prefix) and `Fragments (k of N, spread over time):` with up to **30** rows sampled evenly (`ThingRowSample`) as `date · title · summary (fragmentId)` — or `No thing matches "<ref>".`; results are newline-joined.
   - `read_fragment`: an empty list → `No fragment with id "".`; blank ids are skipped; each id spends one read and renders as a `FragmentBlock` (`sourcedata.FindFragmentsByIDs`, which does not filter `deleted_at`); an unknown id → `No fragment with id "<id>".` and spends nothing; once the 12th read lands with ids still unread, `Fragment read budget exhausted (12 per turn). Work from the summaries you already have, or tell the user what you would need to read.` is appended and the rest are skipped; a call arriving after the budget is spent gets that message in place of its first id and once more if it carried further ids. The budget is per reader, i.e. per turn across all rounds.

   Each result is sent as `tool-output-available` and appended as a `tool-<name>` part `{toolCallId, toolName, input, output, state: "output-available"}`. Handlers never return an error and never signal completion, so dispatch cannot end the loop early.
5. **The assistant row is written after every round** (`chat.TurnWriter`: created on the first write, rewritten in place — `content` only — thereafter; write failures are logged), so an interrupted turn keeps its reads. Only when a conversation row exists; parts are always accumulated in memory regardless.
6. The runner appends a user message = the outputs joined by blank lines, then `PromptGuard` runs `CheckPromptFits` on the whole transcript — too large → logged at warn and sent as an in-band SSE `error` with the guard's text (no summaries hint), stop.

The runner's return value is discarded. After the loop the row is written once more and the stream finishes — a turn that stopped on an in-band `error` still ends with `finish` and `[DONE]`. Without a conversation row nothing is persisted but the loop runs the same.

**Replay on later turns**: `Flatten` turns persisted `tool-read_thing` / `tool-read_fragment` parts (those with a non-empty `output`) back into the assistant text so far + `[You called: …]` + a user message with the outputs joined by blank lines, flushing at the next `text` part or the end of the message, so the model sees its earlier reads without re-reading (`context.md` § 7). A read part without an `output` (an interrupted call) is dropped; the `toolName` falls back to the part type's suffix when absent.

## 6. The SSE stream

`BeginSSE` writes `Content-Type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`, `Cache-Control: no-cache`, `Connection: keep-alive` and commits status 200, after which errors can only be signalled in-band.

Events (each `data: <json>`, flushed after every event when the writer supports it): `start {messageId}` — the server-minted assistant message id, which the client must adopt or the next turn persists a duplicate; `text-start {id}` / `text-delta {id, delta}` / `text-end {id}` (one segment per model call, `text-start` on the first text event, `text-end` only if text started); `tool-input-start {toolCallId, toolName, dynamic: true}`, `tool-input-delta {toolCallId, inputTextDelta}`, `tool-input-available {toolCallId, toolName, input, dynamic: true}` as a tool call streams; `tool-output-available {toolCallId, output}` when the server has a result; `data-<name> {data, transient?}` parts — explore emits only `data-inference_rate {tokensPerSecond}` (transient), at most every 250 ms while text streams (rate = text events per second since the first event of the completion) and once more from the provider's final usage when it reports a rate; refinement adds its own non-transient parts (`refinement.md` § 3–4); `error {errorText}`; `finish`; then `data: [DONE]`.

## 7. Bookmarks

`PATCH /api/explore/conversations/{cid}/messages/{mid}/bookmark`, body `api.BookmarkRequest` `{bookmarked: bool}`. `{cid}` is looked up in `chat_conversation` only (`findExploreConversation`) → 400 `missing conversation id` when empty, 404 `conversation not found` for a refinement's id or an explore that has never sent a turn; an empty `{mid}` → 400 `missing message id`; an unbindable body → 400 `invalid bookmark body`. `{mid}` is a `UIMessage` id, found by scanning the conversation's rows in `created` order and decoding `content` (a turn still streaming has no row yet) → 404 `message not saved yet`; a `system` row, or one whose content does not decode → 422 `only explore turns can be bookmarked`. Both `user` and `assistant` rows qualify. Sets `bookmarked` to the body value (clearing leaves the row and any `fragment_id` in place); save failure → 500 `failed to save bookmark`. Response 200 `api.MessageMark` `{messageId, bookmarked, fragmentId?}`.

`POST /api/explore/conversations/{cid}/bookmarks/save` (same lookup rules) runs `SaveBookmarks` under a context detached from the request's cancellation, in **one transaction**: every row with `chat_conversation_id = {cid} && bookmarked = true`, by `created`; a `system` row, an undecodable one, or a turn with no text is skipped. Text = the message's non-blank `text` parts trimmed and joined by a blank line, with a **user** turn's mention tokens reduced to `@Label` (`StripMentions`; label falls back to the id). A row whose `fragment_id` points at a fragment row that exists with an empty `deleted_at` is reused (`created: false`); otherwise a `fragment` row is created directly (not through the ingest writer, so no content-hash dedupe): `type = "chat"`, `ingested_via = "app"`, `source = "explore:<cid>:<mid>"`, `content` = the text, `occurred_at` = the message row's `created`; the message row is stamped with the new `fragment_id`. The fragment birth hooks fire as for any app-written fragment — the create hook fills `occurred_at` / `ingested_via` only when empty (both are already set), and after the create succeeds the colour worker is signalled, and because `ingested_via != "import"` the annotate signal and a reconcile wave follow (`ingestion.md` § 7). Any save failure rolls the whole batch back → 500 `failed to save bookmarks`. Response 200 `api.SaveBookmarksResponse` `{saved: [{messageId, fragmentId, created}]}`, `[]` when nothing qualified. Idempotent for turns already saved; a turn whose fragment was soft-deleted or hard-deleted gets a fresh one.

## 8. The brief

`POST /api/explore/conversations/{cid}/brief` (same lookup rules) asks the model what projection the session was working towards; nothing is created. Transcript = every non-`system` row with text (`MessageText`, so user mentions are reduced to `@Label`), in `created` order, as `{role, text, bookmarked}` lines; none → 422 `the model returned no brief: the conversation has no turns` (`ErrNoBrief`). Model = `ResolveRoleFor(RoleChat, conversation.generate_with_model)` (error → 500 `failed to write the brief`). Prompt = system `ChatBriefSystem` + one user message from `ChatBriefTranscript`: `The conversation:` then per line `<role>[ [bookmarked]]:` and the trimmed text, closing with `Call propose_brief once.`; `CheckPromptFits` → 422 with the guard text (via `WriteLLMError`). `usage.GenerateWithToolCalls` at an explicitly set Interactive priority with the single tool `propose_brief {name, message}` (both `required`). Quota exhaustion → 402; provider error → envelope; a preempted or interrupted call, or any other failure → 500 `failed to write the brief`. The **last** decodable `propose_brief` call wins; both fields are trimmed; with no usable call, or an empty `message`, the answer text becomes `message` and `name` stays whatever the last call gave (empty with no call); an empty `message` after that → 422 `the model returned no brief`. Response 200 `api.BriefResponse` `{name, message}`.

## 9. Prompt estimate

`POST /api/llm/count-tokens` (`api.md` § 3) binds `api.TokenResolutionRequest` — the `ContextSpec` fields flattened in, plus `window` and `conversationId`; a bind failure → 400 `Invalid JSON body`; a window missing `start` or `end` is treated as absent. Without `conversationId` the handler sums the spec form per item through `explore.CountTokensForSpec` (each item resolved alone and rendered as a fresh delta in the spec's own mode; a resolution error counts 0) against the chat role's default model — that form is `context.md` § 6. With `conversationId` it is the conversation form, `explore.EstimatePrompt`: the conversation is read if it exists, never created (a message load failure → 500 `estimate failed`); its stored messages plus one pending system message (`id: estimate-spec`, `context_spec` part = the body's spec fields — always present, even when empty — and a `window` part when the body's window is bounded) go through `ResolveContextSpecs` and `PrepareLLMPrompt` exactly as a turn would, so a spec identical to the one in effect adds an empty delta and a changed one costs its delta. Tokens are `chars / 4` per message: message 0 → `System`, other `system` messages → `Context`, the rest → `Transcript`. Response 200 `api.TokenResolutionResponse` `{totalTokens, breakdown: {System, Context, Transcript}, model, limit, fits}` where `model` is `ResolveRoleFor(RoleChat, conversation.generate_with_model)` (a resolution failure leaves `model` empty and `limit` 0), `limit` = `PromptBudget(model)` and `fits` = `limit <= 0 || totalTokens <= limit`.

## 10. What explore does not do

- No server-side tools in full mode; no memory beyond the persisted transcript; no summarisation of long histories — the size guard refuses instead, and the omission of context that has since left is the only trimming.
- No routes to list, rename or delete conversations or messages, and no way to set `generate_with_model` from the client: both collections are server-written and readable by any authenticated user (`schema.md` § 2.12–2.13); deleting a `chat_conversation` cascades to its messages.
- No cancellation surface: a turn runs until its stream drains or the request context ends; in summaries mode nothing stops a round already dispatching.
- A bookmark by itself creates nothing; only the save route writes fragments, and it never deletes them — clearing a bookmark or deleting a message leaves the fragment in place.
- The brief creates no projection; the client decides what to do with the name and message.
