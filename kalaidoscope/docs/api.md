## 1. Wire conventions

- JSON field names are **lowerCamelCase** throughout (`fragmentIds`, `snapshotId`, `wholeScope`), with one exception: the `POST /api/ingest` body uses **snake_case** for its multi-word fields (`source_time`, `skip_duplicates`).
- Declared request/response DTOs live in `internal/api` (package `api`). Several handlers bind **anonymous structs** instead of the declared types; where that happens, this document records the fields actually bound, and notes the declared type as unbound.
- Errors raised through PocketBase helpers (`BadRequestError`, `InternalServerError`, …) use PocketBase's standard JSON error envelope. Domain-specific error bodies (quota exhaustion, provider failures) are described in § 13.
- No custom route requires authentication; the collection-rule and auth posture are described in § 13.

## 7. Refinements

Refinement sessions are chat conversations scoped to one projection or reflection, held in `refine_proj_snapshot_conversation` / `refine_refl_snapshot_conversation`. Chat turns inside a session go through `POST /api/chat` (§ 4, refinement dispatch). The routes here open and commit sessions; both exist in identical projection and reflection variants.

| Endpoint | Request | Behaviour & side effects | Response / errors |
|---|---|---|---|
| `POST /api/projections/{id}/refinements`<br>`POST /api/reflections/{id}/refinements` | `CreateRefinementRequest`: `clientId` (required — becomes the conversation's `external_conversation_id`, which is how § 4 dispatch recognizes it), `snapshotId` (optional — scopes the session to an existing snapshot), `contextSpec` (optional), `seedDraft` (optional). | In one transaction: creates the refinement conversation with the path `{id}` stored as the parent relation (the handler does not itself check the entity exists) and `snapshotId`, when given, as the source-snapshot relation (an unknown `snapshotId` aborts the transaction). **Context seeding:** an explicit `contextSpec` wins; otherwise the source snapshot's `context_spec` is inherited. If either is present, a system message is persisted carrying the spec **and** its immediate resolution as `pinned_ids` — so a seeded session can be committed without a single chat turn and still record what its snapshot consumed. **Window seeding** (reflections with a `snapshotId`): the snapshot's `window_spec` is added to that system message when it has a `period`. **Draft seeding:** a non-blank `seedDraft` is persisted as an assistant message in exactly the shape of a real `update_draft` tool call, indistinguishable from a model-produced draft — so external text can be committed without regeneration. | `201` `{refinementId, messages}` — `messages` are the seeded messages with their persisted ids; callers must display these rather than reconstruct copies, or the next turn double-persists. `400` invalid body, missing `clientId`, or missing path id. `500` transaction failure (including unknown `snapshotId`). |
| `POST /api/projections/{id}/refinements/{rid}/commit`<br>`POST /api/reflections/{id}/refinements/{rid}/commit` | Anonymous bind: `updateLensAndContext` (bool). A malformed body is ignored (treated as false). `{rid}` is the **refinement conversation** id. No DTO is declared for this body. | **Draft extraction:** the transcript is scanned newest-first for an assistant `update_draft` tool-call part; the latest system `pinned_ids`, `context_spec`, and `window_spec` parts are read alongside. No draft anywhere → `400` ("no drafted snapshot found in chat"). **Parent resolution:** the conversation's direct parent relation, else the parent of its source snapshot; neither → `400`. A path `{id}` that differs from the resolved parent → `400` ("refinement parent target id mismatch"). **Commit:** appends a new snapshot — `output` = the draft, `context_spec`/`resolved_context` = the transcript's latest recorded state, `model` = refinement-role resolution of the parent's override, `created_from_refinement_id` = `{rid}`, `status: "approved"` and immediately sequenced (per `window_key` for reflections). | `PATCH /api/colours/{id}` | `UpdateColourRequest`: `prompt` (optional), `negativeExamples`, `positiveExamples` (fragment id arrays). `name` is not updatable here. | Manual tagging: each listed fragment gets its `colour_fragment` link **upserted** — an existing link of any `match_type` is overwritten — to `"manual_negative"` / `"manual_positive"`. Negatives are processed before positives, so a fragment appearing in both arrays ends up `manual_positive`. Link save failures are silently ignored. A `prompt`, when present, overwrites `criteria`; updating criteria triggers **no** re-evaluation of existing fragments and **no** staleness anywhere. There is no archiving surface. | `200` `{colourId, prompt}` (`prompt` = the effective criteria after the update). `400` invalid body or missing id. `404` unknown colour. `500` save failure. |

**Async colour evaluation** (feeds from the § 12 fragment-create hook and from `applyRetroactively`): a single in-memory task queue (capacity 1000) drained by one worker goroutine; the queue does not survive a restart. A new fragment enqueues one task per existing colour; a retroactive backfill enqueues one task per fragment. Per task the worker: skips if **any** `colour_fragment` link already exists for the pair (so an existing `manual_negative` also blocks evaluation); builds the prompt from the colour's `criteria` plus up to 20 manual-positive and 20 manual-negative example fragments; uses the colour-role model; and on output containing `YES` writes a link with `match_type` `"llm_matched_tag_on_input"` (new fragment) or `"llm_matched_backfill"` (backfill), recording the model. Scheduler preemption retries in place. Provider auth/quota failures are recorded durably on the colour record (`last_provider_error_kind`, cleared on the next success); other failures drop the task (the next enqueued fragment effectively retries).

## 9. Rotation & reconcile

| Endpoint | Request | Behaviour & side effects | Response / errors |
|---|---|---|---|
| `GET /api/rotation` | — | Evaluates freshness for **all** projections and reflections in one pass. A dependency graph is built from each entity's `current_context_spec` (`sourceProjectionIds` / `sourceReflectionIds`) and walked in topological order; dependency cycles do not fail evaluation (recursion simply stops at a repeated node). Per entity: the **live snapshot** is the approved snapshot with the highest `approval_sequence_number` (for reflections: across all windows). An entity with no approved snapshot is a *draft*: it is returned with only `id`/`type`, is never stale, and does not block dependents. Otherwise: `newFragmentIds` = fragments the spec resolves to now that the live snapshot's `resolved_context` lacks — the diff is one-way, so a fragment that *left* the context (deleted or untagged) does **not** flag staleness; `staleDependencies` = upstreams whose latest approved snapshot differs from the one consumed (work that can be done now); `blockedBy` = upstreams that are not themselves up to date and have at least one approved snapshot (work that must wait); an upstream qualifying as both is reported only in `blockedBy`; both lists are sorted. `pendingWindows` = never-materialized windows per § 6 tiling. Reflection staleness is evaluated entity-level against the single live snapshot; already-materialized windows are never re-flagged. `upToDateSnapshotId` is set only when all four lists are empty. | `200` `{statuses: [EntityStatus]}` — `id`, `type`, `upToDateSnapshotId`, `newFragmentIds`, `staleDependencies`, `blockedBy`, `pendingWindows` `[{id, start, end}]` (all but `id`/`type` omitted when empty). `500` evaluation failure. |
| `POST /api/reconcile` | No body is read. | Signals the wave worker and returns immediately. The signal is buffered by one: a wave requested while one is running coalesces into a single follow-up wave. **Wave behaviour** (background, after the response): re-derives the stale set with the same evaluator as `GET /api/rotation` and processes entities in dependency order; an entity needs work when any of `newFragmentIds` / `staleDependencies` / `blockedBy` / `pendingWindows` is non-empty. Generation is *speculative*: inside the wave, upstream references resolve to the upstream's **newest snapshot regardless of approval status**, and snapshots are chain-marked (`chain_origin`), so approving a chain top-down settles pre-generated dependents without further generations. Projections generate **pending candidates**; reflections generate **directly approved** snapshots. The wave runs at background queue priority (interactive work preempts it; preempted calls retry in place). Dedup guard: an entity with no pending windows is skipped when its newest snapshot — any status — already matches the current lens, effective model, and freshly resolved context. The first generation failure ends the wave (everything upstream of that point is complete); no run state is reported — candidates land via PocketBase realtime, and queue activity is visible in `llm_queue_status`. | `202`, empty body, unconditionally. |

## 10. LLM provider

| Endpoint | Request | Behaviour & side effects | Response / errors |
|---|---|---|---|
| `GET /api/llm/preflight` | — | Reports whether each LLM role can actually run, without making any provider call. Otherwise (**model-set mode**), each role's model comes from the active model set, the provider is inferred from the model, and the provider's credential environment variable must be set. | Always `200`: `{modelSet, ok, roles: [{role, model?, provider?, ok, detail?}]}` — `ok` is the AND of the per-role results, `detail` explains any failing role. |
| `POST /api/llm/validate` | `ValidateProviderRequest`: `provider` (required), `apiKey`, `defaultModel`, `roleModels` (map role → model; empty values dropped). | Live-tests the candidate provider configuration with a real provider call and **persists nothing** — it exists so the setup flow can try a key/model without saving a broken config (saving validates too, via the § 12 config hooks). | `400` invalid body, missing `provider`, or no model anywhere in the config. Otherwise **always `200`**: `{ok: true}`, or `{ok: false, detail, kind?, provider?, model?}` — `kind` present when the failure is a classified provider error, distinguishing a wrong key from an unreachable provider. |

## 12. Hook-modified collection endpoints

These PocketBase hooks change the behaviour of the built-in `/api/collections/...` endpoints (and apply equally to server-internal writes, where noted).

| Hook | Collection | Behaviour |
|---|---|---|
| `OnRecordCreate` | `fragment` | If `source_time` is unset/zero, defaults it to the current time. Applies to every creation path (direct record create, both ingestion paths). |
| `OnRecordAfterCreateSuccess` | `fragment` | Enqueues asynchronous colour evaluation of the new fragment (§ 8). Fires on every successful creation, from any path. |
| `OnRecordDeleteRequest` | `fragment` | **Soft delete.** If `deleted_at` is unset, sets it to now and saves; the row is never deleted. Returns `204` either way, so repeated deletes are idempotent and the original `deleted_at` is preserved. Applies only to the HTTP delete endpoint (server-internal deletes are not intercepted). |
| `OnRecordCreate` | `ingest` | Runs the async batch-ingestion pipeline described in § 2. |
| `OnRecordUpdateRequest` | `kalaidoscope_config` | Request-level gate: if the submitted body touches `model_set` and the requester is not a superuser → `403` ("model_set can only be changed by a superuser"). PocketBase rules are per-collection, not per-field; this hook is the field-level narrowing. |
| `OnRecordUpdate` | `kalaidoscope_config` | Model-level (also covers programmatic saves), before the row is written — rejection means nothing persisted. When the new state has a provider configured: at least one model is required (`400`, `data.default_model` coded `model_required`); for providers requiring a credential, with a key set, any changed models are **live-validated against the provider** before the write — failure → `400` with `data.api_key` coded `provider_<kind>` (§ 13). Credential-less providers (e.g. Ollama) are not live-checked. After the write commits: the config is published to the LLM layer (takes effect on the next call, no restart) and the request scheduler is reconfigured for the provider. |
| `OnRecordAfterUpdateSuccess` | `kalaidoscope_config` | Requests the background lens-drift distillation pass after any committed config change (a role's effective model may have moved out from under an approved lens). |

## 13. Cross-cutting

**Auth posture.** No middleware — authentication, CORS, or rate-limiting — is bound to any of the 25 custom routes: anyone who can reach the port can call all of them. The only auth-aware handler code is entity pin/unpin (§ 5), which silently no-ops unauthenticated. At boot a `users` record `user@kalaido.local` is found or created (password from `KALAIDO_USER_PASSWORD`, else random) and an auth JWT is printed to stdout as `KALAIDO_USER_TOKEN=…` for the host app to capture. The PocketBase `/_/` dashboard stays reachable, with no superuser record created.

**Collection-level API rules** (govern the built-in `/api/collections/*` endpoints; every enabled operation requires `@request.auth.id != ''`, a disabled one is superuser/server-only):

| Access for authenticated users | Collections |
|---|---|
| Full CRUD | `fragment` (delete intercepted → soft delete, § 12), `ingest`, `chat_conversation`, `chat_message` |
| Read-only (writes server-only) | `colour`, `colour_fragment`, `projection`, `reflection`, `projection_snapshot`, `reflection_snapshot`, `refine_proj_snapshot_conversation`, `refine_refl_snapshot_conversation`, `usage`, `llm_queue_status` |
| Read + update only | `kalaidoscope_config` (no create/delete; `model_set` field superuser-only via § 12 hook) |
| Fully hidden | `lens` (read and write both disabled) |
| Read-only SQL view | `view_stream` (non-deleted fragments with colour indices) |

**Shared error shapes.** Standard PocketBase JSON error envelope for handler-raised errors, plus:

- **Kalaido quota exhausted** — `402` `{error: "quota_exhausted", period: "YYYY-MM", used}`. Emitted by chat (both variants) and snapshot generation when the monthly token quota is spent; token usage is aggregated per period in the `usage` collection.
- **Provider errors** — `{error, kind, provider, model, detail}` with status by kind: auth → `409` `provider_auth_failed`; provider quota → `429` `provider_quota_exceeded`; transient → `502` `provider_transient`; anything else → `502` `provider_error`. `401` is deliberately never used: the PocketBase SDK reads it as session expiry and would log the user out over a bad provider key.
- **Config-save validation** — `400` with `data.api_key` as a validation error coded `provider_<kind>` (or `provider_validation_failed`), and `data.default_model` coded `model_required` when a provider is set without any model (§ 12).
- **Blocked upstream** — `409` plain message on generation routes (§ 5/§ 6).
- **Failure inside a `200`** — `POST /api/llm/validate` (`ok: false`), `GET /api/ollama/status` (`reachable: false`), and `POST /api/ollama/pull` (terminal `{error}` line) report failure in the body, never via status code.

**Response formats.** SSE: `POST /api/chat` (Vercel AI UI-message stream v1 framing with `data: [DONE]` terminator) and `POST /api/colours/preview` (raw record frames, no terminator). NDJSON: `POST /api/ollama/pull`. No body: `202` from `POST /api/reconcile`; `204` from the entity deletes and the intercepted fragment delete. `201` from the three create routes (projections, reflections, refinements). Ad-hoc JSON maps (no declared DTO): entity update → `{"id"}`, refinement commit → `{"snapshotId"}`.
