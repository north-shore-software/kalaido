## 1. The evaluation pass

One pass (`reconcile.Evaluator.EvaluateAll`, constructed with a `now`) evaluates **every live `active`** projection and reflection together. Both loads filter `status = 'active' && deleted_at = ''` (`engine.LiveFilter`): a `proposed` entity or a soft-deleted one is not loaded, so it is neither a node nor an edge endpoint, can be neither stale nor blocking, and is absent from the response. A load error aborts the pass with that error.

1. **Graph build.** Each entity is a node carrying its own `current_context_spec` (a spec that fails to decode is treated as empty — an isolated node). Edges come from the spec's `sourceProjectionIds` / `sourceReflectionIds`; a reference to an id that is not a node (non-existent, `proposed`, or soft-deleted) produces no edge. Edges are built from every node's spec regardless of entity type.
2. **Topological order.** A depth-first visit appends each node after its dependencies, so dependencies precede dependents in the result. The visit never fails: on reaching a node already on the visiting stack (a cycle) it returns without error and without visiting further, so cyclic members are emitted in whatever order the traversal reached them. Root iteration is over a Go map, so the relative order of independent nodes is not stable between passes.
3. **Per-node evaluation** (§ 2), in that order, producing one `EntityStatus{id, type, upToDateSnapshotId?, newFragmentIds?, staleDependencies?, blockedBy?, pendingWindows?, staleWindows?}` per entity (`api.EntityStatus` is an alias of `api.ReflectionStatus`; `type` is `projection` or `reflection`). A resolution error in any node aborts the whole pass with that error; nothing partial is returned.

The pass runs on demand and is never cached or scheduled. It is constructed at three sites:

| Site | Caller | On evaluation error |
|---|---|---|
| `handlers.HandleGetReconcile` | `GET /api/reconcile` (`api.md` § 9): the full list is returned as `statuses`, flattened beside the wave state of § 5 | logs `reconcile evaluation failed`; `500 failed to evaluate staleness` |
| `reconcile.EvaluateEntity` | runs the full pass with `time.Now()` and picks the one row whose `id` matches; an id not in the results (not live-active) yields a **zero** status (empty `id` and `type`, nothing stale). Called from: `HandleGenerateCandidate` (`POST /api/projections/{id}/candidates` and `…/snapshots`) and `HandleGenerateReflectionSnapshot` (`POST /api/reflections/{id}/snapshots` and `…/generate-snapshot`), for the `blockedBy` refusal and — reflections — the stale-window candidates handed to `reflections.WindowsToGenerate` (`lifecycle-projection.md` § 4, `lifecycle-reflection.md` § 5.1); `HandleListReflectionWindows` (`GET /api/reflections/{id}/windows`), for the per-window `stale` flag (`lifecycle-reflection.md` § 9) | the generate handlers log `staleness check failed` at warn and proceed with the zero status (no `409`, no stale-window candidates); the windows listing discards the error without logging (every window `stale: false`) |
| `reconcile.runWaveWithWorker` | the start of every wave (§ 3) | logs `wave evaluate failed`; the wave ends with error `evaluate: …` (§ 5) |

The generate handlers refuse with `409 upstream dependencies are not up to date; approve them first` only when the returned `blockedBy` is non-empty; `newFragmentIds`, `staleDependencies` and the window lists never refuse an interactive generation.

## 2. Per-entity verdict

1. **Live snapshot.** The `approved` snapshot with the highest `approval_sequence_number` for the entity (`<fk> = id && status = 'approved'`, ordered `-approval_sequence_number`, limit 1) — for reflections across **all** window keys. A query error counts as none. None → a *draft*: the status carries only `id` and `type` (no `upToDateSnapshotId`, nothing stale). Drafts never block dependents (step 4).
2. **Reflections with a windowed approved snapshot** → § 2.1, and evaluation ends there.
3. **Context diff.** The entity's `current_context_spec` (the entity's, **not** the lens row's) is resolved now, unwindowed, with the caller's context — none of the three callers marks a generation trigger, so upstreams resolve in ordinary approved-only mode (`context.md` § 2–3: live fragments only, upstreams with `deleted_at = ''` only, newest `approved` snapshot per upstream by `approval_sequence_number`). The result is diffed **one way** against the live snapshot's `resolved_context` (`PinnedIDs.Diff`, `context.md` § 5; a receipt that fails to decode is treated as empty; `expandedIds` is ignored): `newFragmentIds` = fragments now in scope that the snapshot did not consume, in resolution order, unsorted. Each snapshot id now in scope but not consumed is looked up in `projection_snapshot`, then `reflection_snapshot`, and mapped to its parent entity as a candidate `staleDependencies` entry; an id found in neither is dropped silently.
4. **Blocked.** Each direct upstream (edge) whose own verdict has no `upToDateSnapshotId` **and** that has at least one `approved` snapshot (a fresh query; a query error counts as none) is `blockedBy`. A draft upstream never blocks. In a cycle, the member evaluated first reads its not-yet-evaluated upstream's zero verdict, so that upstream is reported as blocking whenever it has an approved snapshot, whatever its own freshness.
5. **Precedence.** An upstream that is both a stale dependency and blocking is reported only in `blockedBy`. Both lists are sorted.
6. **Reflections with only windowless snapshots** additionally report `pendingWindows` = `reflections.PendingWindows`: every window of the series (§ 2.1) with no approved snapshot and no open generation claim (`windows.md` § 3, § 6). No `staleWindows` are produced on this path.
7. **Up to date** ⇔ no new fragments, no stale dependencies, no blockers, no pending windows; then `upToDateSnapshotId` = the live snapshot's id.

Consequences of the one-way diff and the live filters:

- Fragments in the snapshot's receipt that are no longer in scope — soft-deleted, dropped from a colour, unpinned, or of a type removed from the spec — do **not** make an entity stale. Explicitly pinned `fragmentIds` are a static set: a new fragment makes a pin-only entity stale only when it is added to the spec.
- A soft-deleted upstream is excluded three ways: it is not a node (no edge, cannot block or be a stale dependency), its snapshots are excluded from resolution (`projection_id.deleted_at = ''` / `reflection_id.deleted_at = ''`), and because the diff is one-way its disappearance from scope flags nothing. Restoring it reinstates all three.
- A lens change or a model change does not make an entity stale here: the evaluator reads neither `lens_id` nor `generated_by_model`. Those surface only as `lensOutdated` in the windows listing (`lifecycle-reflection.md` § 9), as a candidate window in `WindowsToGenerate`, and as non-current in the wave's `SnapshotIsCurrent` guard (§ 3.1).
- A `pending_review` candidate is invisible to the verdict: only approved rows are compared, and an entity whose only newer output is a candidate stays stale until that candidate is approved.

### 2.1 Windowed reflections

The series is `reflections.SeriesWindows` (`windows.md` § 6): the governing grid, every `reflection_window` backfill row, and every window holding an `approved` or `generating` snapshot, sorted by `start` then `end`. The path applies when any series window has an approved snapshot. For each window, oldest first:

- **No approved snapshot**: `pendingWindows` unless a generation claim is open for it (a generating window appears in neither list).
- **Approved snapshot**: that window key's approved snapshot with the highest `approval_sequence_number` is loaded (a query error or an empty result skips the window silently); it becomes the candidate `upToDateSnapshotId` when its window's `end` is the greatest seen so far (string comparison of the RFC3339 bound); the spec is resolved **inside the window** (`context.md` § 2.1); a resolution error skips the window silently. The one-way diff's new fragments mark the window `staleWindows` and join `newFragmentIds` (deduplicated, then sorted). New snapshot ids in the diff are ignored on this path.

No `staleDependencies` or `blockedBy` are computed on this path even when the reflection's spec names upstreams (its edges still exist, and its verdict still decides whether *it* blocks its dependents). Up to date ⇔ no new fragments, no stale windows, no pending windows; `upToDateSnapshotId` = the approved snapshot of the window whose `end` is greatest.

## 3. The reconcile wave

A wave is one call of `reconcile.runWaveWithWorker`, executed by the single `reconcile.Worker` goroutine (`Run`) each time its `workerutil.Signal` fires (§ 4). Before the call `Run` derives a cancellable `waveCtx` from the worker's lifetime context and, under the state lock, sets `running = true`, `lastStarted = now`, clears `currentEntity` and `progress`, and stores the cancel function (§ 3.2). The wave:

1. Runs one evaluation pass (§ 1) with `time.Now()` under `waveCtx` — no generation trigger, so upstreams resolve approved-only and the worklist is exactly what `GET /api/reconcile` reports. An evaluation error ends the wave.
2. Builds the generation context: `queue.Background` priority (`llm-queue-quota.md` § 2.1; preemptible by interactive arrivals, § 2.4) and the generation trigger `generate_all` (`llmcontext.WithGenerationTrigger`). The trigger switches upstream resolution from "newest `approved` by `approval_sequence_number`" to "newest by `created` of any status other than `generating` / `discarded`", i.e. a `pending_review` candidate or an approved row (`context.md` § 3), and is stamped on every row the wave writes as `generation_trigger`.
3. Fixes the worklist: every status, in the returned order (dependencies before dependents), for which any of `newFragmentIds`, `staleDependencies`, `blockedBy`, `pendingWindows`, `staleWindows` is non-empty. Drafts and up-to-date entities are excluded. `progress` is published as `{completed: 0, total: len(worklist)}` — until this point a running wave reports no `progress`.
4. Walks the worklist. Before each entity, a cancelled `waveCtx` ends the wave with `context.Canceled`. Otherwise `currentEntity = {id, type}` is published and § 3.1 runs. A `blockedBy` entity **is** generated (its blocker was generated earlier in the same walk, and speculative resolution consumes that fresh candidate), unlike an interactive generate, which refuses it with `409`. After each entity, `progress.completed` increments and `currentEntity` clears — an entity that § 3.1 skipped counts as completed.
5. Ends at the first entity error, logged `wave generate failed; ending wave` and returned as `<type> <id>: <err>`; entities later in the order are not visited. Returns nil when every entity that needed work was generated or deliberately skipped.

### 3.1 Generating one entity in a wave

`generateEntity(genCtx, app, status)`:

1. **Strategy and status.** Reflections generate `approved` snapshots (as everywhere else); projections generate `pending_review` review candidates.
2. **Liveness.** `engine.FindLive` failing (the entity was hard-removed or soft-deleted since the pass) logs `wave target skipped` and skips the entity; the wave continues.
3. **Which windows.**
   - `pendingWindows` + `staleWindows` non-empty → exactly those windows, pending first, then stale, in status order.
   - otherwise, a reflection whose governing grid is non-empty (`reflections.CurrentGridWindows` at `time.Now()`) → nothing is generated (a scheduled reflection flagged only by `blockedBy` / `staleDependencies` owes no window and never gets a windowless snapshot);
   - otherwise `engine.SnapshotIsCurrent` true → skipped; else one windowless generation.
4. **`SnapshotIsCurrent`** (the dedup guard; windowed generations do not consult it): the entity's newest `pending_review`-or-`approved` snapshot (ordered `created DESC, approval_sequence_number DESC, rowid DESC`; none or a query error → not current) is current iff its `lens_id` equals the entity's `current_lens_id`; its `generated_by_model`, when non-empty, equals `llm.ResolveRoleFor(RoleSnapshot, generate_with_model)` (`models.md` § 5; an empty stored model, or a role resolution that errors, never fails this check); and the entity's `current_context_spec` (the same spec every generation resolves, `refinement.md` § 6), resolved unwindowed under `genCtx` (speculative upstreams), is identical to the snapshot's `resolved_context` in **both** directions (`llmcontext.DiffPinnedIDs`: nothing added, nothing removed; a resolution error → not current).
5. **Per window**, `engine.GenerateSnapshot(genCtx, …)` (`lifecycle-projection.md` § 4.1–4.2, `lifecycle-reflection.md` § 5.2). Before each attempt a cancelled `waveCtx` returns `context.Canceled`. Outcome mapping: `queue.ErrPreempted` → the same window is retried at once (the retry blocks in the scheduler until a slot frees); `engine.ErrLensNotReady` or `engine.ErrGenerationInFlight` → logged `wave target skipped`, this window is abandoned, the next window (if any) proceeds; any other error — including `usage.ErrExhausted`, the prompt-size guard's error, a role-resolution error, and an error wrapping `context.Canceled` from a cancelled model call — is returned and ends the wave.
6. **What a wave generation writes.** `GenerateSnapshot` claims the per-target (per-window) `generating` row; inside its lifetime the spec is resolved speculatively (step 2 of § 3; a resolution error at this point yields an **empty** source block and an empty receipt, not an error). Output is minimised against the newest approved snapshot of the same lens as for any generation; then:
   - **Settle in place.** When the output equals the approved output (byte-for-byte, or the delta turn reports no change) **and** the context carries a generation trigger, `settleApprovedInPlace` runs in one transaction: if the newest approved snapshot (per window for reflections) still belongs to the current `lens_id`, its `context_spec`, `resolved_context`, `generated_by_model` and `generated_at` are overwritten, every other `pending_review` sibling is set `discarded`, no new row is written, the claim row is released (deleted) and the approved snapshot's id is returned. Its `approval_sequence_number` does not move, so dependents that consumed it are not made stale. If the approved snapshot has moved (none, or another lens), the generation falls through to the ordinary store; a transaction error is returned as `settle in place: …` and ends the wave. An interactive generation that changes nothing still produces a candidate.
   - **Otherwise** the claim row is filled in place with `generation_trigger = generate_all`, other pending siblings discarded, and waiters on the claim are woken; a reflection's row is then approved (`ApproveSnapshot`).
7. **Downstream consequences.** Approval promotes a candidate in place (same id, `lifecycle-projection.md` § 4.3), so a dependent whose wave candidate consumed that row reads as consistent without regeneration. A refinement committed on a still-`pending_review` **projection** candidate carries its `generation_trigger` forward onto the committed snapshot (`InheritsCandidateTrigger` is true for projections, false for reflections); every commit, chain or not, requests a wave (§ 4). An interactive generate that finds the wave's claim row open joins it (`engine.GenerateOrJoin` → `AwaitGeneration`, `lifecycle-projection.md` § 4.1) rather than failing.

### 3.2 Cancelling a wave (yield)

`Worker.CancelWave()` takes the stored cancel function under the state lock and clears it; it reports `true` — and stamps `lastCancelled = now` — only when a cancel function was stored **and** `running` was true; it then calls the function whenever one was stored. The cancel reaches `waveCtx` and therefore `genCtx`: a model call waiting for admission in the scheduler returns the context error, a call in flight is aborted and returns `stream interrupted: context canceled`, `GenerateSnapshot` releases its claim row, and the wave ends with that entity's error (§ 3 step 5) — or with `context.Canceled` at the next per-entity / per-window check. A generation past its last model call is not interrupted: it stores its row and the wave ends at the next check. Entities the wave had not reached are left as they were; nothing re-requests them except the entry points of § 4.

The only caller is `workers.Manager.yieldWave(strat, id)`, run at the start of each of the manager's three interactive generation methods — `GenerateProjectionSnapshot` (from `HandleGenerateCandidate`), `GenerateReflectionSnapshot` (from `HandleGenerateReflectionSnapshot` when exactly one window is to be generated) and `GenerateReflectionWindows` (the same handler, several windows). `yieldWave` first asks `engine.HasLiveClaim(strat, id)`: a `generating` row for that entity (any window) younger than the 10-minute claim TTL means the wave (or another request) is already producing it, so nothing is cancelled and the caller joins that run; otherwise — including when the claim query errors — `CancelWave()` is called whether or not a wave is running, and its result is remembered as `yielded`. After the generation, `afterGenerate(status, produced, yielded)` calls `EnqueueWave()` when `yielded` is true **or** when the generation produced a snapshot with status `approved` (`GenerateReflectionWindows` counts any window succeeding as produced). That request is subject to the automatic-wave policy (§ 4): with `autoWave` off, a wave cut short by an interactive generation is not resumed until the next `POST /api/reconcile`.

## 4. Wave entry points

The worker is built by `workers.New` (`boot-and-workers.md` § 1) with `reconcile.Options{AutoWave}`; its `Run` loop is started when the app serves, then `Manager.BootKicks` runs `LogPolicy` (the boot line `automatic waves on` / `automatic waves off; KALAIDO_AUTO_WAVE=1 enables them; the dashboard starts the wave`) and calls `EnqueueWave` once. The worker wakes on a `workerutil.Signal`, a channel of capacity 1: a notification that finds one buffered is dropped, so any number of requests during a running wave coalesce into exactly one follow-up wave (sound because each wave re-derives its worklist). At shutdown the worker's context is cancelled: a wave in progress ends as in § 3.2 (its outcome recorded as cancelled, not as an error), `Run` returns the context error, and both timers below are stopped and the retry count zeroed.

Two triggers exist:

- **`StartWave()`** — the explicit trigger: stops and clears any pending debounce timer, then signals at once. It works whether or not automatic waves are enabled.
- **`EnqueueWave()`** — the automatic trigger: a no-op unless `autoWave` is set; otherwise arms a 3 s debounce timer (`Options.Debounce`; zero means 3 s) or resets the one already armed, and its expiry signals. A burst of triggers within the quiet period yields one wave.

`autoWave` comes from `KALAIDO_AUTO_WAVE`, parsed once at boot by `config.LoadEnv` (`flag`): after trimming and lower-casing, unset, `0`, `false`, `no` and `off` are **off**; any other value is **on**. `cmd/sidecar/main.go` passes it as `server.Options{AutoWave}` → `workers.Options` → `reconcile.Options`; `server.New` / `NewWithSchema` pass the zero `Options`, so a server built through them never starts a wave on its own. `WaveEnabled()` returns it and is published as `policy.wave` by `GET /api/status` (§ 5). With it off, the boot request, every hook and every handler-side request below are silent and the only waves are those `POST /api/reconcile` starts and the retries of § 5.

## 5. Published wave status and retry

The worker keeps eight in-process values under one lock: `running`, `lastStarted`, `lastError`, `lastCompleted`, `lastCancelled`, `currentEntity`, `progress`, `waveCancel`. They are not persisted; a restart zeroes them.

- On each signal, before the wave: `running = true`, `lastStarted = now`, `currentEntity = nil`, `progress = nil`, `waveCancel` set — together, so a reader never observes a new `lastStarted` without `running`. `progress` appears once the worklist is fixed; `currentEntity` is set and cleared per entity (§ 3).
- After the wave (`afterWave`): `running = false`, `currentEntity = nil`; `progress` is left as the wave last set it. A nil result sets `lastError = ""` and `lastCompleted = now`, resets the retry count, and cancels any pending retry timer. An error wrapping `context.Canceled` (a cancel of § 3.2 or shutdown) sets `lastError = ""` and touches nothing else — `lastCompleted` and the retry count keep their values. Any other error sets `lastError = err.Error()` and leaves `lastCompleted` as it was.
- **Retry.** A failed wave whose error wraps `usage.ErrExhausted` (`llm-queue-quota.md` § 5) is logged `wave quota exhausted; not retrying`; the next real trigger re-enters. A cancelled wave is not retried. Any other failure arms a retry timer at `defaultRetryBackoff[min(retries, 2)]` — 1 min, then 5 min, then 15 min for every further consecutive failure — replacing any pending retry timer, and the timer signals the worker directly (no debounce, no `autoWave` check — a failed manual wave retries on its own). The count resets only on a clean wave.

`Worker.Status()` returns a consistent copy (`State{Running, LastStarted, LastError, LastCompleted, LastCancelled, CurrentEntity, Progress}`, the two pointers deep-copied). `Worker.EvaluateStatus()` maps it to the wire type `api.ReconcileStatus`: `running`; `lastStarted`, `lastCompleted`, `lastCancelled` as RFC3339 UTC, omitted while zero; `lastError` omitted while empty; `currentEntity: {id, type}` and `progress: {completed, total}` omitted while nil. Two routes publish it: `GET /api/reconcile` embeds it at the top level of `api.ReconcilePlanResponse` beside `statuses` (a nil worker yields `running: false` and nothing else), and `GET /api/status` (`status.Evaluate`) carries it as `reconcile` alongside `policy.wave` = `WaveEnabled()`, both omitted from the computation when no worker is wired. Nothing in the backend reads the status back; how a client pairs `lastStarted` with `running` to detect that a wave it started has ended is client behaviour and out of scope.
