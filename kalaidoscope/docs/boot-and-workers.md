## 1. Boot sequence

`main` first parses the environment (`config.LoadEnv`: `KALAIDO_MODEL_SET`, `KALAIDO_USER_PASSWORD`, `KALAIDO_AUTO_WAVE`, `KALAIDO_LLM_TRACE`, `KALAIDO_LOG_LEVEL`, `KALAIDO_HAND_EDIT_CREATE_FRAGMENT`; an unparseable model set or log level prints one stderr line and exits `1`), points `slog` at stderr at that level (stdout is reserved for the `KALAIDO_*` lines the desktop wrapper parses), sets `llm.Trace`, and builds the app through `server.NewWithSchemaWithOptions(pocketbase.Config{HideStartBanner: true}, schema.Options{}, server.Options{AutoWave: env.AutoWave, HandEditCreateFragment: env.HandEditCreateFragment})` — banner hidden because the sidecar binds an OS-assigned port and PocketBase would print port 0. It then layers its own registrations and `Start`s. Three hook chains matter: `OnBootstrap` (database open), `OnServe` (HTTP server about to listen) and `OnTerminate` (process ending). PocketBase sorts a chain's handlers by `Priority` (stable, so equal priorities keep registration order; every `BindFunc` here is priority 0), and a hook body placed *before* `Next()` runs in that order ahead of PocketBase's own step, while a body placed *after* `Next()` runs in **reverse** order once that step has completed.

**In `server.NewWithSchemaWithOptions` (library wiring, in order):**

1. `schema.Install` — `OnBootstrap` (after `Next`, so after PocketBase has opened the data files, run its system migrations and cached collections): the schema runner. Its mode comes from `os.Args` at install time: `schema status` → inspect, `schema retry` → retry (clears the failed marker first), anything else → normal. It reads the failed-upgrade marker `<data dir>/schema-migration-failed.json`. With no schema state table: a database that already has a `fragment` collection **fails boot** ("predates schema versioning"); inspect mode only records status; otherwise it applies the canonical schema, creates the state table and stamps `schema.Version` (currently 4) as a bootstrap. With a state table: a stored version above this binary's prints `KALAIDO_SCHEMA_NEWER={"version":n,"latest":m}` to stdout and **fails boot**; inspect mode or an up-to-date database only records status; a failed marker whose `binaryRev` equals this build's is reported again and **fails boot** (`ErrMigrationFailed`), a marker from a different build is cleared; then the upgrade runs — a `VACUUM INTO` backup at `<data dir>/backups/pre-migration-v<from>-<unix>.db` (newest 3 kept), each version's deltas applied and stamped in turn. A delta failure closes every connection (`ResetBootstrapState`), runs the flavour's `BeforeRestore` hook (unset in the sidecar), copies the backup back over the database, writes the marker, prints one stderr line plus `KALAIDO_MIGRATION_FAILED=<json>` on stdout, and **fails boot**. `schema.RegisterCommand` adds the `schema bootstrap|status|retry` console subcommands; each only prints the status the runner recorded (`schema.md` § 1, § 4).
2. `OnServe` (before `Next`): sets `se.InstallerFunc = nil` (PocketBase's installer would otherwise open the superuser dashboard on every start, since no `_superusers` row is ever created; the dashboard stays at `/_/` for a superuser created by hand), then runs the two **boot sweeps**: `engine.SweepGenerationClaims` deletes every `projection_snapshot` / `reflection_snapshot` row with `status = "generating"` (a failed lookup skips that collection silently; a failed delete is logged — `lifecycle-projection.md` § 4), and `ingest.SweepPending` sets every `ingest` row with `status = 'pending'` to `status = "error"`, `error = "server restarted while processing"` (lookup or save failures logged; a warning with the count when any were found — `ingestion.md` § 3). Both kinds of row can only be live while a goroutine of this process runs, so anything present at boot belongs to a crashed run.
3. `registerWriteEcho` — `OnBootstrap` (after `Next`): unless the app runs with `--dev` (`app.IsDev()`), installs a SQL write-echo logger (`ExecLogFunc`) on both DB handles — every `INSERT INTO`/`UPDATE`/`DELETE FROM` is logged at debug (statement whitespace-collapsed and truncated to 500 runes; a failed statement is logged at error with the driver error), skipping `llm_queue_status` and underscore-prefixed PocketBase tables; reads (`QueryLogFunc` left nil) and DDL are never logged. Because both bootstrap hooks do their work after `Next`, the reverse unwind installs this logger **before** the schema runner in step 1 executes, so schema creation and upgrade writes are echoed too. In `--dev` this hook installs nothing.

At this moment no model set or workspace config has been loaded, so the scheduler is born in the compiled-default provider's shape and reshaped in step 9.
5. `RegisterTriggers`: three hooks on `fragment` (`OnRecordCreate` defaults `occurred_at` to now and `ingested_via` to `"app"`; `OnRecordAfterCreateSuccess` signals workers, § 2; `OnRecordDeleteRequest` soft-deletes by setting `deleted_at` and answers `204` — `ingestion.md` § 7), one on `ingest` (`OnRecordCreate`, via `ingest.RegisterHooks` with the manager's three workers and the runner as `ingest.Deps`, § 3), three on `kalaidoscope_config` via `config.RegisterHooks` (`OnRecordUpdateRequest`, `OnRecordEnrich`, `OnRecordUpdate` — `models.md` § 3).

7. `usage.Setup` — `OnServe` (before `Next`): asserts the `usage` collection exists and has a unique single-column index on `period`; either absence returns an error from the hook, which **fails serve** (`llm-queue-quota.md` § 5).
8. `rt.bind` — `OnServe` (after `Next`): `rt.start()` — `Manager.Start` launches the four services' `Run` loops on the runtime errgroup, then `Manager.BootKicks` (the boot kicks, below). `OnTerminate` (before `Next`): `rt.stop()` (shutdown, below). **In `main` (binary wiring, in order):**

15. `server.EnsureReady` — exits `1` if `llm.Ready()` is false (no provider descriptor and no legacy factory registered). Then `a.Start()`: registers PocketBase's `superuser` and `serve` commands, runs `Bootstrap` (the `OnBootstrap` chain of steps 1 and 3), executes the root command on a goroutine, and blocks until that command returns or `SIGINT`/`SIGTERM` arrives, then fires `OnTerminate` (shutdown, below). A non-nil return is logged (`server stopped`) and exits `1`.

**Order at serve time.** PocketBase's `serve` triggers `OnServe` with a finalizer that builds the router and binds the TCP listener. So the before-`Next` bodies run first, in registration order: step 2 (installer off, sweeps), 6 (routes), 7 (usage index), 9 (queue-status reset and subscribe), 10, 11, 12 (Ollama routes; the preload goroutine starts here, before the listener exists), 13, 14; then the listener binds (no installer runs, since `InstallerFunc` is nil); then the after-`Next` bodies run in reverse order: step 9's `Reconfigure`, then step 8's `rt.start()` — the four service loops start and the **boot kicks** run, in this order: `Colour.Signal()` (a colour drain, § 2.1), `Mapping.KickIfPending()` (`sourcedata.PendingAnnotationCount` — live `fragment` rows without a `fragment_annotation`; `SignalAnnotate` when > 0; a count error is silent and kicks nothing), `Reconcile.LogPolicy()` (one info line: `automatic waves on` or `automatic waves off; KALAIDO_AUTO_WAVE=1 enables them; the dashboard starts the wave`), `Reconcile.EnqueueWave()` (§ 2.2; a no-op unless auto-wave is on). Only after every hook has returned does `Serve` begin accepting connections and the port line print. Nothing in the boot path performs a model call; nothing resumes an interrupted generation — workers that keep their state in the database (§ 2) resume by re-deriving it.

**Shutdown.** `SIGINT`/`SIGTERM` (or the root command returning) fires `OnTerminate`. PocketBase's own `pbGracefulShutdown` handler (priority `-9999`, so first) cancels the base request context — every in-flight request and SSE stream is cancelled — and calls `http.Server.Shutdown` with a 1 s deadline before `Next`. Then, in registration order: `rt.stop()` cancels the runtime root context (every worker loop, every runner task and every wave), starts one goroutine that waits on the worker errgroup then `TrackedRunner.Wait`, and blocks on it for at most `shutdownGrace` = 10 s — logging `workers drained` or `workers still running at shutdown; exiting anyway`; then the queue mirror unsubscribes (`SetOnChange(nil)`) and stops its flush timer; then the Ollama preload context is cancelled; finally PocketBase's finalizer `ResetBootstrapState` closes the database. What cancellation means per loop is in § 2 (each `Run` returns `ctx.Err()`; a drain in progress stops at its next context check); a runner task sees the same cancellation through the context it was given (§ 3). Claim rows a cancelled generation released are deleted by `releaseClaim` if that runs before the database closes; any it did not reach are swept at the next boot (step 2).

## 2. Long-lived workers

`workers.Manager` (`internal/workers/manager.go`) owns the four services and is the object handlers reach workers through (`handlers.Deps` embeds it). `workers.New` constructs `mapping.NewWorker`, `colour.NewWorker`, `reconcile.NewWorker(Options{AutoWave})`, `discover.NewWorker(app, maps)` and wires the cross-worker callbacks — `maps.OnSettle(col.OnMapSettled)`, `maps.OnSettle(rec.OnMapSettled)`, `col.OnDrained(rec.EnqueueWave)` — before any loop runs (the callback slices are unguarded and documented as register-before-`Run`). `Start(ctx, g)` puts each service's `Run(ctx)` on the runtime errgroup; `BootKicks` is § 1. The manager also fronts interactive generation for the handlers (`GenerateProjectionSnapshot`, `GenerateReflectionSnapshot`, `GenerateReflectionWindows`): each first `yieldWave`s — cancels a running wave via `Reconcile.CancelWave()` unless `engine.HasLiveClaim` says this very entity is being produced — then generates (or joins) and, `afterGenerate`, calls `Reconcile.EnqueueWave()` when a wave was cut short or an `approved` snapshot was produced. The outcomes of those pairings are `coordination.md`.

All four services share one shape: a `workerutil.Signal` (a `chan struct{}` of capacity 1; `Notify` is a non-blocking send, so a signal that finds the buffer full is a no-op and bursts coalesce into one drain; `Wait(ctx)` returns `ctx.Err()` on cancellation), a `Run(ctx) error` loop started by the manager, and a drain that re-derives its worklist from the database each pass. None holds an in-memory queue of work items; the discover worker holds only a pending-kind *set*. Every worker additionally exposes in-memory in-flight state that `GET /api/status` reads through each domain's `EvaluateStatus` (`api.md`): colour `WorkerStatus{Draining, CurrentColourID, LastStarted, LastCompleted, LastError}`; mapping `Annotating()`, `Consolidating()`, `WantSettle()`, `LastDrainError()`; reconcile `State{Running, LastStarted, LastError, LastCompleted, LastCancelled, CurrentEntity, Progress}` (also on `GET /api/reconcile`); discover `Running()`, `Pending()`, `WaitingOnMap()`, `CurrentStarted()`. These describe the running process only and reset at boot. A drain ended by context cancellation records no error (`LastError`/`lastDrainError` cleared, nothing logged) in the colour, mapping and reconcile workers; the discover worker logs a cancelled flow like any other failure.

**After-drain callbacks.** `workerutil.Callbacks` is a mutex-guarded slice of `func(error)`: `Add` appends, `Detach` removes and returns the whole batch (`workerutil.CallbackBatch`), and `Invoke` calls each with an error. `mapping.Worker` and `discover.Worker` each own one, exposed as `AfterDrain(fn)`. Each loop `Detach`es at the start of a pass and `Invoke`s the detached callbacks with the pass's error once it ends, so a callback registered *during* a pass runs after the *next* one. The only registrant in the tree is `ingest.startPipeline` (the post-import pipeline, `ingestion.md` § 8): it adds a callback to the mapping worker that, on a nil error, signals the three discover kinds in order, and on any error (a cancelled drain included) does nothing; then it calls `Mapping.Signal()`. The discover worker's `AfterDrain` has no registrant.

**Settle hooks.** `mapping.OnSettle` registers callbacks run after every map cycle — both the cycle a full drain ends with and the ticker's — outside the consolidate lock and regardless of whether consolidation succeeded. Two are registered by `workers.New`, in this order: `colour.Worker.OnMapSettled`, which loads the map version and counts `fragment_annotation` rows (either failure logged and the hook abandoned), compares the pair with the one it last saw (initially `-1, -1`, so the first settle always runs) and, when either changed, recomputes thing-backed membership for every colour (`RematchThings`; errors logged — `colours.md` § 3); then `reconcile.Worker.OnMapSettled`, which calls `EnqueueWave()`.

**Drained hooks.** `colour.OnDrained` registers callbacks run after a colour drain that wrote at least one `colour_fragment` link (a drain that only advanced watermarks runs none). The only registrant, from `workers.New`, is `reconcile.Worker.EnqueueWave`.

**Wave timers.** The reconcile worker owns two one-shot `time.AfterFunc` timers under `timerMu`: the 3 s debounce armed by `EnqueueWave` (reset on every call, stopped by `StartWave`) and the retry timer armed after a failed wave (stopped after a clean one). Both simply `signalWave`. `Run` stops both and zeroes the retry count when it exits.

## 3. Detached per-event goroutines

These are started by requests, hooks or calls and run outside — or alongside — the request that caused them. Work that must outlive a request but end with the process goes through the **runner**: `workerutil.Runner` is `Go(f func(ctx))`; the process's implementation is `TrackedRunner`, which runs `f` on its own goroutine under the runtime root context and counts it in a `WaitGroup` that `rt.stop` waits on (§ 1). `InlineRunner` (runs `f` synchronously under `context.Background()`) and `DiscardRunner` (drops `f`) exist for tests only. The runner has exactly two callers.

Per window: `ErrLensNotReady` is warned, other errors logged, `ErrGenerationInFlight` silently left to its owner. One pass — a failed window is simply still pending next time (`lifecycle-reflection.md` § 5, § 9) | windows without a snapshot remain pending; their claim rows are swept at the next boot |
| **Generation fan-out** | `reflections.GenerateWindows` — one goroutine per window, joined with a `WaitGroup` before returning; used by `Manager.GenerateReflectionWindows` (the reflection generate-snapshot handler when more than one window is requested) and by `GeneratePendingWindows` | each goroutine calls `engine.GenerateSnapshot`, retrying `ErrPreempted` in place; results are returned in window order. Concurrency is bounded only by the scheduler | as above |
| **Detached request contexts** | `context.WithoutCancel(e.Request.Context())` in: the projection generate handler (`POST …/candidates`, `…/snapshots`) and the reflection generate handler (`…/snapshots`, `…/generate-snapshot`) — generation runs on the detached context while joining an in-flight claim (`engine.GenerateOrJoin` → `JoinGeneration`) uses the *request* context capped at the 10 min `GenerationClaimTTL`, waking on the in-process `claimHub` and re-reading the claim row on a 500 ms `time.NewTicker` fallback, and a run that ends abandoned is retried once from scratch; the refinement commit handler; the edit-candidate handler (`projections.ApplyEdit`); and `POST /api/explore/conversations/{cid}/bookmarks/save` (`explore.md` § 7) | the operation completes on the request goroutine even if the client disconnects; no goroutine is spawned and the runner is not involved, so `rt.stop` does not wait for it — PocketBase's 1 s `Shutdown` is the only bound | a claim row left `generating` is swept at the next boot, or taken over by the next claim once older than 10 min |
| **Colour preview fan-out** | `POST /api/colours/preview` | `PreviewSession.Run`: an errgroup limited to 20 judges the 20 newest live fragments at `Interactive` priority, each tied to the request context (a disconnect cancels them; a cancelled call is not logged), plus one goroutine that waits for the group and closes the results channel; the handler streams matches as SSE while they arrive | — |
| **Queue-status writer** | `registerQueueStatus` (`OnServe`, before `Next`): writes the `llm_queue_status` singleton as empty (`state = "idle"`, `running = []`, `waiting = {}`, `held = null`) at boot, then `Scheduler.SetOnChange(m.onChange)` | the scheduler publishes every transition as `go s.onChange(st)` (one short goroutine each; nothing is published while no subscriber is set); the subscriber drops any delivery whose `Version` is not newer than the last accepted or that arrives after `stop`, then coalesces writes behind a 300 ms `time.AfterFunc`; the write sets `state` (`active` when anything is running or waiting, else `idle`), `running`, `waiting`, `held`, into the first existing row or a new one. A missing collection or failed save is logged | the row describes the process, not the workspace; reset at next boot |

After `Next` the hook publishes the config and `Reconfigure`s the scheduler | — |

## 4. What is not background

- Staleness (`reconcile.md` § 1) and the aggregate status (`api.md`) are computed on demand per request; there is no periodic evaluator. The wave evaluates only when signalled.
- Snapshot generation from `POST …/candidates`, `…/snapshots` and `…/generate-snapshot` runs on the request goroutine (or its per-window fan-out), detached from cancellation but not from the request's lifetime, and outside the runner.
- Colour **thing** membership is recomputed synchronously inside the settle hook, `Colour.Rematch`, the colour handlers and the discover colours flow — never by the colour worker, which handles prompt membership only.
- There is no cron: the `time.NewTicker` in the consolidate loop is the only recurring timer. Every other timer is one-shot or call-scoped: the wave debounce and retry `AfterFunc`s, the scheduler's wake `AfterFunc`, the queue-status debounce `AfterFunc`, the 500 ms ticker inside `AwaitGeneration`, the 5 s `time.After` between preload attempts, and the 10 s `time.After` bounding shutdown.
- Nothing at boot calls a model. The Ollama preload asks Ollama to load a model with an empty prompt; it does not pass through the scheduler or usage recording.
- Nothing is resumed after a crash: claim rows and pending ingest rows are swept (§ 1 step 2), pending annotations are re-derived and kicked (`KickIfPending`), colour watermarks resume where they were, pending reflection windows wait for the next commit, backfill or wave, and a `discover_run` or `map_run` left `running` stays `running` — each status axis reports such a row as interrupted when its worker is not currently producing it (`map.md` § 3; `discover.md` § 2).
