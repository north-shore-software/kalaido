## 1. Boot sequence

The binary's `main` builds the app through `server.New(true)` (start banner hidden, because the sidecar binds an OS-assigned port and PocketBase prints the banner before the port is known), then layers its own registrations, then `Start`s. Two hook chains matter: `OnBootstrap` (database open) and `OnServe` (HTTP server about to listen). In both, a hook body placed *before* `Next()` runs in registration order ahead of PocketBase's own step, and a body placed *after* `Next()` runs in **reverse** registration order once that step has completed.

**In `server.NewWithSchema` (library wiring, in order):**

1. `schema.Install` — `OnBootstrap` (after `Next`, so after PocketBase has opened the data files, run its system migrations and cached collections): the schema runner. Its mode comes from `os.Args` at install time: `schema status` → inspect, `schema retry` → retry (clears the failed marker first), anything else → normal. It reads the failed-upgrade marker `<data dir>/schema-migration-failed.json`. With no schema state table: a database that already has a `fragment` collection **fails boot** ("predates schema versioning"); inspect mode only records status; otherwise it applies the canonical schema, creates the state table and stamps `schema.Version` (currently 4) as a bootstrap. With a state table: a stored version above this binary's prints `KALAIDO_SCHEMA_NEWER={"version":n,"latest":m}` to stdout and **fails boot**; inspect mode or an up-to-date database only records status; a failed marker whose `binaryRev` equals this build's is reported again and **fails boot** (`ErrMigrationFailed`), a marker from a different build is cleared; then the upgrade runs — a `VACUUM INTO` backup at `<data dir>/backups/pre-migration-v<from>-<unix>.db` (newest 3 kept), each version's deltas applied and stamped in turn. A delta failure closes every connection (`ResetBootstrapState`), runs the flavour's `BeforeRestore` hook (unset in the sidecar), copies the backup back over `data.db` (after removing `-wal`/`-shm`), writes the marker, prints one stderr line plus `KALAIDO_MIGRATION_FAILED=<json>` on stdout, and **fails boot**. `schema.RegisterCommand` adds the `schema bootstrap|status|retry` console subcommands; each only prints the status the runner recorded (`schema.md` § 1, § 4).
2. `OnServe` (before `Next`): disables PocketBase's installer redirect (no `_superusers` row is ever created; the dashboard stays at `/_/` for a superuser created by hand), then **sweeps generation claims**: every `projection_snapshot` / `reflection_snapshot` row with `status = "generating"` is deleted — a claim can only be live while its goroutine runs in this process. A failed lookup skips that collection silently; a failed delete is logged (`lifecycle-projection.md` § 4).
3. `registerWriteEcho` — `OnBootstrap` (after `Next`): unless the app runs with `--dev` (`app.IsDev()`), installs a SQL write-echo logger on both DB handles — every `INSERT`/`UPDATE`/`DELETE` is logged (statement whitespace-collapsed and truncated to 500 runes, failures suffixed `— FAILED: <err>`), skipping `llm_queue_status` and underscore-prefixed PocketBase tables; reads and DDL are never logged. Because both bootstrap hooks do their work after `Next`, the reverse unwind installs this logger **before** the schema runner in step 1 executes, so schema creation and upgrade writes are echoed too. In `--dev` this hook installs nothing (PocketBase's own full echo applies).
4. `RegisterTriggers`: three hooks on `fragment` (`OnRecordCreate` defaults `occurred_at`/`ingested_via`; `OnRecordAfterCreateSuccess` signals workers, § 2; `OnRecordDeleteRequest` soft-deletes — `ingestion.md` § 7), one on `ingest` (`OnRecordCreate`, § 3), three on `kalaidoscope_config` (`OnRecordUpdateRequest`, `OnRecordEnrich`, `OnRecordUpdate` — `models.md` § 3).
5. `RegisterRoutes` — `OnServe` (before `Next`): a router-wide middleware that sets `X-Kalaido-Schema-Version: <schema.Version>` on every response, `GET /api/schema` (returns `schema.CurrentStatus`, `500` on error), and every custom route (`api.md`).
6. `usage.Setup` — `OnServe` (before `Next`): asserts the `usage` collection exists and has a unique single-column index on `period`; either absence returns an error from the hook, which **fails serve** (`llm-queue-quota.md` § 5).
7. Worker wiring, in this order: `colour.Register`, `reconcile.Register` (also sets `engine.RequestWave = reconcile.EnqueueWave`), `mapping.Register`, `mapping.OnSettle(colour.OnMapSettled)`, `mapping.OnSettle(reconcile.OnMapSettled)`, `colour.OnDrained(reconcile.EnqueueWave)`, `discover.Register`, `registerQueueStatus` — the workers, hooks and callbacks of § 2 and § 3. Each `Register` starts its loop goroutine immediately (before bootstrap has even run); the loops block on their channels until signalled.
8. `OnServe` (after `Next`): `llmq.Reconfigure(llmq.ConfigForProvider(llm.ActiveProviderID()))` — reshapes the LLM scheduler for the provider that ended up active once steps 9–10 have run (`llm-queue-quota.md` § 2). Until then the scheduler runs with the Ollama shape it was constructed with.

**In `main` (binary wiring, in order):**

9. `resolveModelSet` — `OnServe` (before `Next`): reads the single `kalaidoscope_config` row (first of `FindAllRecords`, or a new record). A missing collection is logged and the compiled default stays. If `model_set` is empty it is **seeded** from `KALAIDO_MODEL_SET` (default `local`; an unparseable value is `log.Fatal`) and saved — a failed save is logged and the value is used for this run only. Otherwise the stored value wins; an env value that disagrees is logged and ignored; a stored value that no longer parses is **fatal** (`models.md` § 1).
10. `config.LoadAtBoot` — `OnServe` (before `Next`): if a config row exists and `Configured()` is true, publishes it with `llm.SetWorkspaceConfig` and logs provider, default model and override count; otherwise does nothing (`models.md` § 3).
11. `llm.SetProviderFactory` — immediate, not a hook: the one place providers are constructed (`models.md` § 2).
12. `ollama.RegisterRoutes` — `OnServe` (before `Next`): 2 routes. `ollama.RegisterPreload` — `OnServe` (before `Next`): `go preloadDefaultModel(context.Background())` (§ 2.6).
13. `seedSidecarUser` — `OnServe` (before `Next`): a missing `users` collection is skipped silently; otherwise finds or creates the auth record `user@kalaido.local`, sets its password from `KALAIDO_USER_PASSWORD` (or a random one) **on every start**, mints an auth token and prints `KALAIDO_USER_TOKEN=<jwt>` to stdout for the desktop wrapper. A failed save or token mint is logged, not fatal.
14. `reportPort` — `OnServe` (before `Next`): wraps `se.Server.BaseContext`; the wrapper runs once, when `http.Server.Serve` starts, and prints `KALAIDO_PORT=<n>` plus a three-line banner.
15. `server.EnsureReady` — **fatal** if no provider factory is registered. Then `a.Start()`: registers PocketBase's `superuser` and `serve` commands, runs `Bootstrap` (the `OnBootstrap` chain of steps 1 and 3), executes the root command on a goroutine, and blocks until that command returns or `SIGINT`/`SIGTERM` arrives, then fires `OnTerminate` — to which **nothing** in this tree subscribes.

**Order at serve time.** PocketBase's `serve` triggers `OnServe` with a finalizer that builds the router and binds the TCP listener. So the before-`Next` bodies run first, in registration order (steps 2, 5, 6, queue-status reset, 9, 10, 12, 13, 14); then the listener binds; then the after-`Next` bodies run in reverse order: step 8's `llmq.Reconfigure`, then `mapping`'s boot check (a full scan of live `fragment` and `fragment_annotation` rows; `SignalAnnotate` when any live fragment lacks an annotation; a scan error is silent), then `reconcile`'s log line (`automatic waves on/off`) and `EnqueueWave()`, then `colour.Signal()`. Only after every hook has returned does `Serve` begin accepting connections and the port line print. Nothing in the boot path performs a model call; nothing resumes an interrupted generation — workers that keep their state in the database (§ 2) resume by re-deriving it.

## 2. Long-lived workers

All five loops share one shape: a package-level `chan struct{}` of capacity 1 as the wake signal (a signal that finds the buffer full is a no-op, so bursts coalesce into one drain), a loop goroutine started in `Register`, and a drain that re-derives its worklist from the database each pass. None holds an in-memory queue of work items; the discover worker holds only a pending-kind *set*. The mapping, discover and reconcile workers additionally expose in-memory in-flight state (`Annotating`, `Consolidating`, `LastDrainError`; `Running`, `Pending`; `Status{Running, LastStarted, LastError, LastCompleted}`) that `GET /api/organize` reads (`organize.md` § 2); these describe the running process only and reset at boot.

**Follow-up queue.** `internal/followup.Queue` is a mutex-guarded slice of `func(error)`: `Add` appends, `Take` removes and returns the whole slice, `Run` calls each with an error. `mapping` and `discover` each own one, exposed as `AfterDrain(fn)`. Each loop `Take`s at the start of a drain and `Run`s the taken callbacks with the drain's error once it ends, so a callback registered *during* a drain runs after the *next* one. The only registrant in the tree is `ingest.startPipeline` (the post-import chain, `organize.md` § 8): it adds a callback to the mapping queue that, on a nil error, signals the three discover kinds in order, and on any error does nothing; then it calls `mapping.Signal()`. The discover queue has no registrant.

**Settle hooks.** `mapping.OnSettle` registers callbacks run after every map cycle — both the cycle a full drain ends with and the ticker's — outside the aggregate lock and regardless of whether consolidation succeeded. Two are registered, in this order: `colour.OnMapSettled`, which compares the map version and `fragment_annotation` count with the pair it last saw and, when either changed, recomputes thing-backed membership for every colour (errors logged, `colours.md` § 3); then `reconcile.OnMapSettled`, which calls `EnqueueWave()`.

**Drained hooks.** `colour.OnDrained` registers callbacks run after a colour drain that wrote at least one `colour_fragment` link (a drain that only advanced watermarks runs none). The only registrant is `reconcile.EnqueueWave`.

**Wave timers.** The reconcile worker owns two one-shot `time.AfterFunc` timers: the 3 s debounce armed by `EnqueueWave` (reset on every call, stopped by `StartWave`) and the retry timer armed after a failed wave (stopped after a clean one). Both simply signal the loop.

## 4. What is not background

- Staleness (`rotation.md` § 1) and the organise status (`organize.md` § 1) are computed on demand per request; there is no periodic evaluator. The wave evaluates only when signalled.
- Snapshot generation from `POST …/candidates` and `…/generate-snapshot` runs on the request goroutine (or its per-window fan-out), detached from cancellation but not from the request's lifetime.
- Colour **thing** membership is recomputed synchronously inside the settle hook, the colour handlers, and the discover colours flow — never by the colour worker, which handles prompt membership only.
- There is no cron: `time.Tick` in the aggregate loop is the only recurring timer. Every other timer is one-shot or call-scoped: the wave debounce and retry `AfterFunc`s, the scheduler's wake `AfterFunc`, the queue-status debounce, the 500 ms ticker inside `AwaitGeneration`, and the 5 s `time.After` between preload attempts.
- There is no shutdown hook: `SIGINT`/`SIGTERM` ends the process without draining or signalling any worker; in-flight generations end with it, and their claim rows are swept at the next boot (§ 1 step 2).
- Nothing at boot calls a model. The Ollama preload asks Ollama to load a model with an empty prompt; it does not pass through the scheduler or usage recording.
