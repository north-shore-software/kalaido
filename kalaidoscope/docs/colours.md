## 1. Objects

**`colour`** (`schema.md` § 2.3; `DisableWriteOperations`, so server-written only): `name` (required), `swatch` (number; palette slot, § 1.1), `prompt`, `thing_ids` (JSON array of map thing ids; written only by the discover colours flow, never by any colour route), `prompt_match_completed_up_to_fragment_id` (relation → `fragment`, max 1, no cascade; the worker's watermark, § 4), `last_provider_error_kind` (§ 4.2), `created_by_discover_run_id` (relation → `discover_run`, max 1; empty = human-created), `created`, `updated`. A colour created on `POST /api/colours` gets `name`, `prompt` (both trimmed) and `swatch`; one created by discover (`internal/discover/colours.go`) gets `name`, `swatch`, `thing_ids` (resolved to canonical thing ids), `created_by_discover_run_id` when the flow runs under a run record, and no prompt (`discover.md` § 4).

**`colour_fragment`** (`schema.md` § 2.4; server-written): one row per `(colour_id, fragment_id)` (unique index `idx_colour_fragment_pair`, plus `idx_colour_fragment_colour` and `idx_colour_fragment_fragment`), `match_type` (select, required, one of the four values), `created`. Both relations are required and cascade-delete: deleting a colour, or hard-deleting a fragment, removes its rows. No row records which model decided a `prompt` match.

**Membership** = every row whose `match_type != 'manual_negative'`. Every reader applies that rule: `sourcedata.ColourMemberIDs` (behind `colour.MemberIDs`, used by the discover colours flow, and behind `llmcontext.FragmentIDsForColours`, context resolution — `context.md` § 2), `sourcedata.ColourMembersMap` (the discover run context, `discover.md` § 3.4), and the `view_stream` view's `colour_ids` column (`schema.md` § 2.17). `ColourMemberIDs` trims and drops blank colour ids, returns `nil` for an empty list, and de-duplicates fragment ids in row order; `ColourMembersMap` with an empty list returns membership for every colour. A `manual_negative` row is an exclusion; because it occupies the pair's single row it also stops the worker and the thing writer from ever adding the pair back (§ 2).

None of the readers filters soft-deleted fragments at the join: a row for a fragment with `deleted_at` set is still returned as a member here; context resolution drops it afterwards through its own `deleted_at = ''` clause on the fragment query, and `view_stream` selects only live fragments.

### 1.1 Swatch

`colour.NextSwatch(app)` = `count(colour rows) mod 8` (`SwatchCount`), evaluated immediately before the new row is inserted, by both the create path (`colour.Create`) and the discover flow. Nothing enforces uniqueness, nothing ever rewrites the value, and the server never reads `swatch` back.

## 2. Match types and precedence

| `match_type` | Written by | Meaning |
|---|---|---|
| `manual_negative` | `SetManual` (create/PATCH examples) | Excluded, whatever else says |
| `manual_positive` | `SetManual` (create/PATCH examples) | Included |
| `thing` | `applyThingRows` (settle hook, `Rematch`, discover create), `MatchPair` (after a clear) | The fragment's annotation cites one of the colour's `thing_ids` |
| `prompt` | worker (§ 4); `SetPromptMatch` at create (§ 5) | The colour role answered YES to the colour's prompt |

One row per pair; when several reasons apply the higher row in this table wins. The precedence is enforced by the writers, not by a constraint (`internal/colour/match.go`):

- `SetManual` inserts when the pair has no row, is a no-op when the row already has the requested type, and otherwise retypes the existing row in place (its `created` is kept).
- `applyThingRows` deletes only rows of type `thing` that are no longer wanted and inserts `thing` only for wanted fragments that hold **no** row of any type; rows of any other type are never touched.
- `SetPromptMatch` and the worker skip any pair that already holds a row of any type.
- `ClearManual` deletes the row only if it is `manual_positive` or `manual_negative`; on a `thing` or `prompt` row it returns without change and without re-deriving. After a delete (or when the pair had no row at all) it calls `MatchPair`, which re-creates a `thing` row when the fragment's annotation cites one of the colour's things. A prompt match is **not** re-judged by a clear; that pair is judged again only after the watermark is reset (§ 5, `Rematch`).

Consequences: a pair judged `prompt` that later gains a thing citation stays `prompt`; a pair holding `thing` is never sent to the model; `Rematch` deletes the `prompt` rows *before* recomputing things, so a pair that was `prompt` and cites a thing comes back as `thing`.

## 3. Thing-backed membership

`rematch(app, colours)` (serialised by the package-level `rematchMu`, shared with `MatchPair`): for each colour, if `thing_ids` is non-empty (an unparseable field reads as empty) the map index is loaded once per call via `sourcedata.LoadMapIndex` — the document and version (`LoadMapDocument`; an empty document at version 0 when no `kalaidoscope_map` row exists), every `fragment_annotation` row in `created` order (`LoadAnnotationRows`; rows of soft-deleted fragments included), and the `ByThing` reverse index (`IndexRows`: each citation's `ref`, else `name`, resolved through `Document.Resolve` — exact thing id, else normalised name or alias; `map.md` § 4). Each entry of `thing_ids` is resolved the same way; an unresolvable entry is skipped silently. The wanted set is every fragment whose annotation row cites any resolved thing. `applyThingRows` then diffs as in § 2. A colour with no `thing_ids` gets its `thing` rows deleted and nothing inserted. The first colour whose diff fails aborts the pass with `colour <id>: <err>`; earlier colours keep their writes.

Triggers:

- **`Worker.OnMapSettled`** — registered by `workers.New` as `maps.OnSettle(col.OnMapSettled)`, before `maps.OnSettle(rec.OnMapSettled)`, so membership is recomputed before the wave that consumes it. The settle hooks run after every map cycle: at the end of a full annotate drain (when the drain's context is still live) and on each due consolidate tick (`map.md` § 3.2). The hook reads the map version (`sourcedata.LoadMapDocument`) and `count(fragment_annotation)`; an error in either is logged and the hook returns without touching its mark. It compares the pair with a per-worker `settledMark` (initialised to −1/−1, so the first settle after boot always proceeds); the mark is updated **before** the rematch runs, and when both values are unchanged the hook returns without work. It then calls `RematchThings` (every colour, `sourcedata.FindAllColours` in `created` order); an error is logged, the mark is not rolled back, so a failed pass is not retried until the map version or the row count changes again.
- **`RematchThingsFor(app, colourID)`** — one colour (a lookup failure is returned); from `Worker.Rematch` (§ 5) and from the discover colours flow immediately after it saves a colour, before it reads the new colour's members (`discover.md` § 4).
- **`MatchPair(app, colourID, fragmentID)`** — one pair, from `ClearManual` only (§ 2). Loads the colour (lookup failure returned); no `thing_ids` → returns nil. Reads the fragment's first `fragment_annotation` row (query error returned; no row → nil; unparseable `things` → nil), loads the map document, resolves the colour's `thing_ids` to wanted thing ids, then walks the row's citations (`ref`, else `name`): on the first citation resolving to a wanted thing it inserts `thing` if the pair holds no row (any existing row → nil), and returns.

## 4. Prompt-backed membership (the worker)

`colour.NewWorker(app)` builds the worker (`internal/colour/worker.go`); `workers.New` constructs it and `workers.Manager.Start` runs `Worker.Run(ctx)` in the runtime's errgroup once the app serves (`boot-and-workers.md` § 2). `Run` loops on `signal.Wait` until the context is cancelled, then returns `ctx.Err()`. `Signal()` is a `workerutil.Signal` notify: a capacity-1 channel send that drops when a wake is already pending. Signal sites: `OnRecordAfterCreateSuccess("fragment")` in `server.RegisterTriggers` (every fragment birth regardless of `ingested_via`, imports included — `ingestion.md` § 7), `HandleCreateColour` when the saved prompt is non-empty, `Worker.Rematch`, and `Manager.BootKicks` (the first kick at boot, so a watermark left by a crash or a provider outage resumes).

Per wake, `Run` stamps `lastStarted`, sets `draining` true, runs `drain`, clears `draining` and `currentColourID`, then records the outcome (§ 7): `err == nil` → `lastError` cleared and `lastCompleted` = now; `context.Canceled` → `lastError` cleared, `lastCompleted` untouched, nothing logged; any other error → `lastError` = its text, `lastCompleted` untouched, logged as `drain failed`.

`drain`: every colour with `prompt != ''` in `created` order (none → returns with nothing done); the colour role is resolved once per drain with `llm.ResolveRole(RoleColour)` and no per-colour override (`models.md` § 5) — a resolution failure ends the drain with nothing written. Before each colour the worker checks `ctx.Err()` (cancelled → returns the count so far and the context error) and publishes the colour as `currentColourID`. Calls run under the worker context at the role's default priority, Idle (`llm-queue-quota.md` § 2.1). Colours are drained in sequence; `usage.ErrExhausted` (quota admission, `llm-queue-quota.md` § 5) from any colour ends the whole drain at once (later colours wait for the next signal); any other colour error is remembered as the drain's first error and the next colour is still attempted.

`drainColour`: renders the few-shot blocks once per colour — the fragments of the colour's 20 (`exampleLimit`) newest `manual_positive` rows and 20 newest `manual_negative` rows (newest by the link row's `created`; a link query error yields an empty block), loaded by id through `llmcontext.LoadFragmentsByIDs` (`FindRecordsByIds`, no `deleted_at` filter, so a soft-deleted example still renders) and rendered with `llmcontext.RenderFragmentRecords`. Then pages **live** fragments (`schema.NotDeleted()`, i.e. `deleted_at = ''`) in `created,id` order, 200 (`pageSize`) at a time, starting strictly after the watermark fragment (`created > wm.created`, or equal `created` and `id > wm.id`); an empty watermark, or one whose fragment no longer loads, starts from the beginning. For each fragment on the page with no `colour_fragment` row of any type for this colour (`linkedFragmentIDs`, one `IN` query per page): `prompts.ColourEvalPrompt(prompt, positives, negatives, target)` (`prompts.md` § 2) via `usage.GenerateOnce`; `queue.ErrPreempted` retries the same judgment until it completes; a YES per `prompts.ParseYesNo` (the reply's leading letters, case-insensitively equal to `yes`) inserts a `prompt` row. After each page the watermark is set to the page's last fragment id and the colour saved, whether or not anything was written. An empty page ends the colour.

Failure posture: any judging error other than preemption stamps the marker (§ 4.2) and ends this colour's drain with the watermark at the last **completed page** — `prompt` rows already inserted from the partial page persist and are skipped next time; the NO-judged pairs of that page are judged again. A page query, link query, insert, or save error ends the colour likewise. There is no per-fragment retry count, no error row, and no back-off beyond the scheduler's. Cancellation of the worker context surfaces inside a page as a `GenerateOnce` error (`stream interrupted`, or the scheduler's admission error), which is not a `ProviderError` and so leaves the marker alone; the drain then returns `ctx.Err()` at the next colour boundary.

### 4.1 Drained hook

`drain` counts the `prompt` rows it wrote; when the count is greater than zero `Run` calls every function registered with `Worker.OnDrained` (a plain slice, appended before `Run` starts), in registration order, after the outcome has been recorded — including after a drain that ended in error. `workers.New` registers `rec.EnqueueWave` (`reconcile.md` § 4). A drain that only advanced watermarks, or that wrote nothing before failing, fires nothing.

### 4.2 Provider error marker

The worker has no request to fail, so a `*llm.ProviderError` whose `Kind` is `auth` or `quota` (`llm-queue-quota.md` § 6; for HTTP-classified providers 401/403 and 429) is written to the colour's `last_provider_error_kind` — only when the stored value differs — and the drain of that colour stops; a save failure is logged. Any other error kind (`transient`, `other`), a non-`ProviderError` (including `usage.ErrExhausted` from the local quota and a cancellation), and a model-resolution failure leave the field untouched. The next judgment that returns without error for that colour clears it (a write, logged on failure, only when it is non-empty) — before the reply is parsed, so a NO clears it too. The preview route never writes it.

## 5. Routes

All five are registered in `RegisterRoutes` (`server/server.go`). `findColour` reads `{id}` from the path: empty → `400 "missing id"`; unknown → `404 "colour not found"`. Every body-taking route binds a named struct from `internal/api/colours.go`; a body that fails to bind is `400 "invalid request body"`.

- **`POST /api/colours/preview`** `{prompt, positiveExamples?, negativeExamples?}` (`PreviewColourRequest`). `colour.PreparePreview` loads the 20 newest live fragments (`deleted_at = ''`, `-created`; a query error is `500 "failed to fetch fragments"`), then resolves `RoleColour` (`colour.ErrNoModel` → `500 "no model configured for colour matching"`). The handler sets `Content-Type: text/event-stream`, `Cache-Control: no-cache`, `Connection: keep-alive`, requires an `http.Flusher` (`500 "streaming unsupported"`), then commits `200` and flushes before any judgment. `PreviewSession.Run` wraps the request context with `queue.WithPriority(Interactive)` (`llm-queue-quota.md` § 3), renders the example blocks once (ids loaded by `FindRecordsByIds`, no `deleted_at` filter, unknown ids dropped silently), and judges the fragments in an errgroup limited to 20 at a time (`PreviewWorkers`), each via `usage.GenerateOnce` with the same `ColourEvalPrompt`; there is no preemption retry. A YES sends `data: <fragment record JSON>\n\n` and flushes, in completion order, not creation order. A per-fragment error drops that fragment (logged only when the request context is not yet cancelled); a marshal error skips the fragment; a write error ends the stream and the handler returns nil. Zero matches, or zero fragments in the workspace, is an empty stream. Nothing is written to the database; no marker is set.
- **`POST /api/colours`** `{name, prompt, fragmentIds?, positiveExamples?, negativeExamples?}` (`CreateColourRequest`). `name` blank after trim → `400 "name is required"` (checked in the handler before `colour.Create`, whose own `ErrNameRequired` is therefore unreachable from the route). `colour.Create`: `swatch` from `NextSwatch` (§ 1.1), then the row is saved with trimmed `name` and `prompt`; each `fragmentIds` entry — the preview's matches, judged by the same prompt — goes through `SetPromptMatch` (a `prompt` row unless the pair already has one); a failure (including a relation error for an id that is not a fragment) is logged as a warning and that id skipped, with no effect on the response. Examples are applied last (§ 5.1). Any error from `Create` — collection lookup, swatch count, save, examples — is `500 "failed to create colour"`; the colour and any seeded rows written before an examples failure stay committed. If the saved prompt is non-empty the worker is signalled. `deps.Reconcile.EnqueueWave()` is called unconditionally. `thing_ids` and `swatch` are not on the wire. Response `200 {colourId}`.
- **`PATCH /api/colours/{id}`** `{name?, prompt?, positiveExamples?, negativeExamples?, clearExamples?}` (`UpdateColourRequest`; `name` and `prompt` are pointers). `colour.Update` re-loads the colour (a failure here is `ErrNotFound`, reported as `500 "failed to update colour"` since `findColour` has already passed). Examples are applied first (§ 5.1; a failure is `500 "failed to update colour"` before any rename or prompt change is saved). `name` is applied, trimmed, only when present and non-blank after trim; an absent or blank name is ignored silently. `prompt`, when present, is trimmed and stored even if blank; `promptChanged` is true when the trimmed value differs from the stored one (so clearing a prompt counts as a change). The row is saved (`500 "failed to update colour"`); if `promptChanged`, `Worker.Rematch` runs (`500 "failed to restart matching"`) and then `EnqueueWave()`. A PATCH that only changes examples or the name enqueues no wave and signals no worker. Response `200 {colourId, name, prompt}` from the saved record.
- **`POST /api/colours/{id}/rematch`** — no body is read. `Worker.Rematch` (`500 "failed to restart matching"`), `EnqueueWave()`, `202` with no content.
- **`DELETE /api/colours/{id}`** — `colour.Delete` re-loads the colour, then in one transaction: `engine.ScrubContextSpecs` walks, for each of `projection` and `reflection`, every row whose `current_context_spec ~ <colourId>` (substring match; no `deleted_at` filter, so soft-deleted entities are scrubbed too), removes the id from `colourIds` (`scrubSpec` → `engine.RemoveID`) and, when the spec's combined id count shrank, re-serialises the whole spec into `current_context_spec` (a row whose spec fails to parse is skipped silently); then the colour is deleted, cascading its `colour_fragment` rows. A failure anywhere rolls the transaction back → `500 "failed to delete colour"`. Not scrubbed: `lens.context_spec` and the frozen `context_spec` of every `projection_snapshot` / `reflection_snapshot`. No wave is enqueued and no worker signalled. Response `204`.

**`Worker.Rematch(colourID)`** (`internal/colour/worker.go`): loads the colour (a lookup failure is returned to the caller), deletes every `prompt` row of the colour (first delete error returned), sets `prompt_match_completed_up_to_fragment_id` to empty and saves, runs `RematchThingsFor` (§ 3), then `Signal()`s the worker. Manual rows survive; the worker only re-judges the colour if its prompt is non-empty. Each step's failure leaves the earlier steps' writes in place (no transaction).

### 5.1 Applying examples

`colour.ApplyExamples(app, colourID, positive, negative, clear)` writes negatives first (`SetManual … manual_negative`), then positives (`manual_positive`, so a fragment named in both lists ends up `manual_positive`), then clears (`ClearManual`, § 2). Each write is sequential and the first error aborts the rest; earlier writes stay. Example ids are not checked against the `fragment` collection by the handler or by `ApplyExamples`: an id that is not a fragment fails PocketBase's relation validation on save, which the routes report as `500 "failed to create colour"` / `500 "failed to update colour"`. On create the clear list is always nil.

## 6. Cross-subsystem effects

- Context resolution (`context.md` § 2) reads membership live at each generation; a snapshot's pinned receipt freezes the member set at that moment (`context.md` § 5), and the reconcile evaluator diffs against it (`reconcile.md` § 1). Writers that change membership ask for a wave explicitly: create, a prompt-changing PATCH, the rematch route (all via `deps.Reconcile.EnqueueWave()`), and a drain that wrote at least one `prompt` row (§ 4.1). Thing rematches from the settle hook rely on `rec.OnMapSettled`, registered after the colour hook, rather than enqueueing themselves (`reconcile.md` § 4); a PATCH that only changes examples requests nothing, and a `ClearManual` re-derivation requests nothing.
- `view_stream` (`schema.md` § 2.17) exposes, per live fragment, `colour_ids` = the JSON array of its member colour ids (every `colour_fragment` row except `manual_negative`); the palette slot is the colour's own `swatch`.
- Discover reads every colour in `created` order (`sourcedata.FindAllColours`) with `sourcedata.ColourMembersMap` and `colour.ThingIDs` for its run context and `list_existing` (`discover.md` § 3.1, § 3.4); its colours flow creates thing-backed colours with `colour.NextSwatch`, calls `colour.RematchThingsFor` and reads `colour.MemberIDs` so they have members before the run continues (`discover.md` § 4). Its projection and reflection proposals write `colourIds` into `current_context_spec`, which is what the delete-time scrub (§ 5) cleans.
- The worker's judging calls and the preview share the LLM scheduler and usage quota with everything else (`llm-queue-quota.md` § 1, § 5); `boot-and-workers.md` § 2 lists the worker alongside the other signal-driven loops, and `coordination.md` places a colour drain against the other units of work.

## 7. Status axis

`GET /api/status` (`api.md` § 8 indexes the route; the aggregate is `status.Evaluate`) carries the colour axis as `colour` (`api.ColourStatus`), produced by `colour.EvaluateStatus(app, worker)`:

| Field | Source | Value |
|---|---|---|
| `draining` | in-process | `Worker.draining` — true from the start of `drain` until it returns |
| `currentColourId` | in-process (`omitempty`) | the colour `drain` is judging; cleared when the drain returns |
| `lastStarted` | in-process (`omitempty`) | RFC 3339 UTC of the last wake; empty before the first |
| `lastCompleted` | in-process (`omitempty`) | RFC 3339 UTC of the last drain that returned without error; untouched by a cancelled or failed drain |
| `lastError` | in-process (`omitempty`) | text of the last drain's error; cleared by a clean or cancelled drain |
| `totalColoursCount` | rows | `count(colour)` |
| `promptColoursCount` | rows | colours with `prompt != ''` |
| `unjudgedFragments` | rows | for each prompt colour, `count(fragment)` under `pastWatermarkFilter` — live fragments after that colour's watermark in `(created, id)` order — summed over the prompt colours |

A nil worker (no manager wired) leaves the five in-process fields at their zero values and still fills the three counts. `unjudgedFragments` counts fragments past the watermark whether or not they already hold a row for the colour, so it is the drain's remaining scan, not the number of pending model calls; a watermark whose fragment no longer loads counts every live fragment. Any query error returns the axis as filled so far together with the error, which the status route reports as `500 "failed to evaluate status"`. The axis has no state word: `draining`, the counts and `lastError` are the whole surface; `last_provider_error_kind` (§ 4.2) is read from the `colour` row by the client, not aggregated here.
