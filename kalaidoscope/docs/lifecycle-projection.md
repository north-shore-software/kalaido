## 1. Objects and states

A projection is a `projection` row: `name`, `status` (`proposed` | `active`), `description`, `current_context_spec` (JSON; the scope every generation resolves — owned by the entity, the lens carries no copy), `current_lens_id`, `generate_with_model` (per-entity model override, empty = workspace role default), `pinned_by` (users), `created_by_discover_run_id` (empty = human-created), `deleted_at` (the soft-delete stamp, § 6), and the autodates `created`/`updated`. Its output history is a series of `projection_snapshot` rows. A snapshot has four statuses:

| Status | Meaning |
|---|---|
| `generating` | A claim row: a generation is running (§ 4.1). Not output. |
| `pending_review` | A finished candidate awaiting the user. At most one per projection (every path that finishes or approves one discards its siblings). |
| `approved` | Promoted at some point. Not necessarily current. |
| `discarded` | A superseded candidate. Not output. Never deleted. |

The **current** output is a derivation: the `approved` snapshot with the highest `approval_sequence_number` (unique per projection by the partial index `idx_projection_snapshot_approval_seq`, `WHERE status = 'approved'`). Approval promotes a row in place (same id). A snapshot carries three text columns and an edit list (schema v5, `schema.md` § 1.4): `output` — the published text, read by every consumer (context hydration, `context.md` § 4; the minimal-diff anchor, § 4.2); it is empty on a `pending_review` candidate produced by generation, a hand edit or the refinement chat, and is filled from the draft at approval (§ 4.3); `output_draft` — the reviewer's working text, in which every undecided edit appears as a marker line `<<<edit:<id>>>>` (`EditMarkerPrefix`/`EditMarkerSuffix` in `internal/engine/diff.go`) standing in for the passage it concerns; `output_raw` — the model's candidate as returned, before the minimal-diff rewrite; `edits` — a JSON array of `SnapshotEdit` (wire: `id`, `sequence`, `type`, `status`, `contentBefore`, `contentAfter`, `blockIndex`, `fragmentId`, `inlinedText`, `anchorPrev`, `anchorNext`, `supersededBy`, `undoable`, `undoReason`, `createdAt`, `updatedAt`; `internal/api/edits.go`), always written as an array (never null) by the engine's spec stamping. An edit's `type` is `regeneration` (a machine diff between the previous approved text and a regeneration, § 4.2), `refinement` (a passage the refinement chat proposed, `refinement.md` § 3) or `manual` (a hand edit, § 4.4); its `status` is `proposed` (a marker is in the draft), `approved` or `rejected` (inlined into the draft, § 4.5), or `superseded` (revised by a later proposal or overtaken by a regeneration). The draft is segmented into **blocks** — runs of non-blank lines, with a fenced code block (```` ``` ```` or `~~~`, up to three leading spaces) kept whole — by `SegmentMarkdownBlocks`; `blockIndex` is a position in that segmentation.

A snapshot also carries `lens_id`, `context_spec` (the entity's spec at generation), `resolved_context` (the receipt, `context.md` § 5), `generated_by_model`, `generation_trigger` (empty, or `generate_all` for a wave-produced row), `created_from_refinement_id`, `approval_sequence_number`, `approved_at`, `generated_at`, and `created`/`updated`. Snapshots carry no window columns: every filter that scopes a reflection snapshot to a window (`SnapshotWindowFilter`, `ApplySnapshotWindow`) is a no-op for the projection strategy. Lenses are `lens` rows (`prompt`, `parent_lens_id` lineage, `created_from_projection_refinement_id`); they are created by a commit (§ 3) and by the refinement chat's apply leg (`refinement.md` § 3.1, which stamps an uninstalled lens on the candidate it materialises), and no code path updates or removes one (`refinement.md` § 1). A `projection_refinement` row (`projection_id`, `projection_snapshot_id`, `external_conversation_id`) binds one conversation to one projection and, optionally, one snapshot.

A pending candidate is **engaged** (`CandidateEngaged`) when its `edits` contain any entry of type `manual` or `refinement` (regeneration-typed entries do not count, whatever their status), or when any `projection_refinement` row has `projection_snapshot_id` equal to the candidate. Engagement is reported by the staleness evaluator as `candidate.engaged` (`reconcile.md` § 2), makes the reconcile wave skip the projection (§ 4.2), and makes the generate route refuse to replace the candidate unless told to (§ 4).

`proposed` projections are written only by discover (`discover.md` § 5, `insertProposed`): `status = proposed`, `description` = the proposal's message, `current_context_spec` = the proposal's spec, `created_by_discover_run_id` = the run. A projection becomes `active` at creation through the route (§ 2) or at its first refinement commit (§ 3); nothing moves it back. Staleness evaluates rows matching `status = 'active' && deleted_at = ''` only (`reconcile.md` § 1); an `active` projection with no approved snapshot is a *draft* — reported with an empty verdict (its pending candidate, if any, is still reported), and a dependent that pins it is not blocked by it (`reconcile.md` § 2).

## 2. Creation

`POST /api/projections` binds `CreateProjectionRequest` `{name, description?}`; any other key in the body is ignored. A malformed body → 400 `invalid request body`. The row is created in one transaction with `name` (not validated; empty is accepted), `status = active`, and `description` when its trimmed value is non-empty. Nothing else: no `current_context_spec` (null), no lens, no snapshot, no model override. A save error → 500 `create projection failed`. Response `201 {projectionId}`. Until a refinement is committed the projection cannot generate (§ 4.2: `ErrLensNotReady`).

## 3. Authoring: refinement → commit

**Opening.** `POST /api/projections/{id}/refinements` (`refinement.md` § 2) binds `CreateProjectionRefinementRequest` `{clientId, snapshotId?, contextSpec?}`: empty `{id}` → 400 `missing target id`; malformed body → 400 `invalid request body`; empty `clientId` → 400 `missing clientId`. In one transaction a `projection_refinement` row is created with `external_conversation_id = clientId` and `projection_id = {id}`; the projection is loaded live (§ 6) and a missing or soft-deleted projection fails the transaction → 500 `failed to create refinement`. A non-empty `snapshotId` is stored as `projection_snapshot_id` and the snapshot loaded (missing → 500); its `projection_id` is not compared with `{id}`, and its status is not checked. The session's starting context is the request's `contextSpec` when present, else that snapshot's `context_spec`, else nothing. When there is one, a `system` message (id `ctx-<unix-nanos>`) is persisted with a `context_spec` part and, when resolution succeeds, a `pinned_ids` part holding its resolved ids (`context.md` § 2–3). When the projection has a `current_lens_id` whose lens row loads with a non-empty trimmed `prompt`, a second seeded message follows: an `assistant` message (id `seed-<unix-nanos>`) with a `data-lens_seed` part and an `update_lens` tool-call part carrying that prompt — the session starts from the installed lens rather than from nothing. Response `201 {refinementId, messages}` where `messages` is the seeded messages in that order, or empty.

**A turn.** `POST /api/projections/{id}/refinements/{rid}/chat`: empty `{id}` or `{rid}` → 400 `projection id and refinement id required`; unknown refinement → 404 `projection refinement not found`; the parent is resolved from the refinement's `projection_id` (or, when that column is empty, from its source snapshot's `projection_id`) and must be live and equal to `{id}`, else 400 `refinement does not belong to specified projection` — a soft-deleted parent fails this check. The body is `RefinementChatRequest` (malformed → 400 `invalid chat request body`; an empty `id` is replaced by the refinement's `external_conversation_id`), then the turn streams (`refinement.md` § 3): no messages → 400 `messages required`; no model for the `refinement` role → 500 `no model configured for refinement`; quota exhausted → 402; a provider error → its envelope (`llm-queue-quota.md` § 6); prompt too large → 422; any other error → 500 `llm stream failed`. A turn writes projection rows in two ways, both described mechanically in `refinement.md` § 3 and stated here for their effect on the projection's snapshots:

- **The apply leg** (`MaterializeCandidateIfNew`, after a lens is drafted or a regeneration is requested) previews the drafted lens at the `snapshot` role and then: if the refinement is bound to no snapshot (`projection_snapshot_id` empty), it creates a new `lens` row (`prompt` = the draft, `created_from_projection_refinement_id` = this refinement; **not** installed on the projection) and a `pending_review` snapshot with `output = ""`, `output_draft` and `output_raw` = the previewed text, `edits = []`, `lens_id` = that lens, `context_spec`/`resolved_context` from the transcript, `generated_by_model` = the resolved snapshot model, `created_from_refinement_id` = this refinement, and binds the refinement to it; when the turn also suggested a name and the projection's `name` is empty or starts with `Untitled`, `name` is replaced. No other pending candidate is discarded by this path. If the refinement is bound to a `pending_review` snapshot, that candidate is rewritten in place: the baseline is the draft with every remaining marker replaced by its edit's `contentBefore` (`ResolveDraftBaseline`; a draft that resolves to blank falls back to the newest approved `output`), the new draft and `regeneration` edits are `DiffAndMarkBlocks(baseline, preview)` (§ 4.2; a blank baseline stores the preview verbatim with no edits), every prior edit becomes `superseded` (`undoReason = regenerated`, `undoable = false`) except an `approved` edit whose `inlinedText` still occurs verbatim in the new draft, which is kept and re-anchored to where the passage now sits; new edits are numbered after the highest prior `sequence`; a new lens row is created and stamped as the candidate's `lens_id`; `output_raw` = the preview, `context_spec`, `resolved_context` and `generated_by_model` are refreshed; `output` is untouched; a `data-regenerate_superseded` system notice naming the superseded and kept sequences is persisted. A refinement bound to a snapshot that is not `pending_review` materialises nothing.
- **The `refine_candidate` tool** proposes a passage replacement on the bound candidate (`ProposeRefineEdit`, or `ReviseProposalEdit` when the turn answers a targeting notice for an existing `proposed` edit): the candidate must be `pending_review` under a live parent, the target passage is located as a run of whole blocks (whitespace-normalised) or, failing that, as a whitespace-tolerant substring of one block; a target under an existing marker is refused; the located text is replaced by a marker and a `refinement`/`proposed` edit appended (`contentBefore` = the located text, `contentAfter` = the replacement, `blockIndex` = the block it sits in); a revision marks the old edit `superseded` with `supersededBy` and swaps its marker for the new one. Failures are reported to the model as a tool result (`ok: false`) and to the transcript as a notice, never as an HTTP error. Only refinements with both `projection_id` and `projection_snapshot_id` set can propose.

**Commit.** `POST /api/projections/{id}/refinements/{rid}/commit` (`refinement.md` § 5): empty `{rid}` → 400 `refinement id required`; unknown refinement → 404 `refinement not found`. The transcript is read: no drafted lens → 400 `no drafted lens found in chat`; the parent id resolves as for a turn (column, else source snapshot) and an empty result → 400 `refinement missing parent target id`; a non-empty `{id}` that differs from it → 400 `refinement parent target id mismatch`. The output to commit is the apply output paired with the latest lens in the transcript; when there is none and the refinement is bound to a snapshot, that snapshot's trimmed `output_draft`, else its trimmed `output`; still empty → 409 `the latest lens has no generated preview — send another message to regenerate`. `CommitRefinement` then runs detached from request cancellation, in one transaction:

1. The parent is loaded live; a missing or soft-deleted parent fails the commit → 500 `failed to commit refinement`.
2. A `lens` row is created: `prompt` = the drafted lens, `parent_lens_id` = the previous `current_lens_id` when there was one, `created_from_projection_refinement_id` = this refinement.
3. If the refinement is bound to a snapshot that is still `pending_review`, **that candidate is approved in place**: its `output` becomes its trimmed `output_draft` (else its trimmed `output`, else the committed output); a draft still containing a marker fails the commit (`ErrNotApprovable`: `candidate has unresolved edits`) → 500 `failed to commit refinement`; `lens_id` = the new lens, `context_spec` and `resolved_context` from the transcript; `output_draft`, `output_raw`, `edits`, `generated_by_model`, `generated_at`, `generation_trigger` and `created_from_refinement_id` are left as they were. `ApproveSnapshot` (§ 4.3) then stamps the sequence number and discards every other `pending_review` candidate.
4. Otherwise (no bound snapshot, or a bound snapshot that is `approved`, `discarded`, `generating` or missing) a new snapshot is appended with `output = ""`, `output_draft` and `output_raw` = the committed output, `edits = []`, `lens_id` = the new lens, `context_spec` and `resolved_context` from the transcript, `generated_by_model` = `ResolveRoleFor(snapshot, generate_with_model)` (a resolution error is discarded and leaves it empty), `created_from_refinement_id` = this refinement, `generated_at = now`, status `pending_review`, and immediately approved by `ApproveSnapshot`, which copies the draft into `output`, stamps the sequence and discards every other `pending_review` candidate. The inherited `generation_trigger` this path accepts is read only from a still-pending bound snapshot, which step 3 always takes first, so it is always empty here.
5. The projection's `current_lens_id` and `current_context_spec` are re-pointed and `status` is set to `active`.

No check is made for a `generating` claim: a generation in flight completes later under the lens it started with. After the transaction the reconcile worker's `EnqueueWave` is called — a no-op unless automatic waves are enabled (`reconcile.md` § 4). Response `200 {snapshotId}`.

## 4. Generation and approval

`POST /api/projections/{id}/candidates` and `POST /api/projections/{id}/snapshots` share one handler. Empty `{id}` → 400 `id required`. The body is bound into `GenerateProjectionSnapshotRequest` `{sourceId, chatId, fragmentIds, colourIds, messages, preview, discardEngaged, foldIn}`; a malformed body → 400 `invalid request body`; of its fields only `preview`, `discardEngaged` and `foldIn` are read — the other five are accepted and unused. `preview: true` → the result is `pending_review`; otherwise it is **approved** on completion with no review step. The projection is loaded live (missing or soft-deleted → 404 `projection not found`). The handler then evaluates staleness for the whole graph (`reconcile.md` § 1) and reads this projection's row: `blockedBy` non-empty → 409 `upstream dependencies are not up to date; approve them first`; otherwise the engaged flag is taken from the row's `candidate`. An evaluation error is logged as a warning and generation proceeds, but the engagement check is redone directly (`FindPendingCandidate` + `CandidateEngaged`; a failure of either counts as not engaged); a projection the pass does not cover (`status = proposed`) gets an empty verdict and is never blocked or engaged. An engaged candidate with `discardEngaged` absent or `false` → 409 `cannot replace engaged candidate; discard it first`, with `data: {kind: "candidate_engaged"}` in the error envelope. `foldIn: true` marks the generation context as *settle-unchanged* (`llmcontext.WithSettleUnchanged`), which lets a no-change result settle the approved row in place (§ 4.2 step 7) without the wave's speculative resolution and without stamping `generation_trigger`.

The request then enters the worker manager (`Manager.GenerateProjectionSnapshot`): if no live claim exists for the projection (§ 4.1) a running reconcile wave is cancelled after its current entity (`CancelWave`, `reconcile.md` § 3.2); if a live claim exists the wave is left alone and the request will join it. Generation itself runs on a context detached from request cancellation; only the wait on someone else's run is bounded by the request. Afterwards `EnqueueWave` is called when a wave was cut short, or when the generation succeeded with status `approved` — again a no-op unless automatic waves are enabled. When `foldIn` and `preview` are both `true` and the generation succeeded, `CarryOpenRefinementToCandidate` runs best-effort (a failure is logged and the response unchanged): if the returned snapshot is a `pending_review` row of this projection, the newest `approved` snapshot other than it has a `projection_refinement` bound to it (newest by `created`), and that refinement's transcript has drafted no lens, the refinement's `projection_snapshot_id` is re-pointed to the new candidate — which makes the candidate engaged. A settled-in-place result (not pending), no approved snapshot, no bound refinement, or a lens-drafting refinement carries nothing. Response `200 {snapshotId}`.

### 4.1 Claim, and joining a live claim

`ClaimGeneration`, in one transaction: every existing `generating` row for the projection is inspected — one whose `created` is younger than `GenerationClaimTTL` (10 minutes) → `ErrGenerationInFlight`; older ones are deleted as leftovers of a crashed run. A new row is inserted with `projection_id` and `status = generating`, nothing else. That row is the lock and what the UI shows as generating. If the generation fails after the claim, `releaseClaim` deletes the row provided it is still `generating` and wakes in-process waiters. Boot deletes every leftover `generating` row in both snapshot collections (`SweepGenerationClaims`, `boot-and-workers.md` § 1).

When the interactive request meets `ErrGenerationInFlight` it does not refuse (`GenerateOrJoin`): `JoinGeneration` waits on the request context, capped at the claim TTL, for the live claim to be filled. `AwaitGeneration` takes the newest `generating` row (none → `ErrGenerationAbandoned`), subscribes to the in-process claim hub for that row, and loops: the row is re-read first — gone → `ErrGenerationAbandoned`; `discarded` → `ErrGenerationAbandoned`; any status other than `generating` → returned as the result; still `generating` → wait for the hub to signal a settle, a 500 ms poll tick, or the context ending (its error is returned). On `ErrGenerationAbandoned` the handler starts one fresh generation of its own; a second `ErrGenerationInFlight` from that attempt is returned as-is. A joined result carries whatever status the other generation requested (a wave produces `pending_review`) — this request's `preview` flag does not apply to it. A join that times out or is cancelled surfaces as 500 `generate projection failed`.

### 4.2 Produce

`GenerateSnapshot`, in order:

1. The projection is loaded live (a missing or soft-deleted row → an error whose text contains `not found` → 404). The active lens (`refinement.md` § 6) supplies the prompt: `current_lens_id` is dereferenced and a lens row that does not load yields an empty prompt; the scope is the projection's own `current_context_spec`. An empty (trimmed) prompt → `ErrLensNotReady` (409 `This projection's lens is still being prepared — try again in a moment.`), before any claim.
2. The model is `ResolveRoleFor(snapshot, generate_with_model)` (§ 5); a resolution error → 500. The claim is taken (§ 4.1).
3. The spec is resolved unwindowed and hydrated in full mode as the source block (`context.md` § 2–4). A resolution error, or a spec that resolves to nothing, leaves the source block and the receipt empty silently; a hydration error is ignored and whatever text was rendered is used. This step cannot fail for a projection.
4. `ApplyPrompt(lens, sources)` with zero window bounds, then `CheckPromptFits` (`context.md` § 6; `ErrContextTooLarge` → 422 with the estimate text), then one call at the `snapshot` role on the resolved model through the shared call path (`llm-queue-quota.md` § 1; an interactive request runs at the default priority, a wave at `Background`, `llm-queue-quota.md` § 2.1). Output is trimmed; the trimmed text is the raw candidate.
5. The candidate is compared with the newest approved snapshot (highest `approval_sequence_number`) to choose a mode. The row's `output_raw` is always the raw candidate; the mode decides the text (`output` on approval), the draft and the edit list:

   | Situation | Text | `output_draft` / `edits` |
   |---|---|---|
   | No approved snapshot | The raw candidate (from scratch). | The raw candidate / `[]`. |
   | Newest approved snapshot has a different `lens_id` | The raw candidate (from scratch; logged `lens changed since last approval`). | The raw candidate / `[]`. |
   | Candidate equals the approved output byte-for-byte | The approved text; the generation is *unchanged*. | The approved text / `[]`. |
   | Otherwise | **Minimal-diff rewrite**: two more turns on the same conversation — `SnapshotDeltaPrompt(previous)`, and if the trimmed reply is exactly `NO CHANGES` the previous text verbatim (*unchanged*), else `SnapshotMergePrompt()` whose trimmed result is the text (an empty merge reply is an error). A rewrite failure keeps the raw candidate (logged), except a preemption (`llm-queue-quota.md` § 2.4; the error is returned, the claim released — the wave retries the whole generation, a request reports a generic failure) or a dead context (aborted, nothing persisted). | *Unchanged*: the approved text / `[]`. Otherwise `DiffAndMarkBlocks(approved, text)` — the approved text with each changed run of blocks replaced by a marker / one `regeneration`/`proposed` edit per run (§ 4.2, below). On a rewrite failure the diff is taken against the raw candidate. |

   `DiffAndMarkBlocks(before, after, type)`: equal inputs → `before` and `[]`; a blank `before` → a single marker and one edit with `contentAfter = after`, `blockIndex = 0`; a blank `after` → a single marker and one edit with `contentBefore = before`. Otherwise both are segmented into blocks and diffed (Myers, on whole blocks); each maximal run of non-equal operations becomes one edit — `id` a random 15-character string, `sequence` counted from 1, `status = proposed`, `contentBefore` = the deleted blocks joined by a blank line, `contentAfter` = the inserted blocks likewise, `blockIndex` = the marker's position in the resulting draft, `createdAt` = now (RFC 3339 UTC) — and one marker line in the draft; equal blocks are copied through. Blocks are joined by one blank line.

6. Empty text → error (`model returned empty output`, 500), claim released.
7. **Speculative settle.** If the result is *unchanged* and the context carries a generation trigger (only the reconcile wave sets one — `reconcile.md` § 3.1) **or** the fold-in mark (§ 4, `foldIn: true`), no new row is made: `settleApprovedInPlace` rewrites the current approved snapshot's `context_spec`, `resolved_context`, `generated_by_model` and `generated_at` and discards every `pending_review` row for the projection, in one transaction; the claim row is deleted; the approved row's id is the result. If the newest approved snapshot no longer carries the generating lens, nothing is written and the flow falls through to step 8. An interactive generation without `foldIn` that changed nothing still produces a candidate.
8. `completeClaimedSnapshot`: the claim row is filled in place — `lens_id`, `output_raw`, `context_spec` (the projection's current spec), `resolved_context`, `status` (the requested one), `generated_by_model`, `generation_trigger` (from the context; empty for interactive calls), `created_from_refinement_id` empty, `generated_at = now` — and every **other** `pending_review` row for the projection is set `discarded`, in one transaction; after it commits, waiters on the claim are woken. What lands in the text columns depends on the requested status: `pending_review` → `output = ""`, `output_draft` and `edits` as chosen in step 5; `approved` → `output` and `output_draft` both the step-5 text and `edits = []` — a non-preview generation never persists markers.
9. If the requested status is `approved`, `ApproveSnapshot` runs (§ 4.3) as a separate transaction; a failure there → 500, with the row already reading `approved` but carrying no `approval_sequence_number`.

The three callers and what they ask for:

| Caller | Status requested | Marks on context | Upstream snapshots resolve to (`context.md` § 3) |
|---|---|---|---|
| Route, `preview` absent or `false` | `approved` | settle-unchanged when `foldIn: true` | latest approved |
| Route, `preview: true` | `pending_review` | settle-unchanged when `foldIn: true` | latest approved |
| Reconcile wave | `pending_review` | trigger `generate_all`, priority `Background` | newest row that is neither `generating` nor `discarded` |

The wave calls `GenerateSnapshot` directly and never joins: it skips (logging `candidate is engaged`) a projection whose evaluated `candidate.engaged` is true, skips a projection whose newest snapshot is already current (§ 5), retries on preemption, and skips (logging) on `ErrLensNotReady` or `ErrGenerationInFlight` (`reconcile.md` § 3.1).

Response `200 {snapshotId}`. Error mapping: quota exhausted → 402 (`llm-queue-quota.md` § 5; `quota.Set` has no caller in this binary, so `Authorized` always passes and this branch is unreachable); a provider error → its envelope (`llm-queue-quota.md` § 6); `ErrContextTooLarge` → 422; `ErrLensNotReady` → 409 as above; `ErrGenerationInFlight` → 409 `A generation for this projection is already running.` (reachable only from the fresh generation after an abandoned join); any other error whose text contains `not found` → 404 `projection not found`; else 500 `generate projection failed`.

### 4.3 Approval

`POST /api/projections/{id}/candidates/{rid}/approve`: empty `{id}` → 400 `projection id required`; empty `{rid}` → 400 `candidate id required`; the snapshot must exist (404 `candidate not found`) and its `projection_id` must equal `{id}` (404 `candidate does not belong to this projection`). The projection itself is not loaded: a soft-deleted projection's candidate approves normally, and no in-flight check is made. `ApproveSnapshot`, in one transaction: a snapshot already carrying an `approval_sequence_number` is a no-op (200); `generating` → `candidate cannot be approved: generation still running`; `discarded` → `candidate cannot be approved: candidate was superseded`; when `output` is blank after trimming, the draft is promoted — an `output_draft` still containing `<<<edit:` → `candidate cannot be approved: candidate has unresolved edits`, else `output` = the trimmed draft; `output` still blank → `candidate cannot be approved: candidate has no content` — each as 422 (`ErrNotApprovable`). A candidate whose `output` is already non-blank is approved as is, whatever its draft holds. Otherwise `approval_sequence_number` = highest existing + 1 (1 for the first), `approved_at = now`, `status = approved`, and every other `pending_review` row is set `discarded`. `output_draft`, `output_raw` and `edits` are left as they were. Any other failure → 500 `approve failed`. Then the reconcile worker's `EnqueueWave` (a no-op unless automatic waves are enabled, `reconcile.md` § 4). Response `200 {snapshotId}`.

### 4.4 Hand edit of a pending candidate

`POST /api/projections/{id}/candidates/{rid}/edit`: the candidate is resolved as in § 4.3 before the body is read; then `EditCandidateRequest` `{blockPosition, newText}` is bound (malformed → 400 `invalid request body`; an absent `blockPosition` is `0`). `ApplyEdit` runs detached from request cancellation, projections only, in one transaction:

1. The projection is loaded live (a missing or soft-deleted one → 500 `edit failed`). The candidate must be `pending_review` → else 409 `edit rejected: candidate is not pending review`.
2. The working text is `output_draft`, or `output` when the draft is empty. It is segmented into blocks; `blockPosition` outside `[0, blocks)` → 400 `edit rejected: invalid block position: <n>`; a block containing `<<<edit:` → 409 `edit rejected: cannot edit a block under an unresolved edit marker`; a `newText` identical to the block → 422 `edit rejected: edit changes nothing`. The block is replaced by `newText` and the draft re-joined (blank blocks dropped, one blank line between the rest); an empty `newText` therefore deletes the block. There is no uniqueness or emptiness check on the result: a draft may be edited down to nothing.
3. If fragment creation is enabled, a `fragment` row is created: `type = edit`, `ingested_via = app`, `source` = `edit to projection "<name>" (candidate <rid>)`, `content` = the before/after passages in the edit-fragment format (`prompts.md` § 1), `occurred_at = now`. Its birth hooks fire as for any app-written fragment (`ingestion.md` § 7). The fragment's id is appended (once) to the projection's `current_context_spec.fragmentIds` and the projection saved. The switch is `KALAIDO_HAND_EDIT_CREATE_FRAGMENT` (`KALAIDO_CREATE_EDIT_FRAGMENTS` is read instead when the first is unset; `1/true/yes/on` enable, `0/false/no/off` or empty disable, anything else fails boot), parsed at boot and, when true, recorded on the app store under `kalaido.projections.hand_edit_create_fragment`; a store without the key falls back to re-reading the environment on every edit. Default: disabled — no fragment, and the parent's spec untouched.
4. The candidate is updated in place: `output = ""`, `output_draft` = the new draft; `context_spec.fragmentIds` and the receipt's `fragmentIds` and `expandedIds` gain the fragment id when one was created (rewritten unchanged otherwise); a `manual`/`approved` edit is appended (`sequence` = count + 1, `contentBefore` = the old block, `contentAfter = newText`, `blockIndex = blockPosition`, `fragmentId` when created, `createdAt` = `updatedAt` = now) — it carries no `inlinedText`, anchors or `undoable`, so it can never be undone through § 4.5; then every earlier `approved`/`rejected` undoable edit is re-checked against the new draft (§ 4.5, *recompute*). No model call is made.
5. A `system` message (id `hand-edit-<editId>`) with a `data-hand_edit` part (text: the hand-edit notice, `prompts.md` § 2; data: `editId`, `sequence`, `before`, `after`) is persisted onto the newest `projection_refinement` whose `projection_id` and `projection_snapshot_id` match; none → nothing; a persistence error is ignored.

Response `200 {fragmentId, edit}` where `fragmentId` is empty when disabled and `edit` is the appended entry. Any other failure → 500 `edit failed`.

### 4.5 Edit status updates: triage and undo

`PATCH /api/projections/{id}/candidates/{rid}/edits/{eid}`: the candidate is resolved as in § 4.3; empty `{eid}` → 400 `edit id required`; the body is `UpdateSnapshotEditStatusRequest` `{status}` (malformed → 400 `invalid request body`); a `status` other than `approved`, `rejected` or `proposed` → 400 `invalid snapshot edit status: <status>` (`superseded` cannot be requested). `UpdateSnapshotEditStatus` runs detached from request cancellation, in one transaction: the projection must be live (else 500 `update snapshot edit status failed`) and the candidate `pending_review` (else 409 `edit rejected: candidate is not pending review`); no entry with id `{eid}` in `edits` → 404 `snapshot edit not found: <eid>`. The working text is `output_draft` only (no fallback to `output`).

**Approve or reject** (`status` = `approved` | `rejected`): the entry must be `proposed` (else 409 `snapshot edit is already resolved: <eid>`) and its marker must occur in the draft (else 404 `snapshot edit not found: marker for <eid> not found in draft`). The replacement is `contentAfter` for approve, `contentBefore` for reject. The first block containing the marker is located; when the block is exactly the marker it is replaced whole (an empty replacement drops the block), otherwise the marker is replaced inline once. The entry records `inlinedText` = the replacement, `anchorPrev`/`anchorNext` = the neighbouring blocks before the replacement (or the sentinels `^START^`/`^END^` at the ends), `blockIndex` = the marker block's index, `undoable = true`, `undoReason = ""`, `status`, `updatedAt = now`.

**Undo** (`status` = `proposed`): the entry must be `approved` or `rejected` (else 400 `invalid snapshot edit status: <its status>`) and `undoable` true (else 409 `snapshot edit is not undoable: <undoReason, or "edit is not undoable">`). The marker is put back: when `inlinedText` is non-empty, the run of blocks equal to it nearest to `blockIndex` is replaced by the marker, or, for a single-block text, the nearest block containing it has one occurrence replaced inline; when `inlinedText` is empty (a dropped block), the marker is re-inserted between `anchorPrev` and `anchorNext` at the adjacent pair nearest to `blockIndex` (or at the start/end for a sentinel; a draft that is entirely gone becomes the marker alone). A text or anchor pair no longer found → 409 `snapshot edit is not undoable: …` and the transaction rolls back (the `undoable = false` computed on the way is not persisted). On success the entry's `inlinedText`, anchors, `undoable` and `undoReason` are cleared, `status = proposed`, `updatedAt = now`.

Both paths then *recompute* undoability: every `approved`/`rejected` entry still marked undoable is set `undoable = false`, `undoReason = another edit was made on top` when its `inlinedText` no longer occurs in the draft, or (no `inlinedText`) its anchors are no longer adjacent in the draft; save `output_draft` and `edits` (`output` is not touched); and persist a `system` message (id `triage-edit-<eid>-<status>`) with a `data-edit_triage` part (data: `editId`, `sequence`, `status`) onto the newest refinement bound to the projection and candidate, as in § 4.4 step 5. Response `200 {edit}` with the updated entry. Any other failure → 500 `update snapshot edit status failed`.

## 5. Model resolution

Every snapshot-producing call for a projection resolves `ResolveRoleFor(role, generate_with_model)`: a non-empty override (trimmed) wins verbatim, with no check against any model table; else the workspace's model for the role — the workspace config's model when a provider is configured (an unfilled role is an error), else the static model set (`models.md` § 5). Roles: `snapshot` for generation and its minimal-diff turns (§ 4.2), the commit's provenance stamp (§ 3) and the refinement apply leg (`refinement.md` § 3.1); `refinement` for the refinement chat itself. Per-role generation options come from the registry (`models.md` § 1). The concrete model is stamped on every snapshot as `generated_by_model`. `SnapshotCurrency` compares one snapshot with what a generation would consume now and names the first mismatch: `lens_changed` when its `lens_id` differs from `current_lens_id`; `model_changed` when its non-empty `generated_by_model` differs from the model that would be resolved now (an empty stamp never counts); `context_changed` when the spec's current resolution differs from its receipt in either direction. `SnapshotIsCurrent`, the wave's dedup guard (`reconcile.md` § 3.1), applies it to the newest `pending_review`-or-`approved` snapshot (ordered by `created`, then `approval_sequence_number`, then rowid, all descending); a projection with no such snapshot is non-current. The staleness evaluator applies it to the pending candidate and publishes the verdict as `candidate` `{id, outdated, reason, engaged, newFragmentIds}` on the entity's status, narrowing `context_changed` to `new_fragments` when the drift includes fragments the candidate never saw (`reconcile.md` § 2).

## 6. Deletion and restore

`DELETE /api/projections/{id}` soft-deletes. Empty `{id}` → 400 `id required`. The row is loaded regardless of liveness (missing → 404 `projection not found`); an already-deleted row → 204 with no further effect. If a `generating` claim younger than the claim TTL exists for the projection → 409 `a generation is running for this projection` (an older claim does not count). Otherwise, in one transaction, the projection's id is removed from `sourceProjectionIds` in the `current_context_spec` of every `projection` and `reflection` row whose spec text contains it (rows are matched by a `~` substring filter with no liveness condition; a row whose spec fails to parse is skipped; rows whose list did not contain the id are left unsaved), and `deleted_at = now` is stamped. Any other failure → 500 `delete projection failed`. Response 204.

Nothing else is written: `projection_snapshot`, `projection_refinement`, `chat_message` and `lens` rows stay, and snapshots' frozen `context_spec`/`resolved_context` keep any reference to the deleted id. No route hard-deletes a projection; the cascade on `projection_snapshot.projection_id` and `projection_refinement.projection_id` (`schema.md` § 5) is reachable only outside the HTTP surface. While `deleted_at` is set: `PATCH` and generate → 404; refinement-open, commit, hand edit and edit-status update → 500; a refinement turn → 400; approve is unaffected; staleness and the wave exclude the row (a wave that evaluated it before deletion skips it when it reaches it); discover's `list_existing` and its proposal counts exclude it; and context resolution contributes none of its snapshots to dependents (`context.md` § 3), so a dependent that still pins it simply resolves fewer snapshots.

`POST /api/projections/{id}/restore`: empty `{id}` → 400 `id required`; the row is loaded (missing → 404 `projection not found`) and `deleted_at` is cleared when set; a live row is a no-op. A save error → 500 `restore projection failed`. References scrubbed at delete time are not re-added. Response `200 {id}`.

## 7. Update

`PATCH /api/projections/{id}` binds `UpdateProjectionRequest` `{name?, pinned?, generateWithModel?}` (absent fields are untouched; any other key, `windowSpec` included, is ignored). Empty `{id}` → 400 `id required`; a malformed body → 400 `invalid request body`; the projection is loaded live (missing or soft-deleted → 404 `projection not found`). `name` replaces verbatim (empty accepted); `generateWithModel` is trimmed and stored in `generate_with_model` (`""` clears the override; no validation); `pinned` adds (once) or removes (every occurrence of) the **authenticated** user's id in `pinned_by` — with no authenticated user on the request the field is left unchanged silently. `status`, `description` and `current_context_spec` have no update path here. A save error → 500 `update projection failed`. Response `200 {id}`.
