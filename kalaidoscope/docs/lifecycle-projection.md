## 1. Objects and states

A projection is a `projection` row: `name`, `status` (`proposed` | `active`), `description`, `current_context_spec` (JSON; the scope every generation resolves — owned by the entity, the lens carries no copy), `current_lens_id`, `generate_with_model` (per-entity model override, empty = workspace role default), `pinned_by` (users), `created_by_discover_run_id` (empty = human-created), `deleted_at` (the soft-delete stamp, § 6), and the autodates `created`/`updated`. Its output history is a series of `projection_snapshot` rows. A snapshot has four statuses:

| Status | Meaning |
|---|---|
| `generating` | A claim row: a generation is running (§ 4.1). Not output. |
| `pending_review` | A finished candidate awaiting the user. At most one per projection, except the pair a hand edit leaves (§ 4.4). |
| `approved` | Promoted at some point. Not necessarily current. |
| `discarded` | A superseded candidate. Not output. Never deleted. |

The **current** output is a derivation: the `approved` snapshot with the highest `approval_sequence_number` (unique per projection by the partial index `idx_projection_snapshot_approval_seq`, `WHERE status = 'approved'`). Approval promotes a row in place (same id). A snapshot also carries `lens_id`, `output`, `context_spec` (the entity's spec at generation), `resolved_context` (the receipt, `context.md` § 5), `generated_by_model`, `generation_trigger` (empty, or `generate_all` for a wave-produced row), `created_from_refinement_id`, `approved_at`, `generated_at`, and `created`/`updated`. Snapshots carry no window columns: every filter that scopes a reflection snapshot to a window (`SnapshotWindowFilter`, `ApplySnapshotWindow`) is a no-op for the projection strategy. Lenses are `lens` rows (`prompt`, `parent_lens_id` lineage, `created_from_projection_refinement_id`); they are created only by a commit (§ 3) and no code path updates or removes one (`refinement.md` § 1).

`proposed` projections are written only by discover (`discover.md` § 5, `insertProposed`): `status = proposed`, `description` = the proposal's message, `current_context_spec` = `{colourIds, sourceProjectionIds}`, `created_by_discover_run_id` = the run. A projection becomes `active` at creation through the route (§ 2) or at its first refinement commit (§ 3); nothing moves it back. Staleness evaluates rows matching `status = 'active' && deleted_at = ''` only (`reconcile.md` § 1); an `active` projection with no approved snapshot is a *draft* — reported with an empty verdict, and a dependent that pins it is not blocked by it (`reconcile.md` § 2).

## 2. Creation

`POST /api/projections` binds `CreateProjectionRequest` `{name, description?}`; any other key in the body is ignored. A malformed body → 400 `invalid request body`. The row is created in one transaction with `name` (not validated; empty is accepted), `status = active`, and `description` when its trimmed value is non-empty. Nothing else: no `current_context_spec` (null), no lens, no snapshot, no model override. A save error → 500 `create projection failed`. Response `201 {projectionId}`. Until a refinement is committed the projection cannot generate (§ 4.2: `ErrLensNotReady`).

## 3. Authoring: refinement → commit

**Opening.** `POST /api/projections/{id}/refinements` (`refinement.md` § 2) binds `CreateProjectionRefinementRequest` `{clientId, snapshotId?, contextSpec?}`: empty `{id}` → 400 `missing target id`; malformed body → 400 `invalid request body`; empty `clientId` → 400 `missing clientId`. In one transaction a `projection_refinement` row is created with `external_conversation_id = clientId` and `projection_id = {id}`; the projection is loaded live (§ 6) and a missing or soft-deleted projection fails the transaction → 500 `failed to create refinement`. A non-empty `snapshotId` is stored as `projection_snapshot_id` and the snapshot loaded (missing → 500); its `projection_id` is not compared with `{id}`. The session's starting context is the request's `contextSpec` when present, else that snapshot's `context_spec`, else nothing. When there is one, a `system` message (id `ctx-<unix-nanos>`) is persisted with a `context_spec` part and, when resolution succeeds, a `pinned_ids` part holding its resolved ids (`context.md` § 2–3). Response `201 {refinementId, messages}` where `messages` is that seeded message or empty.

**A turn.** `POST /api/projections/{id}/refinements/{rid}/chat`: empty `{id}` or `{rid}` → 400 `projection id and refinement id required`; unknown refinement → 404 `projection refinement not found`; the parent is resolved from the refinement's `projection_id` (or, when that column is empty, from its source snapshot's `projection_id`) and must be live and equal to `{id}`, else 400 `refinement does not belong to specified projection` — a soft-deleted parent fails this check. The body is `RefinementChatRequest` (malformed → 400 `invalid chat request body`; an empty `id` is replaced by the refinement's `external_conversation_id`), then the turn streams (`refinement.md` § 3): no messages → 400 `messages required`; no model for the `refinement` role → 500 `no model configured for refinement`; quota exhausted → 402; a provider error → its envelope (`llm-queue-quota.md` § 6); prompt too large → 422; any other error → 500 `llm stream failed`. Each turn drafts a lens and previews it against the session's pinned context at the `snapshot` role (`refinement.md` § 3.1).

**Commit.** `POST /api/projections/{id}/refinements/{rid}/commit` (`refinement.md` § 5): empty `{rid}` → 400 `refinement id required`; unknown refinement → 404 `refinement not found`. The transcript is read: no drafted lens → 400 `no drafted lens found in chat`; the latest lens has no preview output → 409 `the latest lens has no generated preview — send another message to regenerate`; the parent id resolves as for a turn (column, else source snapshot) and an empty result → 400 `refinement missing parent target id`; a non-empty `{id}` that differs from it → 400 `refinement parent target id mismatch`. `CommitRefinement` then runs detached from request cancellation, in one transaction:

1. If the session names a source snapshot (`projection_snapshot_id`) and that row is still `pending_review`, its `generation_trigger` is inherited (a chain candidate edited mid-review keeps its mark); an approved, discarded or missing source contributes nothing.
2. The parent is loaded live; a missing or soft-deleted parent fails the commit → 500 `failed to commit refinement`.
3. A `lens` row is created: `prompt` = the drafted lens, `parent_lens_id` = the previous `current_lens_id` when there was one, `created_from_projection_refinement_id` = this refinement.
4. The previewed output is appended **as-is** (no regeneration) as an `approved` snapshot: `lens_id` = the new lens, `context_spec` and `resolved_context` from the transcript, `generated_by_model` = `ResolveRoleFor(snapshot, generate_with_model)` (a resolution error is discarded and leaves it empty), `generation_trigger` from step 1, `created_from_refinement_id` = this refinement, `generated_at = now`. `ApproveSnapshot` (§ 4.3) then stamps the sequence number and discards every other `pending_review` candidate — including the source candidate the session was opened on.
5. The projection's `current_lens_id` and `current_context_spec` are re-pointed and `status` is set to `active`.

No check is made for a `generating` claim: a generation in flight completes later under the lens it started with. After the transaction the reconcile worker's `EnqueueWave` is called — a no-op unless automatic waves are enabled (`reconcile.md` § 4). Response `200 {snapshotId}`.

## 4. Generation and approval

`POST /api/projections/{id}/candidates` and `POST /api/projections/{id}/snapshots` share one handler. Empty `{id}` → 400 `id required`. The body is bound into `GenerateProjectionSnapshotRequest` `{sourceId, chatId, fragmentIds, colourIds, messages, preview}`; a malformed body → 400 `invalid request body`; of its fields only `preview` is read — the other five are accepted and unused. `preview: true` → the result is `pending_review`; otherwise it is **approved** on completion with no review step. The projection is loaded live (missing or soft-deleted → 404 `projection not found`). The handler then evaluates staleness for the whole graph (`reconcile.md` § 1) and reads this projection's row: `blockedBy` non-empty → 409 `upstream dependencies are not up to date; approve them first`; an evaluation error is logged and generation proceeds; a projection the pass does not cover (`status = proposed`) gets an empty verdict and is never blocked.

The request then enters the worker manager (`Manager.GenerateProjectionSnapshot`): if no live claim exists for the projection (§ 4.1) a running reconcile wave is cancelled after its current entity (`CancelWave`, `reconcile.md` § 3); if a live claim exists the wave is left alone and the request will join it. Generation itself runs on a context detached from request cancellation; only the wait on someone else's run is bounded by the request. Afterwards `EnqueueWave` is called when a wave was cut short, or when the generation succeeded with status `approved` — again a no-op unless automatic waves are enabled.

### 4.1 Claim, and joining a live claim

`ClaimGeneration`, in one transaction: every existing `generating` row for the projection is inspected — one whose `created` is younger than `GenerationClaimTTL` (10 minutes) → `ErrGenerationInFlight`; older ones are deleted as leftovers of a crashed run. A new row is inserted with `projection_id` and `status = generating`, nothing else. That row is the lock and what the UI shows as generating. If the generation fails after the claim, `releaseClaim` deletes the row provided it is still `generating` and wakes in-process waiters. Boot deletes every leftover `generating` row in both snapshot collections (`SweepGenerationClaims`, `boot-and-workers.md` § 1).

When the interactive request meets `ErrGenerationInFlight` it does not refuse (`GenerateOrJoin`): `JoinGeneration` waits on the request context, capped at the claim TTL, for the live claim to be filled. `AwaitGeneration` takes the newest `generating` row (none → `ErrGenerationAbandoned`), subscribes to the in-process claim hub for that row, and loops: the row is re-read first — gone → `ErrGenerationAbandoned`; `discarded` → `ErrGenerationAbandoned`; any status other than `generating` → returned as the result; still `generating` → wait for the hub to signal a settle, a 500 ms poll tick, or the context ending (its error is returned). On `ErrGenerationAbandoned` the handler starts one fresh generation of its own; a second `ErrGenerationInFlight` from that attempt is returned as-is. A joined result carries whatever status the other generation requested (a wave produces `pending_review`) — this request's `preview` flag does not apply to it. A join that times out or is cancelled surfaces as 500 `generate projection failed`.

### 4.2 Produce

`GenerateSnapshot`, in order:

1. The projection is loaded live (a missing or soft-deleted row → an error whose text contains `not found` → 404). The active lens (`refinement.md` § 6) supplies the prompt: `current_lens_id` is dereferenced and a lens row that does not load yields an empty prompt; the scope is the projection's own `current_context_spec`. An empty (trimmed) prompt → `ErrLensNotReady` (409 `This projection's lens is still being prepared — try again in a moment.`), before any claim.
2. The model is `ResolveRoleFor(snapshot, generate_with_model)` (§ 5); a resolution error → 500. The claim is taken (§ 4.1).
3. The spec is resolved unwindowed and hydrated in full mode as the source block (`context.md` § 2–4). A resolution error, or a spec that resolves to nothing, leaves the source block and the receipt empty silently; a hydration error is ignored and whatever text was rendered is used. This step cannot fail for a projection.
4. `ApplyPrompt(lens, sources)` with zero window bounds, then `CheckPromptFits` (`context.md` § 6; `ErrContextTooLarge` → 422 with the estimate text), then one call at the `snapshot` role on the resolved model through the shared call path (`llm-queue-quota.md` § 1; an interactive request runs at the default priority, a wave at `Background`, `llm-queue-quota.md` § 2.1). Output is trimmed.
5. The candidate is compared with the newest approved snapshot (highest `approval_sequence_number`) to choose a mode:

   | Situation | What is stored |
   |---|---|
   | No approved snapshot | The raw candidate (from scratch). |
   | Newest approved snapshot has a different `lens_id` | The raw candidate (from scratch; logged `lens changed since last approval`). |
   | Candidate equals the approved output byte-for-byte | The approved text; the generation is *unchanged*. |
   | Otherwise | **Minimal-diff rewrite**: two more turns on the same conversation — `SnapshotDeltaPrompt(previous)`, and if the trimmed reply is exactly `NO CHANGES` the previous text verbatim (*unchanged*), else `SnapshotMergePrompt()` whose trimmed result replaces the candidate (an empty merge reply is an error). A rewrite failure keeps the raw candidate (logged), except a preemption (`llm-queue-quota.md` § 2.4; the error is returned, the claim released — the wave retries the whole generation, a request reports a generic failure) or a dead context (aborted, nothing persisted). |

6. Empty output → error (`model returned empty output`, 500), claim released.
7. **Speculative settle.** If the result is *unchanged* and the context carries a generation trigger (only the reconcile wave sets one — `reconcile.md` § 3.1), no new row is made: `settleApprovedInPlace` rewrites the current approved snapshot's `context_spec`, `resolved_context`, `generated_by_model` and `generated_at` and discards every `pending_review` row for the projection, in one transaction; the claim row is deleted; the approved row's id is the result. If the newest approved snapshot no longer carries the generating lens, nothing is written and the flow falls through to step 8. An interactive generation that changed nothing still produces a candidate.
8. `completeClaimedSnapshot`: the claim row is filled in place — `lens_id`, `output`, `context_spec` (the projection's current spec), `resolved_context`, `status` (the requested one, `approved` or `pending_review`), `generated_by_model`, `generation_trigger` (from the context; empty for interactive calls), `created_from_refinement_id` empty, `generated_at = now` — and every **other** `pending_review` row for the projection is set `discarded`, in one transaction; after it commits, waiters on the claim are woken.
9. If the requested status is `approved`, `ApproveSnapshot` runs (§ 4.3) as a separate transaction; a failure there → 500, with the row already reading `approved` but carrying no `approval_sequence_number`.

The three callers and what they ask for:

| Caller | Status requested | Trigger on context | Upstream snapshots resolve to (`context.md` § 3) |
|---|---|---|---|
| Route, `preview` absent or `false` | `approved` | none | latest approved |
| Route, `preview: true` | `pending_review` | none | latest approved |
| Reconcile wave | `pending_review` | `generate_all` | newest row that is neither `generating` nor `discarded` |

The wave calls `GenerateSnapshot` directly and never joins: it skips a projection whose newest snapshot is already current (§ 5), retries on preemption, and skips (logging) on `ErrLensNotReady` or `ErrGenerationInFlight` (`reconcile.md` § 3.1).

Response `200 {snapshotId}`. Error mapping: quota exhausted → 402 (`llm-queue-quota.md` § 5; `quota.Set` has no caller in this binary, so `Authorized` always passes and this branch is unreachable); a provider error → its envelope (`llm-queue-quota.md` § 6); `ErrContextTooLarge` → 422; `ErrLensNotReady` → 409 as above; `ErrGenerationInFlight` → 409 `A generation for this projection is already running.` (reachable only from the fresh generation after an abandoned join); any other error whose text contains `not found` → 404 `projection not found`; else 500 `generate projection failed`.

### 4.3 Approval

`POST /api/projections/{id}/candidates/{rid}/approve`: empty `{id}` → 400 `projection id required`; empty `{rid}` → 400 `candidate id required`; the snapshot must exist (404 `candidate not found`) and its `projection_id` must equal `{id}` (404 `candidate does not belong to this projection`). The projection itself is not loaded: a soft-deleted projection's candidate approves normally, and no in-flight check is made. `ApproveSnapshot`, in one transaction: a snapshot already carrying an `approval_sequence_number` is a no-op (200); `generating` → `candidate cannot be approved: generation still running`; `discarded` → `candidate cannot be approved: candidate was superseded`; output empty after trimming → `candidate cannot be approved: candidate has no content` — each as 422 (`ErrNotApprovable`). Otherwise `approval_sequence_number` = highest existing + 1 (1 for the first), `approved_at = now`, `status = approved`, and every other `pending_review` row is set `discarded`. Any other failure → 500 `approve failed`. Then the reconcile worker's `EnqueueWave` (a no-op unless automatic waves are enabled, `reconcile.md` § 4). Response `200 {snapshotId}`.

### 4.4 Hand edit of a pending candidate

`POST /api/projections/{id}/candidates/{rid}/edit`: the candidate is resolved as in § 4.3 before the body is read; then `EditCandidateRequest` `{oldText, newText}` is bound (malformed → 400 `invalid request body`); empty `oldText` → 400 `oldText required`. `ApplyEdit` runs detached from request cancellation, projections only, in one transaction:

1. The projection is loaded live (a missing or soft-deleted one → 500 `edit failed`). The candidate must be `pending_review` → else 409 `edit rejected: candidate is not pending review`.
2. `oldText == newText` → `edit changes nothing`; then `oldText` must occur exactly once in the candidate's `output`: zero occurrences → `selected text not found in candidate`; more than one → `selected text occurs more than once in candidate`; a replacement leaving only whitespace → `edit would empty the candidate`. Each → 422 `edit rejected: <text>`. An empty `newText` deletes the passage.
3. A `fragment` row is created: `type = edit`, `ingested_via = app`, `source` = `edit to projection "<name>" (candidate <rid>)`, `content` = the before/after passages in the edit-fragment format (`prompts.md` § 1), `occurred_at = now`. Its birth hooks fire as for any app-written fragment (`ingestion.md` § 7).
4. The fragment's id is appended (once) to the projection's `current_context_spec.fragmentIds`; a spec that fails to parse fails the edit (500).
5. A new `pending_review` snapshot is appended: `output` = the candidate's with the passage replaced; `lens_id` and `generated_by_model` copied from the source; `context_spec` = the source's plus the fragment id; `resolved_context` = the source's with the fragment id added to `fragmentIds` and `expandedIds`; `generation_trigger` and `created_from_refinement_id` empty; `generated_at = now`. No model call is made.

The source candidate stays `pending_review`, so two candidates coexist; approving either (§ 4.3), or completing any generation (§ 4.2 step 8), discards the other. Because the approved snapshot's receipt lacks the new fragment, staleness reports it under `newFragmentIds` until the edited candidate, or a later regeneration, is approved (`reconcile.md` § 2). No in-flight check is made. Response `200 {snapshotId, fragmentId}`. Any other failure → 500 `edit failed`.

## 5. Model resolution

Every snapshot-producing call for a projection resolves `ResolveRoleFor(role, generate_with_model)`: a non-empty override (trimmed) wins verbatim, with no check against any model table; else the workspace's model for the role — the workspace config's model when a provider is configured (an unfilled role is an error), else the static model set (`models.md` § 5). Roles: `snapshot` for generation and its minimal-diff turns (§ 4.2), the commit's provenance stamp (§ 3) and the refinement preview leg (`refinement.md` § 3.1); `refinement` for the refinement chat itself. Per-role generation options come from the registry (`models.md` § 1). The concrete model is stamped on every snapshot as `generated_by_model`. `SnapshotIsCurrent`, the wave's dedup guard (`reconcile.md` § 3.1), reads the newest `pending_review`-or-`approved` snapshot (ordered by `created`, then `approval_sequence_number`, then rowid, all descending) and reports it non-current when its `lens_id` differs from `current_lens_id`, when its non-empty `generated_by_model` differs from the model that would be resolved now, or when the spec's current resolution differs from its receipt; a projection with no such snapshot is non-current.

## 6. Deletion and restore

`DELETE /api/projections/{id}` soft-deletes. Empty `{id}` → 400 `id required`. The row is loaded regardless of liveness (missing → 404 `projection not found`); an already-deleted row → 204 with no further effect. If a `generating` claim younger than the claim TTL exists for the projection → 409 `a generation is running for this projection` (an older claim does not count). Otherwise, in one transaction, the projection's id is removed from `sourceProjectionIds` in the `current_context_spec` of every `projection` and `reflection` row whose spec text contains it (rows are matched by a `~` substring filter with no liveness condition; a row whose spec fails to parse is skipped; rows whose list did not contain the id are left unsaved), and `deleted_at = now` is stamped. Any other failure → 500 `delete projection failed`. Response 204.

Nothing else is written: `projection_snapshot`, `projection_refinement`, `chat_message` and `lens` rows stay, and snapshots' frozen `context_spec`/`resolved_context` keep any reference to the deleted id. No route hard-deletes a projection; the cascade on `projection_snapshot.projection_id` (`schema.md` § 5) is reachable only outside the HTTP surface. While `deleted_at` is set: `PATCH` and generate → 404; refinement-open, commit and edit → 500; a refinement turn → 400; approve is unaffected; staleness and the wave exclude the row (a wave that evaluated it before deletion skips it when it reaches it); discover's `list_existing` and its proposal counts exclude it; and context resolution contributes none of its snapshots to dependents (`context.md` § 3), so a dependent that still pins it simply resolves fewer snapshots.

`POST /api/projections/{id}/restore`: empty `{id}` → 400 `id required`; the row is loaded (missing → 404 `projection not found`) and `deleted_at` is cleared when set; a live row is a no-op. A save error → 500 `restore projection failed`. References scrubbed at delete time are not re-added. Response `200 {id}`.

## 7. Update

`PATCH /api/projections/{id}` binds `UpdateProjectionRequest` `{name?, pinned?, generateWithModel?}` (absent fields are untouched; any other key, `windowSpec` included, is ignored). Empty `{id}` → 400 `id required`; a malformed body → 400 `invalid request body`; the projection is loaded live (missing or soft-deleted → 404 `projection not found`). `name` replaces verbatim (empty accepted); `generateWithModel` is trimmed and stored in `generate_with_model` (`""` clears the override; no validation); `pinned` adds (once) or removes (every occurrence of) the **authenticated** user's id in `pinned_by` — with no authenticated user on the request the field is left unchanged silently. `status`, `description` and `current_context_spec` have no update path here. A save error → 500 `update projection failed`. Response `200 {id}`.
