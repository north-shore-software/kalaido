## 1. The spec

`api.ContextSpec` (wire, lowerCamelCase; every field `omitempty`, so an empty spec serialises as `{}`):

| Field | Meaning |
|---|---|
| `wholeScope` | A `WholeScopeMode` string. Empty: not whole scope — the fragment-level selectors below **are** the fragment context. Non-empty: every live fragment is in scope and the three fragment-level selectors add nothing to the scope but mark which fragments are **pinned** (§ 2, § 4). Named values: `"full"` (`WholeScopeFull`) and `"summaries"` (`WholeScopeSummaries`). Resolution tests only `!= ""`; hydration, the explore prompt choice and the token estimate test only `== "summaries"`. Nothing validates the value — any other non-empty string resolves as whole scope and renders as full. |
| `fragmentIds` | Explicit fragments, by id. A static set: it never grows. |
| `fragmentTypes` | Fragments whose `type` is one of these. |
| `colourIds` | Fragments that are members of any of these colours (§ 2). |
| `sourceProjectionIds` | Upstream projections; each contributes at most one snapshot id (§ 3). Contributes even under whole scope, which never includes snapshots on its own. |
| `sourceReflectionIds` | Upstream reflections; likewise. |

The mode is therefore carried by `wholeScope` itself: `""` (selectors only), `"full"` (whole scope, bodies), `"summaries"` (whole scope, rows for everything not pinned). A spec with every field empty resolves to an empty receipt (§ 2): no fragment query runs and no snapshot query runs.

A spec is stored as JSON in `projection.current_context_spec` / `reflection.current_context_spec`, on every snapshot as `projection_snapshot.context_spec` / `reflection_snapshot.context_spec`, and as a `context_spec` part on system messages of explore and refinement transcripts (`schema.md` § 3). The `lens` collection carries no spec: a generation runs the entity's own `current_context_spec`, read beside the lens prompt by `engine.resolveActiveLens` (`refinement.md` § 6). Writers of the entity spec: the entity routes (`lifecycle-projection.md` § 7, `lifecycle-reflection.md` § 3), refinement commit (`engine.CommitRefinement` sets `current_context_spec` to the committed spec in the same transaction as the lens, `refinement.md` § 5), discover's projection creation (`discover.md` § 5), the projection hand-edit path (which appends the new edit fragment's id to `fragmentIds` on both the entity spec and the new snapshot's spec, `lifecycle-projection.md` § 4.4), and `engine.ScrubContextSpecs`, which is run in the deleting transaction by colour delete (drops the colour from `colourIds`), projection soft delete (drops the id from `sourceProjectionIds`) and reflection soft delete (drops the id from `sourceReflectionIds`): it finds every `projection` and `reflection` row whose `current_context_spec ~ <id>` (a substring match on the JSON text, live and deleted rows alike), applies the scrub, and saves only rows whose combined `colourIds`+`sourceProjectionIds`+`sourceReflectionIds` count changed; a row whose spec fails to unmarshal is skipped (`colours.md` § 6, `lifecycle-projection.md` § 6, `lifecycle-reflection.md` § 8). Snapshot `context_spec` values are never scrubbed.

## 2. Resolving fragments

`ResolveSpecToIDs(ctx, app, spec, window)` returns `PinnedIDs{fragmentIds, snapshotIds, expandedIds}` or an error.

- **Pinned fragments** are always computed first (`resolvePinnedFragments`): a single `fragment` query whose filter is the OR of `id = <each fragmentIds>`, `type = <each fragmentTypes>`, and `id = <each colour member>`, ANDed with `deleted_at = ''` and the window clause (§ 2.1). If all three selector lists are empty (after colour lookup) no query runs and the pinned set is empty. A pinned fragment that has been soft-deleted drops out like any other. A fragment matched by several selectors appears once (one row per fragment). A query error fails the whole resolution (`resolve specific fragments: …`).
- **Whole scope** (`wholeScope != ""`): `fragmentIds` = every `fragment` with `deleted_at = ''` (`schema.NotDeleted()`) plus the window clause, via `sourcedata.FindLiveFragmentIDs` (a query error fails the resolution: `find live fragment IDs: …`); `expandedIds` = the pinned fragments that are also in that set, in pinned order (a pin outside the window, or deleted, is not expanded).
- **Otherwise:** `fragmentIds` = the pinned fragments; `expandedIds` = a copy of the same list (recorded even though full mode ignores it, so a later switch to summaries keeps the pins in full).
- **Colour members** (`FragmentIDsForColours` → `sourcedata.ColourMemberIDs`): colour ids are trimmed and blanks dropped; with none left, no query runs. Otherwise every `colour_fragment` row whose `colour_id` is one of the ids and whose `match_type != 'manual_negative'` (`schema.MatchManualNegative`), deduplicated by `fragment_id` in row order; rows with an empty `fragment_id` are skipped. `manual_negative` rows are exclusions and never contribute; a fragment excluded from colour A but explicitly listed in `fragmentIds` (or matched by type) is still included by the OR. A lookup error is logged (`colour fragment lookup failed`, component `llmcontext`) and yields no colour members — the spec still resolves, as if the colours were empty.
- Order is the database's; nothing sorts the fragment ids.

### 2.1 The window clause

`sourcedata.WindowClause(win)`: a nil `api.Window`, or one with an empty `start` or `end`, contributes nothing. Both bounds are parsed with `types.ParseDateTime`; if either fails to parse or is zero, the clause is again empty (the spec resolves unwindowed, silently). Otherwise: ` && ((occurred_at != '' && occurred_at >= start && occurred_at < end) || (occurred_at = '' && created >= start && created < end))` — half-open `[start, end)`; a fragment without an `occurred_at` is placed by its `created` time. The window's `id` is not read. Windows never restrict snapshot ids.

## 3. Resolving upstream snapshots

For each id in `sourceProjectionIds` (and separately `sourceReflectionIds`) the resolver takes **one** snapshot per upstream entity: one status-filtered query over `projection_snapshot` (`reflection_snapshot`) whose filter is the OR of `projection_id = <id>` (`reflection_id = <id>`) ANDed with `projection_id.deleted_at = ''` (`reflection_id.deleted_at = ''`) — a soft-deleted upstream contributes nothing until restored — ordered as below, then deduplicated by parent id (first row per parent wins). An upstream with no qualifying snapshot contributes nothing (no error, no placeholder). Projection snapshot ids come first, then reflection snapshot ids. Neither list is queried when its selector is empty.

Which snapshot qualifies depends on the **generation trigger** marked on the context (`llmcontext.WithGenerationTrigger`; read back by `GenerationTriggerFromContext`, `""` when unset):

| Context | Filter | Order |
|---|---|---|
| Ordinary (no trigger) | `status = 'approved'` | `-approval_sequence_number` |
| Any non-empty trigger — in practice `TriggerGenerateAll` = `"generate_all"` | `status != 'generating' && status != 'discarded'` — i.e. `pending_review` **or** `approved` | `-created` |

Only the reconcile wave sets the trigger (`runWaveWithWorker`, `reconcile.md` § 3); `engine.applySnapshotSpec` stamps the same value into the snapshot's `generation_trigger` field when a generation under that context is stored, unless the `SnapshotSpec` carries its own trigger (`lifecycle-projection.md` § 4.2). For reflections the qualifying snapshot is not restricted by window: the newest approved (or pending) snapshot across all windows and the windowless series is taken.

Query errors in snapshot resolution are swallowed: the snapshot list is simply shorter and the resolution still succeeds.

## 4. Hydration (rendering to text)

**Flat** (`HydrateIDsToText`, always returns a nil error): fragments first, loaded with `LoadFragmentsByIDs` — `sourcedata.FindFragmentsByIDs` = `FindRecordsByIds("fragment", fragmentIds)` (no query for an empty list; an error yields no fragments, silently; there is no `deleted_at` filter at this stage — liveness was decided at resolution) and rendered by `RenderFragmentRecords` in the order that lookup returns them, each as `prompts.FragmentBlock(type, source, id, content)` — `--- <type> from <source> (ID: <id>) ---` + content + blank line, with `EditFragmentGuidance` inserted between header and body for the `edit` type (`prompts.md` § 1). Then projection snapshots: `sourcedata.FindProjectionSnapshotsByIDs` over the whole `snapshotIds` list (reflection ids simply match nothing), their parents loaded in one `FindRecordsByIds("projection", …)`, each rendered as `ProjectionSnapshotBlock(name, snapshotId, output)` (`--- projection "<name>" (ID: <snapshot id>) ---`); a snapshot whose parent is missing or has a non-zero `deleted_at` is skipped silently. Then reflection snapshots likewise (`ReflectionSnapshotBlock`). All lookup errors are ignored. `expandedIds` plays no part.

Flat hydration is used for:

- the generation source block (`engine.prepareGenerationContext`, `lifecycle-projection.md` § 4.2, `lifecycle-reflection.md` § 5.2): the entity's `current_context_spec` is resolved under the generation's window (nil for projections); a resolution **error** leaves the source block and the receipt empty without failing the generation; an empty resolved set likewise hydrates nothing and records an empty receipt; for reflections (`EnsureFragmentsOnly`) a resolved set containing any snapshot id fails the generation with `prepare context: this context must contain fragments only, but snapshots were provided`;
- the refinement apply leg and window re-apply (`refinement.StreamApplyLeg`, `refinement.md` § 3.1, § 4): the transcript's newest `pinned_ids` (§ 5) hydrated flat whatever the spec's mode, skipped when the receipt is empty;
- outside this package, `RenderFragmentRecords` alone renders example and target fragments for the colour prompt (`colours.md` § 4) and the map reader's `read_fragment` output (`tool-loop.md`).

**Deltas** (`Hydrator`, used for transcripts): `chat.HydrateDeltaHistory` builds one hydrator per prompt assembly from the transcript's **final** receipt and **final** mode (`LatestPinnedAndSpec`, § 5; mode = `wholeScope == "summaries"`), then walks the transcript in order. A system message contributes one `system` model message made of: `WindowNotice(start, end)` (`prompts.md` § 1) when it carries a `window` part with both bounds, followed by the delta for its `pinned_ids` part — `Hydrator.Delta(added, removed)` where `(added, removed)` = `DiffPinnedIDs(previous receipt, this receipt)` (§ 5) and the receipt becomes the new "previous". A system message without a parseable `pinned_ids` part contributes no delta (and does not move the previous receipt); one with neither notice nor text is dropped. A delta error is discarded and the text for that step is empty. Non-system messages go through `Flatten` one at a time (§ 7). Both explore (`explore.PrepareLLMPrompt`, `explore.md` § 3) and refinement (`refinement.StreamTurn`, `refinement.md` § 3) prepend their system prompt after this. How an added fragment renders is decided by that final state, not by the mode in force when it arrived:

| Added fragment is… | Rendered as |
|---|---|
| not in the final `fragmentIds` | omitted; counted into `OmittedAddedNotice(n)` |
| already rendered earlier in this transcript (left and came back) | not re-rendered; counted into `RestoredNotice(n)`; marked shown again |
| in the final set, and (final mode is not summaries **or** the id is in the final `expandedIds`) | its full `FragmentBlock` under `AddedNotice` |
| in the final set, otherwise (summaries mode, not pinned) | one summaries row under `SummariesAddedNotice` |

Added snapshots always render in full under `AddedNotice` (through `hydrateFlat`, so the same parent-liveness skip applies). A removed fragment is listed as `- Fragment ID: <id>` under `RemovedNotice` only if it is currently shown to the model (and is then un-shown); removed fragments never shown are counted into `OmittedRemovedLine(n)` (`- <n> documents not shown above`) under the same notice; removed snapshots are always listed as `- Snapshot ID: <id>`. Removed items are never re-rendered, only named. The order within one delta is: added notice + blocks, summaries notice + rows, restored notice, omitted-added notice, removed notice + lines + one blank line.

**Summaries rows** (`hydrateSummaries`): every `fragment_annotation` row is loaded in one pass (`sourcedata.LoadAnnotationRows`: all rows ordered by `created`, each joined to its fragment's `occurred_at` day via `sourcedata.FragmentDates` over live fragments, then stably sorted by that date string; `map.md` § 4) and matched to the added ids in Go; a row-load failure fails that delta with an error, which `HydrateDeltaHistory` discards — the delta text is simply empty for that step. The map document is loaded (`sourcedata.LoadMapDocument`) for thing names; a failure leaves the name table empty, silently. The fragments themselves are loaded by id and insertion-sorted by event time (`occurred_at`, else `created`, compared as `types.DateTime` strings):

- an annotated fragment → `SummaryRowLine`: `- <date> · <title> · <summary, trimmed> (ID: <fragment id>)`, followed by ` [things: <cite>; …]` when the row cites things — a citation with a `ref` renders as `<map name> (<ref>)` when the ref is a thing id in the current map, else the bare ref; a citation with only a `name` renders that name. The row's date is the fragment's `occurred_at` day as `LoadAnnotationRows` recorded it; a row without one prints `undated`;
- an unannotated fragment → `SummaryStubLine`: `- <date> · <type> from <source> · "<snippet>" (ID: <id>; not yet annotated)`, where the date is the `occurred_at` day, else the `created` day, else `undated`, and the snippet (`SummarySnippet`) is the content with whitespace runs collapsed to single spaces, cut to `SummarySnippetChars` = 200 runes with `…` appended when longer.

The block ends with one blank line.

`HydrateDeltaToText(added, removed, summaries)` is the single-shot form — a hydrator whose final context is `added` — used by the token estimate's spec form (§ 6).

## 5. The receipt: `PinnedIDs`

`PinnedIDs{fragmentIds, snapshotIds, expandedIds}` (all `omitempty`; an empty receipt serialises as `{}`). It is persisted in two places:

- On every snapshot as `resolved_context`, always beside `context_spec`, by `engine.applySnapshotSpec` — when a claimed generation completes (`completeClaimedSnapshot`), when refinement commit appends a projection's approved snapshot (`projections.Strategy.CommitRefinementSnapshot`; the reflection strategy's commit writes no snapshot, `refinement.md` § 5), and when a projection hand edit appends its pending snapshot (the edit copies the source snapshot's receipt and adds the new fragment id to both `fragmentIds` and `expandedIds`, `lifecycle-projection.md` § 4.4) — and by `engine.settleApprovedInPlace`, which rewrites `context_spec` and `resolved_context` on the standing approved snapshot (same window, same `lens_id`) when a wave regeneration reproduces its output (`lifecycle-projection.md` § 4.2). `expandedIds` rides along because the whole struct is serialised; no reader diffs it, and the hand-edit path is the only one that carries it forward. Readers: the staleness evaluator (`reconcile.md` § 2), the wave's `engine.SnapshotIsCurrent` check, the hand-edit path, and refinement session opening, which seeds a refinement transcript from the source snapshot's `context_spec` (not its receipt: the spec is re-resolved, below).
- On explore and refinement transcripts as a `pinned_ids` system-message part. `chat.ResolveContextSpecs(history, newMsgs)` starts from the spec and window in effect at the end of `history` (`LatestPinnedAndSpec`) and walks the new messages in order, system messages only: a `context_spec` part that unmarshals replaces the spec; a `window` part that unmarshals sets the window when both bounds are non-empty and clears it otherwise; a message that changed either is resolved under the accumulated pair and, on success, gains a `pinned_ids` part carrying the result. A resolution error leaves the message without a receipt, silently, and the message is persisted that way — the hydrator then emits no delta for it. Parts that fail to unmarshal are ignored. Callers: the explore turn before persisting the new messages (`explore.md` § 2) and the token estimate's conversation form on an unpersisted message (§ 6). The refinement-create handler seeds the same parts directly when it seeds a spec: `context_spec`, then (reflections only) `window`, then `pinned_ids` from `ResolveSpecToIDs` under that window — nil for projections, the request window or the default refinement window for reflections — skipped silently on error (`refinement.md` § 2).

`LatestPinnedAndSpec(msgs)` reads a transcript's current state: scanning newest to oldest over system messages, it takes independently the newest `pinned_ids`, `context_spec` and `window` part that unmarshals (a part that fails to parse is skipped and the scan continues to older ones), stopping once all three are found. A `window` part with an empty bound counts as found and yields a nil window. Absent parts yield an empty receipt, an empty spec, and a nil window. Readers: `HydrateDeltaHistory` and `ResolveContextSpecs` (above), `explore.ConversationSummaries` (the mode test, `explore.md` § 3), the refinement drafting turn and window re-apply (receipt and window for the apply leg, `refinement.md` § 3.1, § 4), and `refinement.ExtractDraftedLensAndSpec` (receipt, spec and window handed to commit, `refinement.md` § 5).

**Diffs.** `PinnedIDs.Diff(other)` = ids in the receiver not in `other` (one-directional; used by staleness: `current.Diff(recorded)`, where a windowed reflection considers only `fragmentIds` and the windowless verdict considers both lists — `reconcile.md` § 2, § 2.1). `DiffPinnedIDs(old, new)` returns both `added` (new − old) and `removed` (old − new), each in its source order (used by transcript hydration and by `SnapshotIsCurrent`, which resolves the entity's spec with a nil window and treats the newest pending-or-approved snapshot as current only when both are empty — `reconcile.md` § 3.1). Both compare `fragmentIds` and `snapshotIds` as opaque strings and **ignore `expandedIds`**; `IsEmpty` likewise ignores it.

Discover's `list_existing` also resolves every live projection's and reflection's `current_context_spec` with a nil window, ignoring errors, and reports only the receipt's `fragmentIds` (`discover.md` § 3.1).

## 6. Prompt-size guard

`llm.EstimateTokens(chars)` = `chars / 4` (bytes, integer division). `llm.PromptBudget(model)` = `window − window/8`, where `window` = `llm.SelectedProvider(model).ContextWindow()`; `0` when the provider reports `≤ 0`. `llm.CheckPromptFits(model, chars)`: a provider reporting `≤ 0` is never checked (returns nil); otherwise refuses when the estimate exceeds the budget with `&ContextTooLargeError{Model, Estimated, Limit}` — `Limit` is the **full window**, not the budget — whose message is `the context is about <n> tokens but <model> accepts about <m> — narrow the window or the context` (numbers as `%.1fM` from 1,000,000, `<n>k` from 1,000, else plain) and which unwraps to `ErrContextTooLarge` (`context too large for the model`). `llm.MessagesChars(msgs)` sums the byte length of every message's `Content`.

`ContextWindow()` is a constant per provider (`models.md` § 6): Gemini 1,000,000; Ollama 256,000 (the live `num_ctx` probe is not used here); the error provider returned for an unconfigured model reports 0, so such a prompt is unchecked and fails at the call instead.

The seven `CheckPromptFits` call sites, with what each does on refusal, followed by the two token-estimate forms, which reuse `EstimateTokens` and `PromptBudget` but never call the guard:

| Site | Measured text | On `ContextTooLargeError` |
|---|---|---|
| Explore turn (`explore.StreamTurn`) | the hydrated transcript incl. system prompt | logged; wrapped in `explore.PromptTooLargeError` whose text is the message plus, when the mode is not summaries, the hint ` Switch the scope to "Summaries" in the context bar to chat over it through summaries instead.`; the handler answers `422` with that text (`explore.md` § 4) |
| Summaries-mode tool rounds (`explore.StreamSummariesTurn`, the loop's `PromptGuard`) | the transcript plus each round's echo and results | logged; an SSE `error` event with the message; the loop stops (`explore.md` § 5) |
| Refinement turn (`refinement.StreamTurn`) | the hydrated transcript incl. system prompt | logged; `422` with the message from the handler (`refinement.md` § 3) |
| Refinement name-only continuation (`StreamNameOnlyContinuation`) | the transcript plus the echo and `NameRecordedContinue` line | logged; no continuation text (`refinement.md` § 3) |
| Apply leg (`refinement.ApplyDraftLens`) | the assembled apply prompt | `apply lens: …`; the leg emits a `refine_error` part/event with `kind: "context_too_large"` and the message (`refinement.md` § 3.1) |
| Snapshot generation (`engine.GenerateOutput`) | the assembled apply prompt | the generation fails (`generate standard: …`); the interactive generate routes map it to `422` through `WriteGenerateError` → `WriteLLMError` (`lifecycle-projection.md` § 4.2, `lifecycle-reflection.md` § 5.2); in the wave the error is returned and ends the wave (`reconcile.md` § 3.1) |
| Explore brief (`explore.GenerateBrief`) | the brief system prompt plus the transcript lines | `422` from the brief route through `WriteLLMError` (`explore.md` § 8) |
| Token estimate, spec form (`POST /api/llm/count-tokens`) | see below | reports `limit` and `fits`, never refuses |
| Token estimate, conversation form | see below | likewise |

`handlers.WriteLLMError` checks quota exhaustion, then provider errors, then `ContextTooLargeError` / `ErrContextTooLarge` → `422` with the error's message.

The same `chars / 4` estimate backs `POST /api/llm/count-tokens` (`api.md` § 3). The bound body is `api.TokenResolutionRequest`: the six spec fields inline plus `window` and `conversationId`; a window with a missing bound is dropped before either form. **Spec form** (no `conversationId`, `HandleResolveTokens`): each selector is resolved and rendered on its own with `explore.CountTokensForSpec` — `ResolveSpecToIDs` then `HydrateDeltaToText` as a fresh context, summaries rows only when that one-selector spec's `wholeScope == "summaries"`; a resolution error counts as 0. `WholeScope` is counted once when set (as rows under summaries, since the one-field spec has no pins); fragment-level pins (`Fragment:<id>`, `Type:<t>`, `Colour:<id>`) are counted only when `wholeScope` is empty or `"summaries"`, and always in full (their one-selector specs have no `wholeScope`); snapshot pins (`Projection:<id>`, `Reflection:<id>`) always. `totalTokens` is the sum; `model` and `limit` = the chat role's **default** model (`ResolveRoleFor(RoleChat, "")`) and its `PromptBudget` (both zero-valued when resolution fails), `fits` = `limit ≤ 0 || totalTokens ≤ limit`. **Conversation form** (`explore.EstimatePrompt`): the persisted transcript of the `chat_conversation` whose `external_conversation_id` matches (or none, for a conversation that has not sent yet) plus one unpersisted system message (`id` `estimate-spec`) carrying the request's spec fields as a `context_spec` part and, when a window was sent, a `window` part, resolved as a turn would be (`ResolveContextSpecs`, § 5), is assembled with `explore.PrepareLLMPrompt`; message 0 is counted as `System`, other system messages as `Context`, the rest as `Transcript`; `model` and `limit` come from the conversation's `generate_with_model` override resolved against the chat role (the default when the conversation does not exist), so this form does honour the override; an estimate error (message load failure) → `500 estimate failed`.

## 7. Mentions and flattening

`Flatten(uiMessages)` turns a persisted UI transcript into model messages, one UI message at a time (its only caller is `HydrateDeltaHistory`, which feeds it non-system messages singly):

- a message carrying a `data-window_reapply` part (`WindowReapplyPartType`) is dropped entirely (`refinement.md` § 4);
- `text` parts are appended after `ExpandMentions`;
- `tool-read_fragment` / `tool-read_thing` parts (the two names in `prompts.ReadFragmentToolName` / `ReadThingToolName`) whose data has a non-empty `output` are collected (tool name from `toolName`, else the part type without `tool-`); at the next `text` part or the end of the message the pending reads flush as **two** messages — one in the UI message's role holding the text so far plus `\n\n[You called: <names>]` (`DiscoverEchoToolCalls`), and a `user` message holding the outputs joined by a blank line — and the text buffer restarts (`explore.md` § 5). A read part without `output` (an interrupted call) is invisible;
- a `tool-update_lens` part with a non-empty `input.lens` is echoed as `[You called <toolName>, setting the lens to:]\n<lens>` (`LensEcho`), separated from preceding text by a blank line — the **only** tool part echoed;
- every other part type (`tool-apply_result`, `tool-suggest_name`, `data-*`, unknown tools) is invisible to the model.

A message that yields no text and no reads produces nothing.

`ExpandMentions` rewrites the client's wire token `@[Kind:id|Label]` (Kind ∈ Fragment, Projection, Reflection, Colour, Type; id 1–32 chars of `[A-Za-z0-9_-]`; label 0–80 chars without `]`, CR or LF; an empty label falls back to the id) into the prompt forms in `prompts.md` § 1: `@"<label>" (Fragment ID: <id>)`, `@"<label>" (Projection: <id>)`, `@"<label>" (Reflection: <id>)`, `@"<label>" (Colour — its tagged fragments are in the context)`, and for Type `@"<id>" (fragment type — those fragments are in the context)` (the label is not used). Anything not matching passes through as literal text. The raw token is what persists; expansion happens only at prompt assembly, and only through `Flatten`. Mentions do **not** change resolution — the client is expected to have added the item to the spec.

`StripMentions` rewrites the same token to `@<label>` (label falling back to the id) for text kept as content rather than sent to the model: `explore.MessageText` applies it to user turns, so the bookmark-save path and the brief's transcript lines carry labels, not tokens (`explore.md` § 7, § 8).
