## 1. The run

A run cut short by shutdown (context cancelled before or during a model call) ends `error` this way; a process death mid-run leaves a `running` row with partial `outputs`, and nothing at boot or later resumes, sweeps or finishes it (§ 8 reports it as interrupted). ## 2. Kick, worker, guards, and order

**Kick.** `POST /api/discover` (`handlers.HandleDiscoverKick`) binds `api.StartDiscoverRequest` `{kind}`: a body that fails to bind → `400 invalid request body`; a `kind` not among `discover.Kinds()` (the `flows` map's keys, in Go map order) → `400 unknown discover kind`; else `Signal(kind)` and `202` with no body. The signal is asynchronous: the response says nothing about whether the run will pass its guards. `Signal` itself silently ignores an unknown kind (the handler is the only caller that checks first). The post-import pipeline (`ingest.startPipeline`, run when the batch was ingested with organise-after; `ingestion.md` § 8) registers a `mapping.AfterDrain` callback that, only when the map drain ended without error, signals `colours`, `projections`, `reflections` in that order, then signals the map. No hook, interval, settle callback or boot kick signals discover; `workers.Manager.BootKicks` does not touch it.

**Worker.** `workers.New` builds one `discover.Worker` over the mapping worker (`discover.NewWorker(app, maps)`) and starts it as one of the four services (`boot-and-workers.md` § 2). `Signal` marks the kind in a pending set and notifies a 1-slot coalescing `workerutil.Signal` (a second notify while the token is unconsumed is dropped, which loses nothing: the pending set is what the loop reads). Each wake: detach the `AfterDrain` follow-ups registered so far (`Worker.AfterDrain` exists; no caller in the binary registers one), take **every** pending kind at once in the fixed `kindOrder` **colours → projections → reflections** (so the later flows can scope by colours the first one just created) and clear the set, then run each in turn; if the worker's context is cancelled between kinds the remaining taken kinds are dropped and are not re-marked pending. While a kind runs, `Running()` returns it and `CurrentStarted()` the wall-clock start; `Pending()` lists the kinds still marked, in kind order (all three read by § 8). A kind signalled during a run — the running kind included — is picked up on the next wake. A failed run is logged (`flow run failed`, kind, error) and the next kind still runs; the detached follow-ups receive the last error of the pass.

**`run(flow)`.** In order: `llm.ResolveRole(RoleMap)`; set `WaitingOnMap()` true and call `mapping.WaitSettled()`, which blocks while a consolidation holds the consolidate mutex (`map.md` § 3.3) — it does not wait for annotation to drain nor for the settle hooks that run after integration (thing rematch, `colours.md` § 3); clear the flag; build the run **context** (§ 3.3–3.4) — a `mapreader.Reader` with a 12-read budget over a snapshot of the things document, its version and every `fragment_annotation` row, plus every colour's membership indexed against those rows. Then the guards, each ending the run **before any row exists**: no things on the map → `discover: the map is empty`; for `projections` and `reflections` only (`scopesByColour`), no colour row at all → `discover: no colours exist yet`. A failure in role resolution or context loading ends the run the same way, logged only. Then the run row is created, the loop executes under `queue.Background` priority (`llm-queue-quota.md` § 2.1), and `finishRun` closes the row (§ 1).

## 3. The tool loop

Discover binds the shared `agent.Runner` (`tool-loop.md` § 2) with `MaxRounds = 30`, a `Generate`, a `Dispatch` and an `OnRoundEnd`; it sets no `StopBeforeLastDispatch`, no `PromptGuard` and no `OnToolDispatched`. The transcript opens with the flow's system prompt and one user turn: the flow's initial block (§ 4–6), then `What already exists:` + § 3.1, then `Coverage now:` + § 3.2 in the flow's measure. The flow's `Existing` list is computed first; a database error there ends the run as `error` before any model call (the run row already exists). The advertised tools are the five shared ones in this order — `read_thing`, `read_fragment`, `list_existing`, `coverage`, `finish` — followed by `flow.Tools`. `read_colour` is bound in the dispatch registry for **every** flow but advertised only by projections and reflections.

**`Generate`.** One `usage.GenerateWithToolCalls` at `RoleMap` with the resolved model and the advertised tools, wrapped in `usage.RetryThrottled` (`llm-queue-quota.md` § 4): a call the scheduler preempted is re-entered at once without limit; a `ProviderError` of kind quota or transient is retried with exponential back-off (2 s initial, 1 min cap, 3 min total); any other error ends the run as `error`, and a cancelled context is checked before every attempt and ends it the same way. `rounds` counts only calls that returned. The reply text is kept as `lastReply` for `finish`.

**`Dispatch`.** The registry handles the six bound tools; any other name falls through to the flow's `Dispatch` (§ 4–6), which answers `Rejected: no tool named "…"` for a name it does not own. A flow `Dispatch` that returns a Go error (collection lookup, save, rematch, member read) ends the run as `error` at once — later calls in the same round are not dispatched, and rows already written stay (and are in `outputs`, § 1). A returned `Output` is appended to `outputs`; a rejection (`Rejected: <reason>`) appends nothing and the run continues. `OnRoundEnd` saves progress (§ 1).

The loop's stop rules (`tool-loop.md` § 2.3) as discover experiences them: a round with no tool calls ends the run `done` with no `summary`; `finish` ends it after its round; after the 30th round any calls it made are still dispatched and saved but their results are never sent, and the run ends `done` (with a `summary` only if that round called `finish`). When `finish` shares a round with other calls, every call in the round is executed in order and all results are discarded. Each assistant turn is echoed into the transcript as the reply text plus `[You called: a, b]`; tool results go back as one user turn.

### 3.1 `list_existing`

`existingEntities`: every `colour` (created order; description `prompt: <prompt>; built on <thing names>` with either half omitted when empty, `thing_ids` that do not resolve on the run's document dropped; fragments = every `colour_fragment` link except `manual_negative`, deduplicated), then every live `projection` and `reflection` (`deleted_at = ''`, created order, any status; description = the row's `description`; fragments = its `current_context_spec` resolved now with no window (`context.md` § 2), an unreadable spec or a resolution error counted as zero). A row with `status = proposed` carries the note `proposed by this run` when its `created_by_discover_run_id` is this run, else `proposed by an earlier run, not yet opened`. Each line is `- <kind> "<name>" (<id>) [<note>]: <description> — <n> fragments` (note and description omitted when empty); nothing at all → `Nothing exists yet.` Counts are live at call time, so colours and proposals made earlier in the run appear.

### 3.2 `coverage`

Two measures, chosen by flow. Both report `<hit> of <total> annotated fragments (<pct>%)` (integer percent; 0 when there are no rows) over the run's rows and up to 10 gaps (`coverageThingList`), sorted by uncovered count descending with an unstable sort (ties in no defined order).

- **Colours flow** (`coverage`): covered = the fragment ids of every entity in the latest existing list (colours included) ∪ every id this run marked covered; the line ends `sit inside an existing or proposed scope.` Gaps are **things** with at least one uncovered citing row (a thing id in the index but missing from the document is skipped): `Least covered things:` then `<id> · <name> · <u> of <n> fragments uncovered`.
- **Projections and reflections flows** (`colourCoverage`): covered = the fragment ids of existing **projections and reflections only** ∪ this run's covered set — a colour is what gets covered, not a cover; the line ends `sit inside an existing or proposed projection or reflection.` Gaps are **colours** from the run's index with at least one uncovered annotated member: `Colours least covered:` then the same line shape, `n` = the colour's annotated members.

The run's covered set grows only through the flow tools (§ 4–6); reads never mark anything covered.

### 3.3 The reader (`read_thing`, `read_fragment`)

Discover constructs the shared map reader with `mapreader.New(app, 12)` (`tool-loop.md` § 7) and embeds it in the run context, so the run holds for its whole life one things document with its version (an empty document at version 0 when no map row exists), every `fragment_annotation` row **sorted by date ascending** (stable, so undated rows come first and created order breaks ties), and the thing → row-index map (`sourcedata.IndexRows`: each citation resolved by `ref`, else by `name`, deduplicated per row; unresolvable citations dropped). A row's `Date` is the fragment's `occurred_at` as `YYYY-MM-DD`, looked up over live fragments only: an annotation row whose fragment has been soft-deleted stays in the set, undated. A thing ref resolves by exact id, else by normalised name or alias (`mapdoc.Document.Resolve`).

A thing card (`tool-loop.md` § 7.3): `id · name · kind[ · aka aliases]`, the blurb, `<n> fragments[, first_seen to last_seen]` (n = citing rows; the span from the document), `Relationships:` in both directions as `From (id) kind To (id)` (only where both ends resolve), then either `No annotated fragments cite it.` or a `Timeline:` month histogram (`YYYY-MM: count`, `undated` for rows without a date) and `Fragments (k of n, spread over time):` — up to 30 rows sampled evenly across the citing set as `date · title · summary (fragmentId)`. An unknown ref → `No thing matches "…".` The exhaustion wording and the 12-per-run budget are discover's (`tool-loop.md` § 7.4); the same reader serves the explore summaries mode under its own construction (`explore.md` § 5).

### 3.4 Colours in the run context

At run start every colour is loaded in created order with: its `thing_ids` resolved through the document (unresolvable refs dropped; ids and names of the rest kept), `Members` = the colour's membership (every `colour_fragment` link except `manual_negative`), `RowIdx` = the members that have an annotation row (sorted row indexes), and the first/last dated row among them. `ByColour` maps colour id → `RowIdx`. A colour ref resolves by id, else by case-insensitive exact name; blank refs resolve to nothing. A **ubiquitous colour** is one whose annotated members exceed 40 % of all rows when there are at least 20 rows (§ 6.3).

The colours block on the initial turn is `Colours (id · name · built on · fragments · span):` with one line per colour, `<id> · <name>[ · built on a, b] · <members> fragments[ · first to last]` (`(no colours yet)` is unreachable: the flows that render the block cannot start without a colour). A colour card (`read_colour`) is that line, then `None of its fragments is annotated yet.` when `RowIdx` is empty, else a month `Timeline:` of the annotated members and `Fragments (k of n, spread over time):` — up to 30 evenly sampled annotated rows. An unknown ref → `no colour with id "…"`. This index is built once per run: a colour created by the same run is visible to `list_existing` (database) but not to `read_colour`, the colours block, ubiquity, cover lines or `colourCoverage`.

## 4. The colours flow (creates)

Tool `create_colour {name, thingIds}` (both required). Initial turn: `What the workspace is about:` + the narrative (or `(no narrative yet)`), `Things, heaviest first (id · name · kind · fragments · span · what it is):` listing every thing whose document `fragments` count is ≥ 5 (`worklistFloor`) heaviest first (stable, so document order breaks ties), one line `<id> · <name> · <kind> · <fragments> · <span or ->· <blurb>` (else `(nothing on the map reaches the floor yet)`), `Relationships:` (only when the document has any, only lines with both ends resolvable), guidance. Its coverage measure is § 3.2's thing measure.

Rejections, in order: unreadable arguments (`the arguments could not be read`); blank name (`name is required`); empty `thingIds` (`give at least one thing id`); then per ref in order, an unresolvable one — a blank entry included — (`No thing matches "…".`) or a **ubiquitous** thing (§ 6.3). Refs are canonicalised to ids and deduplicated. Then a `colour` row is saved with `name`, `swatch` = current colour count mod 8 (`colour.NextSwatch`, `colours.md` § 1.1), `thing_ids` (JSON array of ids), `created_by_discover_run_id` — **no prompt, no description** — followed by `colour.RematchThingsFor` so `colour_fragment` rows exist immediately (computed from a fresh map index, not the run's snapshot; `colours.md` § 3); its membership is read back and marked covered; `outputs` gets `{kind: colour, id, name}`; the result is `Created colour "<name>" (id: …, <n> members).` A failure in the collection lookup, swatch count, save, rematch or member read ends the run as `error` (§ 3). Colours are real rows the moment they are saved; nothing is proposed and no later step revisits them.

## 5. The projections flow (proposes)

Tools `read_colour {ids}` and `propose_projection {name, message, colourIds?, sourceProjectionIds?}` (only `name` and `message` are declared required). Initial turn: the narrative, the colours block (§ 3.4), `Relationships:` (when any), guidance — no things list. Coverage is § 3.2's colour measure.

Rejections, in order: unreadable arguments; blank name or message (`name and message are both required`); a colour ref that resolves to nothing (blank entries skipped; `no colour with id "…"`); a ubiquitous colour; a `sourceProjectionIds` entry (trimmed, blanks dropped, deduplicated) that is not a live `projection` row — missing or soft-deleted alike, any status otherwise → `no projection with id "…"` (rows proposed earlier in this run qualify); neither colours nor sources (`give at least one of colourIds or sourceProjectionIds`). Then `insertProposed` saves a `projection` with `name`, `status = proposed`, `description = message`, `current_context_spec = {colourIds, sourceProjectionIds}` (each key omitted when empty), `created_by_discover_run_id`; no fragments are pinned, no lens, no snapshot, no refinement. The union of the colours' members from the run's index is marked covered; `outputs` gets `{kind: projection, id, name, status: proposed}`; the result `Proposed projection "<name>" (id: …, <n> fragments in scope).` counts only the colours' members (sources contribute nothing to `n`).

## 6. The reflections flow (proposes)

Tools `read_colour {ids}`, `rhythms {grain, thingIds?}` (`grain` required, enum `week`|`month`) and `propose_reflection {name, message, thingIds, colourIds, cadence, startTime}` (all six declared required; `cadence` enum `daily`|`weekly`|`monthly`|`quarterly`). Initial turn: the narrative, the colours block, the month-grain rhythms block over every thing (§ 6.2), guidance — no relationships. Coverage is § 3.2's colour measure.

`rhythms`: unreadable arguments → rejection; with `thingIds`, every non-blank ref must resolve (first failure → `No thing matches "…".`) and both lists are restricted to those things; `grain` is trimmed and lower-cased, and anything other than `week` is treated as `month`.

### 6.1 Proposal

Checks, in order, each a rejection: unreadable arguments; blank name/message; the schedule (`reflections.BuildReflectionSpec`): `cadence` (trimmed, case-insensitive) not one of the four → `cadence "…" is not one of daily, weekly, monthly, quarterly`; `startTime` (trimmed) not parseable as `YYYY-MM-DD`, RFC3339 or `YYYY-MM` (the parsed calendar day is taken at midnight UTC; `YYYY-MM` gives the 1st) → `startTime "…" is not a date; use YYYY-MM-DD`; a start after now → `startTime <date> is in the future; the start is when the rhythm began`; whole periods from start to now exceeding 1000 (`reflections.MaxGridWindows`) → `that start and cadence give <n> periods, more than the 1000 a series can hold; choose a coarser cadence or a later start`. Then the evidence and scope: an unresolvable thing; no things (`give the rhythm's things as thingIds`); a ubiquitous thing; an unresolvable colour; no colours (`give at least one colourId`); a ubiquitous colour; and the **cover floor**: over the rhythm's rows (§ 6.2 — the rows citing every named thing), the rows held by any of the named colours must be at least 50 % of them (`rhythmCoverFloor`), else `those colours hold <h> of the <t> fragments about <things>; a scope must hold most of the rhythm` followed by `. Colours that do: …` (up to 3 covers, § 6.2's cover parts) or `. No colour covers it, so it cannot be proposed in this run; name it at finish`. A rhythm with no rows passes the floor (0 ≥ 0).

The schedule is built in Go, never taken from the model: `period` = `24h` / `168h` / `720h` / `2160h` for the four cadences, `duration = period`, `startTime` = the floored start as RFC3339; `window_spec_versions` = `[{versionNumber: 1, effectiveFrom: <start, RFC3339 UTC>, spec}]`, i.e. one version **effective from the start** so every grid window since then is pending once a lens exists (`windows.md` § 2–3, `lifecycle-reflection.md` § 4). The `reflection` row is saved as in § 5 with `current_context_spec = {colourIds}` — the things are evidence only and are not stored. The colours' members are marked covered; `outputs` gets `{kind: reflection, id, name, status: proposed}`; the result is `Proposed reflection "<name>" (id: …, <n> fragments in scope, holding <h> of <t> about <things joined " with ">, <cadence as passed> from <YYYY-MM-DD>).`

### 6.2 Rhythm detection (`rhythm.go`)

Computed from the run's annotation rows, never asked of the model. A dated row falls in a bucket at a grain: **month** (calendar month; ordinal `year*12 + month − 1`, start = the 1st, UTC) or **week** (Monday of its week; ordinal = weeks since the epoch's Monday, + 1). Undated or unparseable dates count toward `Total` but no bucket. A bucket's title is that of the first row it received (rows arrive in date order).

**Singles.** Every thing in the index with ≥ 5 citing rows and present in the document (`worklistFloor`; restricted to the given things when `thingIds` was passed) gets: `Total` rows, `ActiveBuckets` (distinct buckets), `SpanBuckets` (first to last ordinal inclusive), `First`/`Last` bucket starts, `Onset` = the start of the first run of ≥ 3 consecutive buckets (`rhythmOnsetRun`), else the first bucket, and a `Ubiquitous` flag (§ 6.3). Singles are not filtered by activity; after sorting, at most 25 are kept (`rhythmSingleLimit`).

**Pairs.** Eligible things are the non-ubiquitous ones at or above the floor and present in the document; for every row citing two or more of them, each pair (sorted ids) accumulates that row — with `thingIds`, only pairs containing at least one given thing. Pairs with fewer than 3 active buckets (`rhythmActiveFloor`) are dropped; after sorting, at most 25 are kept (`rhythmPairLimit`).

**Ordering** (`sortRhythms`, stable over an input in map order): active buckets desc, then regularity (`Active / Span`, 0 when the span is 0) desc, then `Total` desc, then first thing id asc; full ties keep an undefined relative order.

**Cards.** `Name (id)[ with Name (id)] · <total> fragments`, then either ` · undated` (no dated row: the card ends here, with no cover line or buckets, although the cover is still computed) or ` · <active> of <span> <grain>s active, <first> to <last> · onset <onset>[ · ubiquitous: not a rhythm, do not propose on it]`, the **cover line** (indented), and up to 12 evenly sampled active buckets (`rhythmBucketSample`) as `<start>: <count> · <title>`. The block heads the two lists `Rhythms at the <grain> grain (things, most sustained first):` / `Rhythms at the <grain> grain (pairs of things cited together, most sustained first):`, with `(no thing reaches the floor yet)` / `(no pair is cited together in three or more buckets)` when empty.

**Cover line.** Over the rhythm's rows (a single's citing rows; for a pair, the rows citing both), every non-ubiquitous colour holding at least one of them, ranked exact carriers first (a colour whose resolved `thing_ids` include every thing of the rhythm), then by rows held desc, then id asc; the top 3 (`rhythmCoverList`) render as `covered by: <name> (<id>[, built on it]) <held> of <total> · …`, followed by `<k> in no colour` when some rows are held by no non-ubiquitous colour. No carrier → `no colour covers it: not proposable in this run`.

### 6.3 Ubiquity

The one rule, `ubiquitousRows(n)`: false when there are fewer than 20 rows (`ubiquityMinRows`), else true when `n` exceeds 40 % of all rows (`ubiquityShare`). For a thing, `n` = its citing rows; for a colour, `n` = its annotated members. A ubiquitous thing is flagged on its rhythm card, excluded from pairing, and rejected as a scope by the colours flow and by the reflections proposal (`<name> (<id>) is cited across most of the workspace; it is the cast, not a rhythm, and cannot be a reflection's scope` — the same text in both flows). A ubiquitous colour is rejected as a scope by the projections and reflections flows (`colour <name> (<id>) holds most of the workspace; that is the cast, not a rhythm, and it cannot be a scope on its own`) and never appears on a cover line, in a cover-floor suggestion, or among the rows a cover line counts as held.

## 7. What discover does not do

- It never generates output, drafts a lens, or opens a refinement; a proposal is an ordinary live `projection` / `reflection` row that the client recognises by `status = proposed` and `description`. No backend route reads or acts on proposals as such — `discover` is the only package that writes or tests the `proposed` entity status, and nothing on the server reads `description` back. The row leaves `proposed` only when a refinement commit on it sets `status = active` (`refinement.md` § 5, `lifecycle-projection.md` § 3, `lifecycle-reflection.md` § 4), or it is soft-deleted like any other row (`lifecycle-projection.md` § 6, `lifecycle-reflection.md` § 8). Until then it is invisible to staleness, which evaluates `status = 'active'` rows only (`reconcile.md` § 1), and is counted by § 8.
- It never deletes or edits an existing entity, never creates colours outside the colours flow, and never re-runs on its own; each run is one kick, and the only automatic kick is the post-import pipeline (§ 2).
- It never pins fragments or things: a proposal's scope is colours (and, for projections, source projections), so it grows with the colours.
- It never reads fragment bodies beyond the 12-read budget, never sees a prompt-colour's rule beyond the prompt text in `list_existing`, and never refreshes its colour index or map snapshot during a run.
- It never records a refused run (§ 2 guards, model resolution or snapshot-load failures), never re-queues kinds dropped at shutdown, and never cleans up a run interrupted by process death.

## 8. The discover status axis

`discover.EvaluateStatus(app, worker, version, things)` is composed into `GET /api/status` as `discover` (`api.md` § 9); the aggregate passes the things document's current `version` and its thing count. The wire shape (`api.DiscoverStatus`): `state`, `running` (omitted when empty), `pending`, `due`, `runs`, `proposals {projections, reflections}`, `waitingOnMap`, `currentStarted` (omitted when no run is in progress; RFC3339 UTC). Any database error ends the evaluation with that error, failing the route.

- **From the worker** (in-process only; absent when no worker is wired, in which case `pending` is `null`, `running` is empty and `waitingOnMap` false): `running` = `Running()`; `pending` = `Pending()` in kind order; `waitingOnMap` = the flag set around `WaitSettled` in § 2 (true only while `running` is set); `currentStarted` = `CurrentStarted()`.
- **From rows**, per kind in kind order: `runs[kind]` = the newest `discover_run` of that kind by `created` — `{id, status, error?, model?, rounds?, mapVersion?, finished, interrupted?}` where `model` = `generated_by_model`, `finished` = the row's `updated` (also for a `running` row), and **`interrupted`** = `status = running` while the worker is not currently running that kind (a crash leftover, or a row whose closing save failed; with no worker wired, every `running` row). `due` (only when `things > 0`, else always empty): the kind has no `done` run, or its newest `done` run's `map_version` is below the current version — an `error` or `running` newest run does not count either way. `proposals` = counts of `projection` and `reflection` rows with `status = proposed` and `deleted_at = ''`.
- **`state`**, first rule that matches: `running` when `running` is set (including while waiting on the map); `pending` when `pending` is non-empty; `never_run` when no kind has any run row; `due` when `due` is non-empty; else `settled`.
