## 1. Request and routing

Body is `api.ChatRequest`: `{id, messages: [{id, role, parts: [{type, text?, data?}]}]}` (AI-SDK `UIMessage`s; `data` is raw JSON). A body that fails to bind → 400 `invalid chat request body`.

The handler first looks `id` up as the `external_conversation_id` of a `projection_refinement`, then of a `reflection_refinement`; a hit dispatches the whole request to `HandleChatForRefinement` (`refinement.md` § 3; a window-only send is § 4). The lookups run whatever `id` is, including empty. Otherwise this is a general chat.

## 2. Persistence

- **Conversation**: `chat_conversation` found or created by `external_conversation_id = id`. A create that fails (a lost race) re-reads the winner; if that also fails the error is logged and the turn runs with **no persistence**. An empty `id` skips the lookup entirely — the turn still runs, nothing is stored. The row's `generate_with_model` field is the per-conversation model override, re-read every turn; no route sets it, and the collection is server-written (create/update/delete rules `nil`, read rule `@request.auth.id != ''`), so only a superuser or server code can set it.
- **Messages**: `chat_message` rows keyed by `chat_conversation_id` (the same table holds refinement transcripts under `projection_refinement_id` / `reflection_refinement_id`, `PersistMessage` picking the column from the owning collection). `content` = the whole `UIMessage` as JSON; `generated_by_model` = the model that produced an assistant row, `""` for every incoming message; `bookmarked` and `fragment_id` are § 7. Rows load ordered by `created`; a row whose `content` fails to decode is skipped silently.
- **New messages** = incoming messages whose `id` is not already stored (dedupe by id only; content is never compared). Before persisting, `ResolveContextSpecs` walks the new **system** messages: one carrying a decodable `context_spec` part and/or a decodable `window` part re-resolves the cumulative (spec, window) pair — the pair starts from the newest of each in the stored history, a `window` with an empty `start` or `end` clears the window — through `ResolveSpecToIDs` (`context.md` § 2–3) and appends a `pinned_ids` part (`context.md` § 5) to that message. A resolution error appends nothing and is not logged; the message persists without a receipt and later hydration sees no context change from it. New messages are then persisted one by one; a failure is logged and the turn continues.

The client is expected to send the full transcript each turn; only the unknown ids are stored, so a client that re-sends an assistant message under a new id creates a duplicate row.

## 3. Prompt assembly

`PrepareLLMPrompt` → `HydrateDeltaHistory` over stored + new messages. It first reads the transcript's **final** state with `LatestPinnedAndSpec`, which scans system messages newest-first and takes, each independently, the newest `pinned_ids`, the newest `context_spec` and the newest `window` part. **Mode** is the newest `context_spec`'s `wholeScope == "summaries"` over the whole transcript, whichever message carries it; `"full"` and an absent `wholeScope` are both full mode. One `Hydrator` is built on the final `pinned_ids` and that mode (`context.md` § 4). It then walks every message in order: a system message contributes `WindowNotice(start, end)` when it carries a bounded `window` part, plus — only when it carries a `pinned_ids` part — the hydrated delta between the previous `pinned_ids` and this one (a delta error is discarded and renders as nothing); the message is emitted only if the resulting text is non-empty. Every other message is `Flatten`ed (`context.md` § 7), which is also where mention expansion happens: every `@[Kind:id|Label]` token in a `text` part is rewritten to its model-facing reference form at prompt assembly, while the raw token is what persists. Because every delta renders against the final context, a fragment that has since left the context is omitted with a count rather than replayed, a conversation that switched modes re-renders its whole history in the new mode, a fragment the user pinned (by id, type or colour — the receipt's `expandedIds`) renders in full even in summaries mode, and a fragment that left and came back is announced as restored rather than rendered twice. An empty hydrated transcript → 400 `messages required`; a transcript whose only content is a non-empty context delta is not empty and proceeds to the model.

The system prompt is prepended: `ChatSystemPrompt`, or in summaries mode `ChatSummariesSystemPrompt(digest)` = `ChatSystemPrompt` + `ChatSummariesLegend` + digest. The digest (`SummariesMapDigest(doc, 2)`) is the current map: the narrative (or `(no narrative yet)`), the things with at least **2** fragments heaviest-first as `id · name · kind · fragments · span · blurb` (or `(nothing on the map reaches the floor yet)`), and every relationship whose two ends resolve. A map load failure yields an empty digest silently; the legend is still sent.

Model = `ResolveRoleFor(RoleChat, conversation.generate_with_model)`: a non-blank override is used verbatim (trimmed, unvalidated), else the chat role's default (`models.md` § 5); none → 500 `no model configured for chat`. `CheckPromptFits(model, chars)` (`context.md` § 6) refuses with **422** and the guard's message; in full mode the message is suffixed ` Switch the scope to "Summaries" in the context bar to chat over it through summaries instead.` The assistant message id is minted as `txt-<unix-nanos>`.

## 4. Full-mode turn

`usage.Stream(RoleChat, model, msgs, nil)` — no tools — at Interactive priority (the role default, `llm-queue-quota.md` § 2.1). Quota exhaustion → 402 (`llm-queue-quota.md` § 5); a classified provider error → its envelope (`llm-queue-quota.md` § 6); any other error → 500 `llm stream failed`. The response is then an SSE stream (§ 6) relaying the completion; when it drains, and only when a conversation row exists, one assistant `chat_message` is persisted with `id` = the minted id, a `text` part if any text arrived and a `tool-<name>` part `{toolCallId, toolName, input}` per tool call (none can occur without tools); no parts → no row. A stream cut mid-way persists whatever text arrived — `StreamTurn` reads the event channel to its close and does not distinguish a completed stream from an aborted one.

## 5. Summaries mode

Selected per § 3. The model sees rows instead of bodies for everything in scope that the user did not pin; pinned fragments and upstream snapshots stay in full (`context.md` § 4). It is given two tools built on the discover reader (`discover.md` § 3.3): `read_thing {ids: [string]}` and `read_fragment {ids: [string]}` (both `required: ["ids"]`; dispatch also accepts a single `id`), with chat wording and a **12 fragment reads per turn** budget. The reader (map document and all annotation rows) is loaded once per turn, before anything is streamed; a load failure → 500 `load map for summaries chat`. The first model call is made with the tools and maps errors exactly as § 4.

The turn is a loop of at most **4 model calls** (`maxChatToolRounds`) inside one SSE response (one assistant message on the client):

1. Stream round *r*; its text is emitted under the text id `<messageId>-r<r>` and appended as a `text` part; its tool calls are collected.
2. No tool calls, or this was the 4th call → stop.
3. Dispatch each call through the reader, in order:
   - `read_thing`: at most **10** refs per call (extra refs are dropped and the output opens with `read_thing takes at most 10 ids per call; the first 10 were read.`); each ref (trimmed) resolves by thing id, else by normalised name (lower-cased, whitespace collapsed, trailing punctuation dropped), to a thing card, or `No thing matches "<ref>".`
   - `read_fragment`: an empty list → `No fragment with id "".`; blank ids are skipped; each id spends one read and renders as a `FragmentBlock`, an unknown id → `No fragment with id "<id>".` and spends nothing; once the 12th read lands with ids still unread, `Fragment read budget exhausted (12 per turn). …` is appended and the rest are skipped; a call arriving after the budget is spent gets that message in place of its first id and once more if it carried further ids. The budget is per reader, i.e. per turn across all rounds.
   - any other name → `no tool named "<name>"`.

   Each result is sent as `tool-output-available` and appended as a `tool-<name>` part `{toolCallId, toolName, input, output, state: "output-available"}`. **The assistant row is written (created, then rewritten in place) after every round**, so an interrupted turn keeps its reads.
4. Append to the model transcript an assistant message = the round's text + `\n\n[You called: <names>]`, then a user message = the outputs joined by blank lines. `CheckPromptFits` again — too large → an in-band SSE `error` event with the guard's text (no summaries hint), stop. The 4th call, when reached, is made **without tools** so the turn ends in text.
5. A `Stream` error opening a later round → SSE `error` with the raw error text (quota exhaustion and provider errors take this path too, not their § 4 envelopes), stop.

After the loop the row is written once more and the stream finishes. Without a conversation row nothing is persisted but the loop runs the same.

**Replay on later turns**: `Flatten` turns persisted read parts back into the assistant text + `[You called: …]` + a user message with the outputs, so the model sees its earlier reads without re-reading (`context.md` § 7). A read part without an `output` (an interrupted call) is dropped.

## 6. The SSE stream

Headers `Content-Type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`, `Cache-Control: no-cache`, `Connection: keep-alive`; status 200 is committed by the first event, after which errors can only be signalled in-band.

Events (each `data: <json>`): `start {messageId}` — the server-minted assistant message id, which the client must adopt or the next turn persists a duplicate; `text-start {id}` / `text-delta {id, delta}` / `text-end {id}` (one segment per model call, `text-end` only if text started); `tool-input-start {toolCallId, toolName, dynamic: true}`, `tool-input-delta {toolCallId, inputTextDelta}`, `tool-input-available {toolCallId, toolName, input, dynamic: true}` as a tool call streams; `tool-output-available {toolCallId, output}` when the server has a result; `data-<name> {data, transient?}` parts — the general chat emits only `data-inference_rate {tokensPerSecond}` (transient), at most every 250 ms while text streams (rate = text events per second since the first event) and once more from the provider's final usage when it reports a rate; refinement adds the non-transient `refine_lint`, `refine_error` and `window_reapply` (`refinement.md` § 3–4); `error {errorText}`; `finish`; then `data: [DONE]`. Flushing happens after every event when the writer supports it.

## 7. Bookmarks

`PATCH /api/chat/conversations/{cid}/messages/{mid}/bookmark`, body `api.BookmarkRequest` `{bookmarked: bool}`. `{cid}` is looked up in `chat_conversation` only → 404 `conversation not found` for a refinement's id or a chat that has never sent a turn; an unbindable body → 400 `invalid bookmark body`. `{mid}` is a `UIMessage` id, found by scanning the conversation's rows and decoding `content` (a turn still streaming has no row yet) → 404 `message not saved yet`; a `system` row, or one whose content does not decode → 422 `only chat turns can be bookmarked`. Both `user` and `assistant` rows qualify. Sets `bookmarked` to the body value (clearing leaves the row and any `fragment_id` in place); save failure → 500. Response 200 `api.MessageMark` `{messageId, bookmarked, fragmentId?}`.

`POST /api/chat/conversations/{cid}/bookmarks/save` (same 404 rule) runs `SaveBookmarks` under a context detached from the request, in **one transaction**: every row with `bookmarked = true`, by `created`; a `system` row, an undecodable one, or a turn with no text is skipped. Text = the message's `text` parts trimmed and joined by a blank line, with a **user** turn's mention tokens reduced to `@Label` (`StripMentions`). A row whose `fragment_id` points at a fragment with empty `deleted_at` is reused (`created: false`); otherwise a `fragment` row is created directly (not through the ingest writer, so no content-hash dedupe): `type = "chat"`, `ingested_via = "app"`, `source = "chat:<cid>:<mid>"`, `content` = the text, `occurred_at` = the message row's `created`; the message row is stamped with `fragment_id`. The fragment birth hooks fire as for any app-written fragment — defaults, colour signal, annotate signal, reconcile wave (`ingestion.md` § 7). Any save failure rolls the whole batch back → 500 `failed to save bookmarks`. Response 200 `{saved: [{messageId, fragmentId, created}]}`, `[]` when nothing qualified. Idempotent for turns already saved; a turn whose fragment was soft-deleted gets a fresh one.

## 8. The brief

`POST /api/chat/conversations/{cid}/brief` (same 404 rule) asks the model what projection the session was working towards; nothing is created. Transcript = every non-`system` row with text, in order, as `{role, text, bookmarked}` lines; none → 422 (`ErrNoBrief`). Model = `ResolveRoleFor(RoleChat, conversation.generate_with_model)` (error → 500). Prompt = system `ChatBriefSystem` + one user message from `ChatBriefTranscript` (bookmarked lines marked `[bookmarked]`); `CheckPromptFits` → 422 with the guard text. `usage.GenerateWithToolCalls` at Interactive priority with the single tool `propose_brief {name, message}` (both required). Quota exhaustion → 402; provider error → envelope; a preempted or interrupted call → 500 `failed to write the brief`. The **last** `propose_brief` call wins; with no usable call, the answer text becomes `message` and `name` stays empty; an empty `message` after trimming → 422. Response 200 `api.BriefResponse` `{name, message}`.

## 9. Prompt estimate

`chat.EstimatePrompt` answers the conversation form of `POST /api/context/tokens` (`api.md` § 3; the spec form is `context.md` § 6): a body carrying `conversationId` sizes that chat's next turn. The conversation is read if it exists, never created; its stored messages plus one pending system message (`id: estimate-spec`, `context_spec` part = the body's spec fields, `window` part when the body's window is bounded) go through `ResolveContextSpecs` and `PrepareLLMPrompt` exactly as a turn would, so a spec identical to the one in effect adds an empty delta and a changed one costs its delta. Tokens are `chars / 4` per message: the first message → `System`, other system messages → `Context`, the rest → `Transcript`. The handler returns 500 `estimate failed` on error, else 200 `{totalTokens, breakdown: {System, Context, Transcript}, model, limit, fits}` where `model` is resolved through the conversation's `generate_with_model` override (a resolution failure leaves `model` empty and `limit` 0), `limit` = `PromptBudget(model)` and `fits` = `limit <= 0 || totalTokens <= limit`.

## 10. What the chat does not do

- No server-side tools in full mode; no memory beyond the persisted transcript; no summarisation of long histories — the size guard refuses instead, and the omission of context that has since left is the only trimming.
- No routes to list, rename or delete conversations or messages, and no way to set `generate_with_model` from the client: both collections are server-written and readable by any authenticated user (`schema.md` § 2.12–2.13); deleting a `chat_conversation` cascades to its messages.
- A bookmark by itself creates nothing; only the save route writes fragments, and it never deletes them — clearing a bookmark or deleting a message leaves the fragment in place.
- The brief creates no projection; the client decides what to do with the name and message.
