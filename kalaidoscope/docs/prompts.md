Every tool and parameter description string is a `prompts` constant; the defining files hold only the JSON schema skeletons, built by hand or through `agent.IDTool` (one required string parameter of a given name), `agent.IDsTool` (a required `ids` string array), `agent.EmptyTool` (no properties) and `agent.StringArraySchema` (a string-array property fragment) (`tool-loop.md` § 6). `required` lists and enums are enforced by the schema only where the provider honours it — the refinement handler re-checks `directive`, `target`/`replacement` and `whole_scope` (`ApplyContextOps` treats any value other than `full` / `pins` as "leave the mode alone"), and the discover dispatchers re-check name/message/scope presence, cadence and dates themselves (§ 2, rejections); unknown keys are ignored everywhere. An `llm.Tool` is `{name, description, parameters}`; a call comes back as `llm.ToolCall{id, name, args}`.

## 4. Wire identifiers that are also prompt text

- `update_lens`, `regenerate_from_lens`, `suggest_name`, `refine_candidate`, `update_context`, `apply_result` are simultaneously tool names the model sees (`apply_result` never), persisted part types (`tool-<name>`, data `{toolCallId, toolName, input}` from `chat.ToolCallPart`) on refinement assistant messages, and strings the client reads. The compiled lens is not a tool part: it persists as `data-lens` `{lens}` (`LensPartType`, `LensPartData`), which `refinement.LatestLensPart`, `refinement.ExtractDraftedLensAndSpec` (commit, `refinement.md` § 5) and `refinement.CarryOpenRefinementToCandidate` (a refinement that has drafted a lens is not carried to a fold-in candidate) all read; each also still reads a legacy `tool-update_lens` part whose `input.lens` is non-empty, the shape `refinement.SeedLensTurn` fabricates when a projection or reflection refinement opens on an entity whose `current_lens_id` lens has a prompt (`refinement.md` § 2), alongside a `data-lens_seed` `{}` part and, for a reflection with a window that has an approved output, a `tool-apply_result`. `llmcontext.Flatten` echoes `data-lens` and legacy `tool-update_lens` as `LensEcho`, echoes `data-context_confirmation` as `ContextProposalEcho`, drops the whole assistant turn when it carries a `data-window_reapply` part, and is silent on every other tool part — `tool-apply_result`, `tool-suggest_name`, `tool-regenerate_from_lens`, `tool-refine_candidate` and a directive-form `tool-update_lens` never re-enter the transcript, so the model sees its directive only through the compiled lens.
- The other refinement part types the package names — `data-hand_edit`, `data-refine_target`, `data-edit_triage`, `data-refine_result`, `data-regenerate_superseded`, `data-regenerate_confirmation`, `data-regenerate_confirm`, `data-regenerate_cancel`, `data-refine_proposal_result`, `data-context_confirmation`, `data-context_confirm`, `data-context_cancel` (`HandEditPartType`, `RefineTargetPartType`, `EditTriagePartType`, `RefineResultPartType`, `RegenerateSupersededPartType`, `RegenerateConfirmationPartType`, `RegenerateConfirmPartType`, `RegenerateCancelPartType`, `RefineProposalResultPartType`, `ContextConfirmationPartType`, `ContextConfirmPartType`, `ContextCancelPartType`) — split into three groups: system-message parts the hydrator turns into notices (§ 2); assistant-message parts streamed to the client and never rendered to the model (`data-refine_result` `{ok, editId, sequence}` / `{ok, error}`, `data-regenerate_confirmation`, `data-context_confirmation` except for its echo); and system-message parts the client appends to steer the next send (`data-regenerate_confirm` → `refinement.StreamRegenerateConfirmed` re-applies the current lens with no model turn; `data-regenerate_cancel` and `data-context_cancel` → an empty SSE response, the part persisted for the next turn's notice; `data-context_confirm` travels with a `context_spec` part and is not special-cased — the turn proceeds with the new context). The `data-refine_error` and `data-refine_lint` part types and the `refine_error` / `refine_lint` / `lens` SSE data names are string literals in `refinement/chat.go`, not `prompts` constants.
- `read_thing`, `read_fragment` are persisted as `tool-<name>` parts with their `output` (`chat.ToolResultPart`, `state: output-available`) on explore assistant messages and replayed by `Flatten` as an assistant echo plus a user turn of outputs; a part without `output` (an interrupted turn) is skipped (`context.md` § 7). `read_colour` and the discover-only tools are never persisted as parts; discover transcripts are not stored.
- `propose_brief` is never persisted: its arguments return to the client as the brief response and nothing is created.
- `EditFragmentKind` (`edit`) is both the stored `fragment.type` value and the kind the model reads in the block header; `ContextLegend` quotes it.
- `ThingCitation`'s JSON tags (`ref`, `name`, `kind`, `note`) are the stored shape of `fragment_annotation.things`, read back by `sourcedata.LoadAnnotationRows`, `mapping.consolidate` and the colour thing-rematch (`colours.md` § 3).
- The kind vocabulary the annotate and consolidate prompts dictate (`person, organisation, place, project, topic, other`) is `mapdoc.Kinds`; `mapdoc.NormalizeKind` folds `organization` / `company` / `org` to `organisation` and anything else unknown to `other`.
- The cadence words in `ProposeCadenceParamDescription` and the `propose_reflection` schema enum are the keys of `reflections.CadencePeriods`, mapping to grid periods `24h`, `168h`, `720h`, `2160h`; the model never sees the durations. The `startTime` layouts are `reflections.ParseStartDate`'s.
- Thing references in every tool argument resolve through `mapdoc.Document.Resolve` (exact id, then normalised name); colour references through `discover.Context.colourByRef` (exact id, then case-insensitive name) — so the "ids" the schemas ask for accept names, as the parameter descriptions say. Fragment ids and kinds in `update_context` arguments are not resolved at proposal time: `ApplyContextOps` copies them into the proposed spec as given (deduplicated, blanks dropped, an id both pinned and unpinned ends up unpinned), and validation happens only when the confirmed `context_spec` is resolved like any other.
