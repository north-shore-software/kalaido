**Scope.** The refinement conversation shared by projections and reflections: how a session is opened and seeded, how each chat turn drafts a lens through a tool call and then executes it as a from-scratch preview, the window-reapply turn, what a commit installs, the lens row itself, and how a generation resolves the active lens. Entity-agnostic; the per-entity consequences of a commit are in `lifecycle-projection.md` § 3 and `lifecycle-reflection.md` § 4. Transcript hydration, `PinnedIDs`, the prompt-size guard and flattening are in `context.md` § 4–7; the model-facing text (system prompt, tool descriptions, apply prompt, echo/continuation strings) is inventoried in `prompts.md` § 2–4; the routes as a wire index are `api.md` § 7 (turns via § 4).

**Completeness anchor.** 4 refinement routes registered in `server/server.go` (`POST /api/{projections,reflections}/{id}/refinements`, `POST /api/{projections,reflections}/{id}/refinements/{rid}/commit`); the `POST /api/chat` route is registered with `HandleChatForRefinement` as its refinement handler and dispatches to it when the request's `id` matches a `projection_refinement` or `reflection_refinement` row; 2 tools advertised to the refinement model (`update_lens`, `suggest_name`); 1 fabricated tool that no model is ever offered (`apply_result`); 1 lens-row write site (`engine.CommitRefinement`) and 1 `current_lens_id` write site (the same function).

## 1. Objects

- A **refinement conversation** is a row in `projection_refinement` or `reflection_refinement` (both collections have API create/update/delete disabled; reads require an authenticated request): the parent relation (`projection_id` / `reflection_id`, cascade-deleted with the parent row), for projections optionally the snapshot it was opened from (`projection_snapshot_id`, cascade-deleted with the snapshot), the client's `external_conversation_id` (unique per collection), and `created`. `reflection_snapshot_id` exists on the reflection collection but is never written by the create route. Its messages are `chat_message` rows keyed by `projection_refinement_id` / `reflection_refinement_id` (cascade-deleted with the conversation), each storing one UI message (`{id, role, parts}`) in `content` and the producing model in `generated_by_model` (empty for user, system and fabricated rows). Soft-deleting the parent (`lifecycle-projection.md` § 6, `lifecycle-reflection.md` § 8) leaves conversations and messages in place; only a hard delete of the row cascades.
- A **lens** is an immutable `lens` row: `prompt` (the standing instruction, plain text), `parent_lens_id` (the lens it replaced on the parent — audit lineage only, nothing reads back through it), exactly one of `created_from_projection_refinement_id` / `created_from_reflection_refinement_id`, and `created`. The lens carries **no** context spec: the scope it applies to is the parent's `current_context_spec` (§ 6). The collection has both read and write disabled for API clients. Lens rows are written only by `CommitRefinement` (§ 5), never updated, and never deleted — none of the lens row's own relations (`created_from_*_refinement_id`, `parent_lens_id`) carries a cascade, so hard-deleting a refinement conversation, a parent entity or an older lens leaves lens rows in place; the relations pointing at `lens` (`current_lens_id`, `lens_id`) carry none either.
- A lens is **stamped on snapshots** through `lens_id`: every `projection_snapshot` / `reflection_snapshot` written through `applySnapshotSpec` records the lens that produced it (the parent's `current_lens_id` for a generation; the source snapshot's `lens_id` for a hand edit, `lifecycle-projection.md` § 4.2). Readers compare a snapshot's `lens_id` with the parent's `current_lens_id`: `latestApprovedOutput` refuses to minimise against an approved output of another lens (the regeneration then runs from scratch), `settleApprovedInPlace` refuses to settle onto it, `SnapshotIsCurrent` reports it as not current, and the reflection series marks such a window `lensOutdated` and includes it in the windows a generate call covers (`lifecycle-reflection.md` § 5.1, § 9).
- The **drafted lens** during a session is not a row: it is the `input.lens` of the newest `tool-update_lens` part on an assistant message. A lens row is created only at commit.

## 2. Opening a session (`POST …/{id}/refinements`)

Body `{clientId, snapshotId?, window?, contextSpec?}` (`api.CreateRefinementRequest`); malformed body → 400 `invalid request body`; empty `clientId` → 400 `missing clientId`; empty path id → 400 `missing target id`. In one transaction:

1. The conversation row is created with `external_conversation_id = clientId`. **Projections:** the parent must exist and not be soft-deleted (`FindLive`), `projection_id = {id}`; if `snapshotId` is given it is stored in `projection_snapshot_id` and the `projection_snapshot` row loaded — the snapshot's own parent is not checked against `{id}`. **Reflections:** `reflection_id = {id}`, the parent loaded via `FindLive`; `snapshotId` is **ignored**. Any load failure (missing or soft-deleted parent, missing snapshot, unique-index violation on `clientId`) rolls back and is reported as 500 `failed to create refinement` — never 404.
2. The seeded context spec is chosen: the body's `contextSpec` if present; else (projections) the source snapshot's `context_spec`; else (reflections) the parent's `current_context_spec` when it is non-empty and not `null`. A projection opened without `snapshotId` and without `contextSpec` is seeded with **no** spec.
3. Reflections only: the target window is the body's `window` if both `start` and `end` are set, else `DefaultRefinementWindow(parent, now)` (`windows.md` § 7) — nil for an unscheduled reflection. Its `id` is always recomputed server-side (`WindowID(reflectionId, window)`); a client-supplied `id` is discarded. Projections never get a window.
4. If a spec or a window exists, one **system** message (id `ctx-<unixnano>`) is persisted carrying, in order: a `context_spec` part (when a spec exists), a `window` part `{id,start,end}` (when a window exists), and — when a spec exists — a `pinned_ids` part resolved now under that window (`context.md` § 2–3, § 5). A resolution error silently drops the `pinned_ids` part; the spec and window parts are still persisted.
5. Reflections with a `current_lens_id` whose `lens.prompt` is non-blank: an **assistant** message (id `seed-<unixnano>`) is persisted carrying a `data-lens_seed {}` marker, a `tool-update_lens` part (`toolCallId` `seed-lens-<n>`, `input {lens}`), and — only when a window was chosen **and** that window has an approved `reflection_snapshot` with non-blank `output` — a `tool-apply_result` part (`seed-apply-<n>`, `input {output}`) with the newest-approved output. An unscheduled reflection (nil window) never receives the apply part even if it has an approved windowless snapshot. A reflection with no lens, a lens row that fails to load, or a projection gets no seed turn.

Response `201 {refinementId, messages}` — the seeded messages exactly as persisted; the client must render these ids rather than reconstruct them, or the next turn persists duplicates (`ExtractNewMessages` dedupes by id only). A session with seeded context but no drafting turn cannot be committed (§ 5).

## 3. A drafting turn (`POST /api/chat` routed to a refinement)

`HandleChat` binds `{id, messages}` and looks `id` up as `external_conversation_id` first in `projection_refinement`, then in `reflection_refinement`; a hit dispatches to `HandleChatForRefinement` before any plain-chat handling (`chat.md` § 1). Then:

1. Stored messages are loaded (a load error is ignored and treated as an empty transcript); incoming messages whose ids are unknown are the new ones. `ResolveContextSpecs` appends a `pinned_ids` part to each new **system** message carrying a `context_spec` and/or `window` part, resolved against the cumulative (spec, window) pair — a `window` part with empty bounds clears the window. New messages are persisted with an empty `generated_by_model`; a persist failure is logged and the turn continues.
2. The parent is resolved (`projection_id`/`reflection_id`, else via the source snapshot; a soft-deleted parent resolves to none) and its `generate_with_model` read; a refinement has no model of its own. With no parent the override is empty and role defaults apply.
3. **Re-apply check** (§ 4): if the new messages contain no `user` message and at least one system message with a bounded `window` part, the turn is a window re-apply and the lens-writer is not consulted. Any other send — including one that carries only a `context_spec` part, or only an unbounded `window` part — proceeds as a drafting turn against the transcript as it stands.
4. The transcript is hydrated (`HydrateDeltaHistory`: window notices, context deltas in the mode the latest spec selects, `Flatten` for non-system messages — `context.md` § 4, § 7) and prefixed with `RefinementSystemPrompt` (`prompts.md` § 2). Because the system prompt is always present, the `400 messages required` branch that follows is unreachable.
5. Model = `ResolveRoleFor(RoleRefinement, parent.generate_with_model)` — the entity's override, when set, wins for this role too; no model → 500 `no model configured for refinement`. `CheckPromptFits` over the hydrated transcript's characters refuses with 422 and the guard's text (`context.md` § 6) before the call.
6. `usage.Stream` at `RoleRefinement` (provider defaults for generation options; `Interactive` queue priority) with tools **`update_lens`** (`lens` required, `suggested_name` optional) and **`suggest_name`** (`name` required); `llm-queue-quota.md` § 1. Quota exhaustion → 402 envelope; a classified provider error → its envelope (`llm-queue-quota.md` § 6); any other error → 500 `llm stream failed`. All of these occur before the SSE stream opens.
7. The turn streams as an AI-SDK UI-message stream opened with `start {messageId: txt-<unixnano>}` (`chat.md` § 6). Each tool call is persisted as a `tool-<name>` part **as it arrives** — the assistant `chat_message` row is created on the first write and rewritten in place after that — then the final text part plus all tool parts are written. The row's `generated_by_model` is the refinement model. A turn that produces neither text nor a tool call writes no row.
8. **Name-only continuation:** when the turn has no text, at least one tool call, and no `update_lens` call carrying a non-empty `lens`, a second model call is made on the same open stream: the transcript plus an assistant echo of the tool names called and a user message `NameRecordedContinue` (`prompts.md` § 2), with **no tools** advertised, guarded by `CheckPromptFits`. Its text streams under id `<textId>-c1` and is appended to the same persisted message as a `text` part. A guard refusal, a call error or an empty reply is logged and the turn ends with only the tool parts; no error reaches the client.
9. The **lens** is the `lens` argument of the turn's last `update_lens` call with a non-empty `lens`. If there is none (a clarifying question, a `suggest_name`-only turn, or a call with an empty lens) the stream finishes; the preview keeps its prior output. Nothing in code counts questions per turn, enforces the interview before the first lens, or checks `suggested_name`/`name` length — those are prompt instructions only (`prompts.md` § 2).
10. **Lint:** if `engine.LensCountPin` finds a totality count phrase in the lens (`N in total`, `total of N`, `N total`, `all N`; `N` = digits or the number words one–twenty, case-insensitive), a non-transient `data-refine_lint {match}` part is streamed and persisted on the same message. The apply still runs; nothing is redrafted.
11. **Apply leg** (§ 3.1) against the transcript's latest `pinned_ids` and `window` (`LatestPinnedAndSpec`: newest system part of each type), then `finish`.

### 3.1 The apply leg

`streamApplyLeg` executes the drafted lens through `engine.ApplyDraftLens`:

- Source block = `HydrateIDsToText` of the pinned ids — always the **full** (flat) rendering of fragments and upstream snapshots (`context.md` § 4), whatever `wholeScope` mode the spec selects; empty when nothing is pinned (the lens is then applied to no sources).
- Model = `ResolveRoleFor(RoleSnapshot, parent.generate_with_model)`; no model → `data-refine_error {kind: apply_failed, message: "no model configured for generation"}` before any tool event.
- A fabricated tool call named `apply_result` (`toolCallId` `apply-<unixnano>`) is streamed: `tool-input-start` **before** the model call, then a `tool-input-delta` of `{"output":"` and one JSON-string-escaped delta per text chunk as the model produces them, then `"}` and a `tool-input-available` carrying the authoritative trimmed output.
- Prompt = `ApplyPrompt(lens, sourceBlock, windowStart, windowEnd)` as a single user message (`prompts.md` § 2; zero bounds for a nil window), at `RoleSnapshot` options (temperature 0) and the role's `Interactive` queue priority, via `usage.GenerateStreamMsgs` — no tools. `CheckPromptFits` is applied to the prompt's length. A preempted call, an interrupted stream, and an empty (whitespace-only) output are all errors.
- **Always from scratch:** the minimal-diff rewrite production regeneration applies when the same lens re-runs over new sources (`lifecycle-projection.md` § 4.2) is never applied to a preview.
- On failure a non-transient `data-refine_error {kind, message}` part is streamed and persisted instead of the apply part: `quota_exhausted` (message `generating the preview failed — send another message to retry`), `context_too_large` (message = the guard's text), or `apply_failed` (same generic message; covers preemption, provider errors, interruption and empty output). Deltas already streamed are not retracted; no `tool-input-available` follows. The message keeps its lens part; the client's preview keeps the last successful output; a commit of this lens is refused (§ 5).
- On success the `tool-apply_result {output}` part is appended to the **same** assistant message as the `tool-update_lens` part and the row rewritten.

The lens-writing model never sees `apply_result`, `suggest_name` or any `data-*` part: `Flatten` echoes only `tool-update_lens` (as `LensEcho`) back into the transcript (`context.md` § 7). The refinement role and the snapshot role are resolved separately and may be different models, though a parent `generate_with_model` override applies to both.

## 4. Window re-apply (reflections)

A send whose new messages contain no `user` message and a system message with a bounded `window` part re-executes the standing lens against that window (the last such part wins when several are new):

- The stream opens with `start {messageId: reapply-<unixnano>}`. The lens is the newest non-blank `tool-update_lens` on any assistant message. If none exists yet, the stream just finishes (the window and its re-resolved `pinned_ids` are already on the transcript and the first drafting turn will use them).
- Otherwise a fabricated assistant turn is streamed and persisted: a `data-window_reapply {start, end}` part, a **replayed** `update_lens` tool call (`tool-input-start` + `tool-input-available` with the same input, id `<original toolCallId>-reapply`) so the lens/output pairing invariant holds on the new message, then the apply leg (§ 3.1) with the transcript's latest `pinned_ids` (already re-resolved under the new window in step 1 of § 3) and the new window. The row's `generated_by_model` is empty.
- `Flatten` drops any message carrying `data-window_reapply`, so the lens-writer never sees these turns; `ExtractDraftedLensAndSpec` (§ 5) does see them, so the newest re-apply's output is what a commit pairs with the lens.
- Nothing entity-specific gates this path: a projection conversation that receives a bounded `window` part follows it too.

## 5. Commit (`POST …/{id}/refinements/{rid}/commit`)

1. Empty `{rid}` → 400 `refinement id required`; unknown → 404 `refinement not found`. `ExtractDraftedLensAndSpec` loads the transcript (error → 500 `failed to extract drafted lens`), takes the latest `pinned_ids`, `context_spec` and `window` (§ 3 step 11), and scans **assistant** messages newest-first for the first one whose `tool-update_lens` has a non-blank `input.lens`; the trimmed `tool-apply_result.input.output` on **that same message** is the output (the last part of each type on the message wins). Messages without a lens part are skipped; the seed turn (§ 2 step 5) and re-apply turns (§ 4) qualify like any other.
2. Refusals: no lens on the transcript → 400 `no drafted lens found in chat` (also the zero-turn seeded-session case); lens without output → 409 `the latest lens has no generated preview — send another message to regenerate` (a failed or still-running apply).
3. Parent id = the conversation's `projection_id`/`reflection_id`, else via the source snapshot's parent; neither → 400 `refinement missing parent target id`. A non-empty path `{id}` that disagrees with it → 400 `refinement parent target id mismatch`.
4. `engine.CommitRefinement` runs on a context detached from request cancellation (`context.WithoutCancel`), in one transaction; the transcript's window is passed and **ignored**. Any failure → 500 `failed to commit refinement`.
   - Projections only: if a source snapshot is recorded and is still `pending_review`, its `generation_trigger` is carried forward (an edit mid click-through keeps the speculative-chain mark; refining an approved snapshot does not).
   - The parent is loaded with `FindLive` (missing or soft-deleted → the transaction fails).
   - A `lens` row is created: `prompt` = the drafted lens, `parent_lens_id` = the parent's previous `current_lens_id` (if any), `created_from_projection_refinement_id` or `created_from_reflection_refinement_id` = `{rid}`.
   - Projections only: a `projection_snapshot` is appended with `lens_id` = the new lens, `output` = the previewed output, `context_spec` / `resolved_context` = the transcript's latest spec and pinned ids (zero-valued when the session never had a spec), `status = approved`, `generated_by_model` = `ResolveRoleFor(RoleSnapshot, parent.generate_with_model)` (resolution failure leaves it empty), `created_from_refinement_id = {rid}`, `generation_trigger` = the carried trigger (else the value marked on the context, i.e. none here), `generated_at = now` — then `ApproveSnapshot` assigns the next `approval_sequence_number`, sets `approved_at`, and discards the parent's other `pending_review` candidates (`lifecycle-projection.md` § 4.3). Reflections publish **nothing**: the previewed window was a sample.
   - The parent's `current_lens_id` is re-pointed to the new lens, `current_context_spec` set to the transcript's latest spec, and `status` set to `active` (a discover-proposed entity becomes active here).
5. After the transaction, for both entity kinds: `RequestWave()` when the hook is set (`reconcile.Register` sets it to `EnqueueWave` at boot, a no-op unless `KALAIDO_AUTO_WAVE` is set — `rotation.md` § 3, `boot-and-workers.md` § 2). Reflections only, before the response is written: `RunPendingWindows` spawns one background goroutine generating every window the series owes (`PendingWindows`: no approved output and no generation in flight) as approved at `Background` priority (`lifecycle-reflection.md` § 5); a window that already has an approved snapshot under the old lens is left as it is, reported `lensOutdated`.
6. Response `200 {snapshotId}` — the new snapshot id for projections, `""` for reflections.

The refinement conversation and its messages are not deleted, closed or marked by a commit; further turns on the same conversation continue from the same transcript, and a second commit creates another lens whose `parent_lens_id` is the first.

## 6. Active-lens resolution

`engine.resolveActiveLens(strat, rec)` loads the row named by the parent's `current_lens_id` from `lens` and returns its `prompt` together with the parent's own `current_context_spec` (decoded leniently; a missing or unreadable spec is the zero spec). A parent without a lens (never committed), or whose lens row cannot be loaded, yields an empty prompt; `GenerateSnapshot` refuses it with `ErrLensNotReady` before claiming (`lifecycle-projection.md` § 4.1; the generate routes report it as 409 with `…lens is still being prepared…`, and the wave and backfill skip it). Generation therefore executes the **parent's** `current_context_spec` — the spec the commit set, as later rewritten by anything that edits the parent's spec (the colour-delete scrub, `colours.md` § 6; a candidate edit, `lifecycle-projection.md` § 4.2) — and `SnapshotIsCurrent` compares the newest snapshot's `resolved_context` against that same spec resolved now. The snapshot's `lens_id` is taken from `current_lens_id` on the same record in the same call, so a lens and its scope are always read from one parent row.
