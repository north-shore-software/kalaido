## 1. Objects

- A **refinement conversation** is a row in `projection_refinement` or `reflection_refinement` (both: API create/update/delete disabled; list/view require an authenticated request): the parent relation (`projection_id` / `reflection_id`, cascade-deleted with the parent row), for projections the snapshot it is bound to (`projection_snapshot_id`, cascade-deleted with the snapshot — set at open from the request, re-pointed by the first materialised candidate (§ 3.5) and by a fold-in carry (§ 8)), the client's `external_conversation_id` (unique per collection), and `created`. `reflection_snapshot_id` exists on the reflection collection but is never written. Its messages are `chat_message` rows keyed by `projection_refinement_id` / `reflection_refinement_id` (cascade-deleted with the conversation), each storing one UI message (`{id, role, parts}`) in `content` and the producing model in `generated_by_model` (empty for user, system, seed, re-apply, regenerate-confirm and notice rows); `chat.LoadMessages` reads them in `created` order and silently skips rows whose `content` does not decode. `bookmarked` and `fragment_id` on `chat_message` are never set for refinement rows. Soft-deleting the parent (`lifecycle-projection.md` § 6, `lifecycle-reflection.md` § 8) leaves conversations and messages in place; only a hard delete of the row cascades (`schema.md` § 5).
- A **lens** is an immutable `lens` row: `prompt` (the standing instruction, plain text), `parent_lens_id` (the lens it replaced on the parent — audit lineage only, nothing reads back through it; set only by a commit), exactly one of `created_from_projection_refinement_id` / `created_from_reflection_refinement_id`, and `created`. The lens carries **no** context spec: the scope it applies to is the parent's `current_context_spec` (§ 6). The collection has both read and write disabled for API clients. Lens rows are written by `engine.CommitRefinement` (§ 5) and by `MaterializeCandidateIfNew` (§ 3.5, projections only — a preview lens stamped on a `pending_review` candidate, never installed on the parent), never updated, and never deleted — none of the lens row's own relations carries a cascade, so hard-deleting a refinement conversation, a parent entity or an older lens leaves lens rows in place; the relations pointing at `lens` (`current_lens_id` on the parent, `lens_id` on snapshots) carry none either.
- A lens is **stamped on snapshots** through `lens_id`: every `projection_snapshot` / `reflection_snapshot` written through `engine.applySnapshotSpec` records the lens that produced it (the parent's `current_lens_id` for a generation; the new lens for a commit; a preview lens for a materialised candidate). Readers compare a snapshot's `lens_id` with the parent's `current_lens_id`: `latestApprovedOutput` refuses to minimise against an approved output of another lens (the regeneration then runs from scratch, `lifecycle-projection.md` § 4.2), `settleApprovedInPlace` refuses to settle onto it, `SnapshotCurrency` reports `lens_changed` (`reconcile.md` § 2), `WindowsToGenerate` includes such a window in the set a reflection generate call covers, and `GET /api/reflections/{id}/windows` reports it `lensOutdated` (`lifecycle-reflection.md` § 5.1, § 9).
- The **drafted lens** during a session is not a row: `LatestLensPart` scans assistant messages newest-first and returns the first part that is either a `data-lens {lens}` part with non-blank `lens` (what a drafting turn writes, § 3 step 12) or a `tool-update_lens` part whose `input.lens` is non-blank (the seed turn, § 2 step 5, and re-apply replays, § 4; also transcripts written before the compiler existed). A `tool-update_lens` part carrying only `input.directive` — every live `update_lens` call — is **not** a lens. A lens row is created only at commit or at candidate materialisation.
- A refinement conversation has **no model of its own**: both model roles it uses resolve through the parent's `generate_with_model` (§ 3 step 8, § 3.1), read at each turn via `refinement.Parent` — the parent named by `projection_id` / `reflection_id`, else (rows that predate that column) the parent of the snapshot in `<type>_snapshot_id`; a soft-deleted parent resolves to none.
- For projections the conversation is **bound to one candidate**: `projection_snapshot_id` names the snapshot that receives `refine_candidate` proposals (§ 3.2), the hand-edit and triage notices (§ 7), and the regenerated draft (§ 3.5). A conversation opened without `snapshotId` has no binding until its first successful preview creates a candidate.

## 2. Opening a session (`POST …/{id}/refinements`)

Projections bind `api.CreateProjectionRefinementRequest` `{clientId, snapshotId?, contextSpec?}`; reflections bind `api.CreateReflectionRefinementRequest` `{clientId, window?, contextSpec?}` — a `snapshotId` sent to the reflection route is not a bound field and is dropped. Malformed body → 400 `invalid request body`; empty `clientId` → 400 `missing clientId`; empty path id → 400 `missing target id`. In one transaction:

1. The conversation row is created with `external_conversation_id = clientId`. **Projections:** the parent must exist and not be soft-deleted (`projections.FindLive`), `projection_id = {id}`; if `snapshotId` is given it is stored in `projection_snapshot_id` and the `projection_snapshot` row loaded — the snapshot's own parent and status are not checked. **Reflections:** `reflection_id = {id}`, the parent loaded via `reflections.FindLive`. Any failure inside the transaction (missing or soft-deleted parent, missing snapshot, unique-index violation on `clientId`) rolls back and is reported as 500 `failed to create refinement` — never 404.
2. The seeded context spec is chosen: the body's `contextSpec` if present; else (projections) the source snapshot's `context_spec` when it decodes; else (reflections) the parent's `current_context_spec` when it is non-empty, not the literal `null`, and decodes. A projection opened without `snapshotId` and without `contextSpec` is seeded with **no** spec.
3. Reflections only: the target window is the body's `window` if both `start` and `end` are set, else `reflections.DefaultRefinementWindow(parent, now)` (`windows.md` § 7) — nil for an unscheduled reflection. Its `id` is always recomputed server-side (`reflections.WindowID`, `windows.md` § 4); a client-supplied `id` is discarded. Projections never get a window.
4. If a spec or a window exists, one **system** message (id `ctx-<unixnano>`) is persisted carrying, in order: a `context_spec` part (when a spec exists), a `window` part `{id,start,end}` (reflections, when a window exists), and — when a spec exists — a `pinned_ids` part resolved now by `llmcontext.ResolveSpecToIDs` under that window (nil for projections; `context.md` § 2–3, § 5). A resolution error silently drops the `pinned_ids` part; the spec and window parts are still persisted. The message is persisted with an empty `generated_by_model`.
5. **Seed turn** (`SeedLensTurn`, both entity kinds): when the parent's `current_lens_id` names a `lens` row whose `prompt` is non-blank after trimming, an **assistant** message (id `seed-<unixnano>`) is persisted carrying a `data-lens_seed {}` marker, a `tool-update_lens` part (`toolCallId` `seed-lens-<n>`, `input {lens}` — the trimmed prompt), and — reflections only, when a window was chosen **and** that window has an approved `reflection_snapshot` (newest by `approval_sequence_number`) with non-blank `output` — a `tool-apply_result` part (`seed-apply-<n>`, `input {output}`). Projections are seeded with a nil window, so they never receive the apply part even when the source snapshot is approved. An unscheduled reflection (nil window) never receives the apply part either. A parent with no lens, or a lens row that fails to load, gets no seed turn.

Response `201 {refinementId, messages}` — the seeded messages exactly as persisted (`messages` omitted when none were seeded). The client must render these ids rather than reconstruct them, or the next turn persists duplicates (`chat.ExtractNewMessages` dedupes by id only).

## 3. A turn (`POST …/{id}/refinements/{rid}/chat`)

`handleRefinementChat` (bound per collection by `HandleProjectionRefinementChat` / `HandleReflectionRefinementChat`) rejects an empty `{id}` or `{rid}` with 400 `<type> id and refinement id required`, loads `{rid}` from the route's refinement collection (404 `<type> refinement not found`), and requires `refinement.Parent` to resolve to a live parent whose id equals `{id}` (else 400 `refinement does not belong to specified <type>` — also the answer for a soft-deleted parent). It binds `api.RefinementChatRequest` = `api.ChatRequest` `{id, messages}` (400 `invalid chat request body`); an empty `id` is filled from the conversation's `external_conversation_id`, but nothing downstream reads `id` — `messages` is the whole contract. `HandleChatForRefinement` then runs `refinement.StreamTurn`:

1. Stored messages are loaded (a load error is ignored and treated as an empty transcript); incoming messages whose ids are unknown are the new ones. `chat.ResolveContextSpecs` appends a `pinned_ids` part to each new **system** message carrying a `context_spec` and/or `window` part, resolved against the cumulative (spec, window) pair — the pair starts from the transcript's latest values (`llmcontext.LatestPinnedAndSpec`) and each new system message updates it in order; a `window` part with empty bounds clears the window; a resolution error leaves the message without a `pinned_ids` part. New messages are persisted with an empty `generated_by_model` **before any dispatch below** — a declined proposal, a cancelled regenerate and a client notice are all on the transcript whatever leg runs; a persist failure is logged and the turn continues.
2. The parent is resolved (§ 1) and its `generate_with_model` read; with no parent the override is empty and role defaults apply.
3. **Dispatch**, in this order, each test looking only at the new messages and each returning nil the moment a `user` message is seen:
   - `ReapplyWindow`: a system message with a bounded `window` part → the window re-apply leg (§ 4).
   - `IsRegenerateConfirmed`: a system message with a `data-regenerate_confirm` part → the regenerate-confirmed leg (§ 3.4).
   - `IsRegenerateCancelled`: a `data-regenerate_cancel` part → the stream opens with `start {messageId: regen-cancel-<unixnano>}` and immediately `finish`es; no row is written beyond the notice persisted in step 1.
   - `IsContextCancelled`: a `data-context_cancel` part → the same empty stream under `ctx-cancel-<unixnano>`.
   - Anything else — a user message, a `context_spec`-only send, a `data-context_confirm` send (the accepting message also carries the new `context_spec`, so it is an ordinary drafting turn under the changed context) — is a **drafting turn** against the transcript as it stands. A send whose new messages carry several of these parts takes the first leg in the list.
4. **Standing lens** (`hasLens`, `currentLens`): the transcript's `LatestLensPart` (§ 1); when none, the parent's `current_lens_id` → `lens.prompt` (trimmed, non-blank); when the parent has no `current_lens_id`, the parent's own `prompt` field (trimmed, non-blank). A parent whose `current_lens_id` names an unloadable or blank lens yields no lens — the `prompt` fallback is only reached when `current_lens_id` is empty.
5. The transcript is hydrated by `chat.HydrateDeltaHistory`: every system message renders as one system turn of `WindowNotice(start, end)` (when it carries a bounded `window` part) followed by the context delta between the previous `pinned_ids` and this message's, rendered by one `llmcontext.Hydrator` built from the transcript's final `pinned_ids` and the final spec's mode (`context.md` § 4), followed — separated by blank lines — by the rendered text of every notice part it carries (§ 7); a system message that yields no text (a spec part whose resolution failed and no notice) is dropped. Non-system messages go through `llmcontext.Flatten` (`context.md` § 7): text parts with mentions expanded; `data-lens` and `tool-update_lens` parts with a non-empty lens echoed as `LensEcho`; `data-context_confirmation` echoed as `ContextProposalEcho(reason)`; a message carrying `data-window_reapply` dropped whole; everything else (`apply_result`, `suggest_name`, `refine_candidate`, `regenerate_from_lens`, `update_context` calls, every other `data-*`) invisible.
6. `prompts.RefinementPrompt(hasLens)` is prepended: `RefinementRevisionPrompt` when a standing lens exists, else `RefinementCreationPrompt` (`prompts.md` § 2). Because the system prompt is always present, the `400 messages required` branch that follows is unreachable.
7. Model = `llm.ResolveRoleFor(RoleRefinement, parent.generate_with_model)` — a non-blank override wins for this role too; no model → 500 `no model configured for refinement`. `llm.CheckPromptFits` over the hydrated transcript's characters refuses with 422 and the guard's text (`context.md` § 6) before the call.
8. **Tools advertised**: with a standing lens `update_lens`, `regenerate_from_lens`, `refine_candidate`, `update_context`; without one the same plus `suggest_name` (order as declared: `update_lens`, `regenerate_from_lens`, `suggest_name`, `refine_candidate`, `update_context`). Schemas (§ 3.2–3.4 for semantics): `update_lens {directive}` (required); `regenerate_from_lens {}`; `suggest_name {name}` (required); `refine_candidate {target, replacement}` (both required); `update_context {whole_scope: "full"|"pins", pin_fragment_ids[], unpin_fragment_ids[], pin_fragment_types[], unpin_fragment_types[], reason}` (`reason` required). Nothing entity-specific gates the set: a reflection conversation is offered `refine_candidate` and `regenerate_from_lens` too.
9. `usage.Stream` at `RoleRefinement` (no per-role generation options; `Interactive` queue priority — the request context carries no override) with those tools; `llm-queue-quota.md` § 1. Quota exhaustion → 402 envelope; a classified provider error → its envelope (`llm-queue-quota.md` § 6); any other error → 500 `llm stream failed`. All of these occur before the SSE stream opens; once it is open the handler returns nil whatever happens.
10. The turn streams as an AI-SDK UI-message stream (`chat.BeginSSE`: `Content-Type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`) opened with `start {messageId: txt-<unixnano>}`; text as `text-start` / `text-delta` / `text-end` under that id, transient `data-inference_rate` parts at most every 250 ms and once at the end, model tool calls as `tool-input-start` / `tool-input-delta` / `tool-input-available` with `dynamic: true` (`explore.md` § 6). Each tool call is persisted as a `tool-<name>` part **as it arrives** through `chat.TurnWriter` — the assistant `chat_message` row is created on the first write and rewritten in place after that — then the final text part plus all tool parts are written. The row's `generated_by_model` is the refinement model. A turn that produces neither text nor a tool call writes no row.
11. **Name-only continuation** (`StreamNameOnlyContinuation`): when the turn has no text, at least one tool call, and none of: an `update_lens` call with a non-empty `directive`, a `refine_candidate` call with non-empty `target` and `replacement`, a `regenerate_from_lens` call, an `update_context` call that decodes — a second model call is made on the same open stream: the hydrated transcript plus an assistant echo of the tool names called (`DiscoverEchoToolCalls`, trimmed) and a user message `NameRecordedContinue` (`prompts.md` § 2), with **no tools** advertised, guarded by `CheckPromptFits`. Its text streams under id `<textId>-c1` and is appended to the same persisted message as a `text` part; tool calls in the continuation are dropped. A guard refusal, a call error or an empty reply is logged and the turn ends with only the tool parts; no error reaches the client. In practice the condition is met by a `suggest_name`-only turn, or by calls whose arguments fail the checks above (an `update_lens` with an empty `directive`).
12. **`refine_candidate`** calls are executed next (§ 3.2), every one of them in call order, each streaming a `data-refine_result` part and persisting a system notice.
13. **`update_lens`**: the last call with a non-empty `directive` (`LatestUpdateLensArg`) is compiled (§ 3.3) into a full lens by a second model call. On success `currentLens` becomes the compiled text, a non-transient `data-lens {lens}` part is streamed and appended to the message, then the **lint**: `LensCountPin` tries four case-insensitive patterns in order — `<N> in total`, `total of <N>`, `<N> total`, `all <N>` (`<N>` = digits or the number words one–twenty) — and returns the first match; a hit streams and persists a non-transient `data-refine_lint {match}` part on the same message. Nothing is redrafted. Per-item counts (`exactly two bullet points`) do not match. A compile failure is logged; no part and no error reach the client, `currentLens` keeps its prior value, and the turn continues as if no lens had been drafted.
14. **`update_context`**: when the turn carries a decodable `update_context` call (the last one wins), the proposed spec is computed (§ 3.4), a non-transient `data-context_confirmation {spec, reason}` part is streamed and appended, and the turn ends with `finish` + `[DONE]` — **no apply leg**, even when a lens was compiled on the same turn (that lens is on the transcript and will be applied by a later regenerate).
15. **Apply decision**: the apply leg (§ 3.1) runs when `currentLens` is non-empty **and** either no standing lens existed at step 4 (the first lens of a creation session applies immediately) or the turn called `regenerate_from_lens`. A revision-session turn that only compiles a lens does **not** apply it — the candidate keeps its draft until a regenerate. Before applying on a `regenerate_from_lens` call the regenerate gate (§ 3.4) may end the turn instead. The apply runs against the transcript's latest `pinned_ids`, `context_spec` and `window` (`LatestPinnedAndSpec`: newest system part of each type, the window read even from an unbounded part as nil) with the turn's `suggest_name` argument (first call with a non-blank `name`, trimmed) carried along; then `finish` + `[DONE]`.

Nothing in code counts questions per turn, enforces the interview before the first lens, enforces "update_context alone on its turn", forbids `update_lens` and `refine_candidate` on one turn, or checks `name` length — those are prompt instructions only (`prompts.md` § 2).

### 3.1 The apply leg

`StreamApplyLeg` executes a lens through `refinement.ApplyDraftLens`:

- Source block = `llmcontext.HydrateIDsToText` of the pinned ids — always the **full** (flat) rendering of fragments and upstream snapshots (`context.md` § 4), whatever `wholeScope` mode the spec selects; empty when nothing is pinned (the lens is then applied to no sources).
- Model = `ResolveRoleFor(RoleSnapshot, parent.generate_with_model)`; no model → `data-refine_error {kind: apply_failed, message: "no model configured for generation"}` before any tool event.
- A fabricated tool call named `apply_result` (`toolCallId` `apply-<unixnano>`) is streamed: `tool-input-start` **before** the model call, then a `tool-input-delta` of `{"output":"` and one JSON-string-escaped delta (`JSONStringChunk`) per text chunk as the model produces them, then `"}` and a `tool-input-available` carrying the authoritative trimmed output.
- Prompt = `ApplyPrompt(lens, sourceBlock, windowStart, windowEnd)` as a single user message (`prompts.md` § 2; `engine.WindowBounds` gives zero bounds for a nil window), at `RoleSnapshot` options (temperature 0) and `Interactive` queue priority, via `usage.GenerateStreamMsgs` — no tools. `CheckPromptFits` is applied to the prompt's byte length. A preempted call (`queue.ErrPreempted`), an interrupted stream (the request context cancelled mid-stream), and an empty (whitespace-only) output are all errors.
- **Always from scratch:** the minimal-diff rewrite production regeneration applies when the same lens re-runs over new sources (`lifecycle-projection.md` § 4.2) is never applied to a preview. The diff against the previous draft happens afterwards, at materialisation (§ 3.5), not in the model call.
- On failure a non-transient `data-refine_error {kind, message}` part is streamed and persisted instead of the apply part: `quota_exhausted` (message `generating the preview failed — send another message to retry`), `context_too_large` (message = the guard's text), or `apply_failed` (same generic message; covers preemption, provider errors, interruption and empty output). Deltas already streamed are not retracted; no `tool-input-available` follows. The message keeps its lens part; the client's preview keeps the last successful output; nothing is materialised; a commit of this lens is refused unless the bound snapshot supplies an output (§ 5).
- On success the `tool-apply_result {output}` part is appended to the **same** assistant message and the row rewritten, then `MaterializeCandidateIfNew` (§ 3.5) runs; its result and error are discarded.

The lens-writing model never sees `apply_result`, `suggest_name`, `refine_candidate`, `regenerate_from_lens` or `update_context` calls, nor any `data-*` part other than `data-lens` and `data-context_confirmation` (§ 3 step 5). The refinement role and the snapshot role are resolved separately and may be different models, though a parent `generate_with_model` override applies to both.

### 3.2 `refine_candidate` (projections with a bound candidate)

For every `refine_candidate` call whose arguments decode (in call order, after the continuation), when the conversation has both `projection_id` and `projection_snapshot_id` — a reflection conversation or an unbound projection conversation silently does nothing, and the call is persisted as an inert `tool-refine_candidate` part:

1. The target edit is chosen by `ResolveNoticeEditID`: the newest `data-refine_target` system notice on the transcript (§ 7) that carries an `editId` is followed through the bound snapshot's `edits` — if that edit is `proposed` it is the target; if it is `superseded` its `supersededBy` chain is walked (cycle-guarded) until a `proposed` edit is found; an `approved`/`rejected` edit, an unknown id, or a chain ending elsewhere yields no target. The notice's `editId` is matched against the candidate's current edits, so a notice about an edit a regeneration has since superseded resolves to nothing.
2. With a target edit: `projections.ReviseProposalEdit(projection, snapshot, editId, replacement)` — the old proposal becomes `superseded` (`supersededBy` = the new id), a new `proposed` edit of type `refinement` with the old `contentBefore`, the trimmed `replacement` as `contentAfter` and the old `blockIndex` is appended, and the old marker in `output_draft` is replaced by the new one. Without one, and with a non-empty `target`: `projections.ProposeRefineEdit(projection, snapshot, target, replacement)` — the trimmed `target` must match a run of one or more markdown blocks of the draft (whitespace-normalised) or, failing that, a whitespace-tolerant regex over the target's words inside one block; the matched passage is replaced in `output_draft` by an edit marker (`<<<edit:<id>>>>`) and a `proposed` edit of type `refinement` (`contentBefore` = the passage, `contentAfter` = the replacement, `blockIndex` = the block) is appended. Both require the candidate to be `pending_review` and to belong to the projection, refuse a passage already under a marker, and refuse a replacement equal to the target / to the old `contentAfter`. With neither a target edit nor a `target` argument the result is `ErrTargetNotFound`. The edit-row mechanics and their errors are `lifecycle-projection.md` § 4.4.
3. The outcome is streamed as a non-transient `data-refine_result` part — `{ok: true, editId, sequence}` or `{ok: false, error}` — appended to the assistant message, and a **system** notice (id `refine-proposal-<unixnano>`, part `data-refine_proposal_result` with `text` = `RefineProposalSuccessNotice(sequence)` / `RefineProposalFailureNotice(error)` and the same data) is persisted so the next turn's model sees it (§ 7). A failed proposal is logged; no HTTP error results.

`refine_candidate` never touches the lens and never triggers the apply leg; a turn that also called `update_lens` compiles the lens as well.

### 3.3 The lens compiler (`CompileLens`)

An `update_lens` call carries a `directive`, not a lens. `CompileLens` makes one further model call at `RoleRefinement` with the same model as the drafting turn, through `usage.GenerateOnceMsgs` (`Interactive` priority, no tools, no guard — `CheckPromptFits` is not applied to this prompt): system message `LensCompilerSystemPrompt` (`prompts.md` § 2), then every **non-system** message of the hydrated transcript (the context blocks and notices are dropped; user turns, lens echoes and proposal echoes remain), then one user message: `Current standing lens:` in `<<< >>>` fences when a standing lens exists, `Directive for this update:` + the directive when non-empty, and `Please write the complete standing lens instruction now.` The reply, trimmed, is the new lens. A preempted call, an interrupted stream or any provider error is the failure case of § 3 step 13; an empty reply is accepted as an empty lens (the `data-lens` part is written with `lens: ""`, which `LatestLensPart` then ignores, and no apply runs).

### 3.4 `update_context` and `regenerate_from_lens`

**`update_context`** never changes the context. `ApplyContextOps` computes the spec that would result from the transcript's latest `context_spec`: `whole_scope` `"full"` sets `wholeScope = full`, `"pins"` clears it (any other value, including omitted, leaves it), and `fragmentIds` / `fragmentTypes` are rebuilt as the current list plus the pins, in order, with empties and duplicates dropped and every id in the matching unpin list removed (an id both pinned and unpinned ends unpinned); `colourIds`, `sourceProjectionIds`, `sourceReflectionIds` and a `summaries` mode pass through untouched. The proposal goes to the client as `data-context_confirmation {spec, reason}` (`reason` trimmed) and the turn ends (§ 3 step 14). The client answers on a later send: a system message carrying `data-context_confirm` **and** the new `context_spec` part (resolved to `pinned_ids` in step 1 like any spec change, then an ordinary drafting turn), or `data-context_cancel` (an empty stream, step 3). `IsContextConfirmed` exists but no dispatch branch calls it. No server state records an open proposal; nothing prevents a second proposal before the first is answered.

**`regenerate_from_lens`** carries no arguments. On a turn that called it (and has a lens to apply), the bound candidate's `edits` are read: when at least one edit is `approved`, a non-transient `data-regenerate_confirmation {affectedEdits: [...]}` part listing those edits is streamed and appended and the turn ends without applying. An unbound conversation or one whose snapshot fails to load has no approved edits and applies straight away. The client answers with a system message carrying `data-regenerate_confirm` (→ `StreamRegenerateConfirmed`: the stream opens under `regen-confirm-<unixnano>`; the lens is the transcript's `LatestLensPart`, else the parent's lens / `prompt` field as in § 3 step 4; with none the stream just finishes; otherwise an assistant row with a single `data-regenerate_confirm` part (no data) and empty `generated_by_model` is written and the apply leg (§ 3.1) runs with the transcript's latest `pinned_ids`, spec and window and no suggested name) or `data-regenerate_cancel` (an empty stream; the cancel notice is what the next turn's model reads, § 7). The confirmed leg does not re-check the approved edits.

### 3.5 Materialising the candidate (`MaterializeCandidateIfNew`)

Runs after every successful apply (drafting, re-apply and regenerate-confirmed legs alike). Reflection conversations and projection conversations without `projection_id` return immediately — a reflection preview is never stored anywhere but the transcript. Otherwise:

- **Bound to a `pending_review` candidate** (`projection_snapshot_id` names a snapshot with `status = pending_review`): the candidate is rewritten in place, outside any transaction. The baseline `prev` is `engine.ResolveDraftBaseline(output_draft, edits)` — the current draft with every unresolved marker replaced by its edit's `contentBefore` (an accepted or rejected edit is already inlined; an undecided proposal shows its original passage) — or, when that is blank, the projection's newest approved snapshot's `output`. With a non-blank baseline, `engine.DiffAndMarkBlocks(prev, output, regeneration)` produces the new `output_draft` (equal blocks kept, each run of changed blocks replaced by a marker) and one `proposed` edit of type `regeneration` per changed run; with none the draft is the raw output and no edits. Prior edits are then reconciled: an `approved` edit whose `inlinedText` still occurs verbatim in the new draft is **kept** (its `blockIndex` re-anchored by `BlockRunIndex`, `updatedAt` = now); every other prior edit becomes `superseded` with `undoReason = regenerated` and `undoable = false` (those not already superseded are listed as newly superseded); new edits are numbered from the prior maximum `sequence` + 1. A `lens` row is created (`prompt` = the applied lens, `created_from_projection_refinement_id` = `{rid}`, no `parent_lens_id`) and, when its save succeeds, stamped as the candidate's `lens_id` (a failed save leaves the old `lens_id` and is not logged). The candidate's `output_draft`, `output_raw` (= the raw output), `edits`, `context_spec`, `resolved_context` and `generated_by_model` (= the apply model) are set and saved (a save failure is logged and returned — and discarded by the caller). `output`, `status`, `generation_trigger` and `generated_at` are untouched. When any edit was superseded or kept, a **system** notice (id `superseded-regen-<unixnano>`, part `data-regenerate_superseded` with `text` = `RegenerateSupersededNotice(superseded, kept)` and data `{sequences, kept}`) is persisted (§ 7). A bound snapshot that is not `pending_review` (approved, discarded, generating, or missing) makes the call a **no-op**: the preview lives only on the transcript, and no new candidate is created.
- **Unbound** (`projection_snapshot_id` empty): in one transaction the projection is loaded (`FindRecordById` — soft deletion is not checked), a `lens` row is created as above, a `projection_snapshot` is appended with `lens_id` = that lens, `output = ""`, `output_draft` = `output_raw` = the output, `edits = []`, `context_spec` / `resolved_context` = the transcript's latest spec and pinned ids, `status = pending_review`, `generated_by_model` = the apply model, `created_from_refinement_id = {rid}`, `generation_trigger` from the context (none here), `generated_at = now` — outside the claim machinery, so an existing pending candidate or a live `generating` claim of the same projection is neither discarded nor joined (`lifecycle-projection.md` § 4.1). The conversation's `projection_snapshot_id` is set to the new row. When the turn carried a `suggest_name` and the projection's `name` is empty or starts with `Untitled`, `name` is set to it. A transaction failure is logged and discarded.

## 4. Window re-apply (reflections)

A send whose new messages contain no `user` message and a system message with a bounded `window` part re-executes the standing lens against that window (`StreamWindowReapply`; the last such part wins when several are new):

- The stream opens with `start {messageId: reapply-<unixnano>}`. The lens is the transcript's `LatestLensPart` (§ 1) — the parent's stored lens is **not** consulted here. If none exists yet, the stream just finishes (the window and its re-resolved `pinned_ids` are already on the transcript and the first drafting turn will use them).
- Otherwise a fabricated assistant turn is streamed and persisted: a `data-window_reapply {start, end}` part, then a replay of the lens in the same shape it was found — a `data-lens {lens}` part when the newest lens is a compiled one, or an `update_lens` tool call (`tool-input-start` + `tool-input-available` with the original `input`, id `<original toolCallId>-reapply`) when it is a seed or legacy tool part — so the lens/output pairing invariant holds on the new message, then the apply leg (§ 3.1) with the transcript's latest `pinned_ids` and spec (already re-resolved under the new window in step 1 of § 3) and the new window, no suggested name. The row's `generated_by_model` is empty. The lint (§ 3 step 13) does not run on a re-apply; materialisation (§ 3.5) does, and is a no-op for reflections.
- `Flatten` drops any message carrying `data-window_reapply`, so the lens-writer never sees these turns; `ExtractDraftedLensAndSpec` (§ 5) does see them, so the newest re-apply's output is what a commit pairs with the lens.
- Nothing entity-specific gates this path: a projection conversation that receives a bounded `window` part follows it too, and its successful apply then materialises a candidate (§ 3.5).

## 5. Commit (`POST …/{id}/refinements/{rid}/commit`)

1. Empty `{rid}` → 400 `refinement id required`; unknown in the route's collection → 404 `refinement not found`. `refinement.Commit` runs `ExtractDraftedLensAndSpec`: it loads the transcript (error → 500 `failed to commit refinement`), takes the latest `pinned_ids`, `context_spec` and `window` (§ 3 step 15), and scans **assistant** messages newest-first for the first one carrying a lens — a `data-lens` part with non-blank `lens`, or a `tool-update_lens` part whose `input.lens` decodes (its trimmed value, possibly empty, overwrites a `data-lens` seen earlier on the same message); the trimmed `tool-apply_result.input.output` on **that same message** is the output (the last part of each type on the message wins). Messages without a lens part are skipped; the seed turn (§ 2 step 5), re-apply turns (§ 4) and regenerate-confirmed rows (§ 3.4, which carry no lens part and are therefore skipped) are scanned like any other — a seeded reflection session whose window had an approved output can be committed with zero turns. A transcript with no lens logs a warning listing every `role/partType` scanned.
2. Refusals: no lens on the transcript → 400 `no drafted lens found in chat`. **Output fallback:** when the paired output is empty and the conversation is bound to a snapshot, that snapshot's `output_draft` (trimmed; **including any unresolved edit markers**) else its `output` is used — so a revision session whose lens was compiled but never applied commits the bound candidate's current draft. Still no output → 409 `the latest lens has no generated preview — send another message to regenerate` (a failed or still-running apply on an unbound session).
3. Parent id = the conversation's `projection_id`/`reflection_id`, else via the source snapshot's parent (§ 1); neither → 400 `refinement missing parent target id`. A non-empty path `{id}` that disagrees with it → 400 `refinement parent target id mismatch`.
4. `engine.CommitRefinement` runs on a context detached from request cancellation (`context.WithoutCancel`), in one transaction; the transcript's window is not passed. Any failure → 500 `failed to commit refinement`.
   - Projections only (`InheritsCandidateTrigger`): if a bound snapshot is recorded and is still `pending_review`, its `generation_trigger` is carried forward (an edit mid click-through keeps the speculative-chain mark; refining an approved snapshot does not); a bound snapshot that fails to load is ignored.
   - The parent is loaded with `engine.FindLive` (missing or soft-deleted → the transaction fails).
   - A `lens` row is created: `prompt` = the drafted lens, `parent_lens_id` = the parent's previous `current_lens_id` (if any), `created_from_projection_refinement_id` or `created_from_reflection_refinement_id` = `{rid}`.
   - **Projections bound to a `pending_review` candidate** (the common case after § 3.5): that candidate is approved in place rather than a new snapshot appended. Its `output` is set to the trimmed `output_draft`, else its trimmed `output`, else the trimmed transcript output; a draft that still contains an edit marker fails the transaction (`ErrNotApprovable: candidate has unresolved edits` → 500). `lens_id` = the new lens, `context_spec` / `resolved_context` = the transcript's latest spec and pinned ids; `generated_by_model`, `generation_trigger`, `created_from_refinement_id`, `edits` and `output_draft` are left as they were (the carried trigger computed above is not written on this path). `engine.ApproveSnapshot` then assigns the next `approval_sequence_number`, sets `approved_at`, `status = approved`, and discards the parent's other `pending_review` candidates (`lifecycle-projection.md` § 4.3). The parent is updated as below and the transaction ends here.
   - Otherwise `strat.CommitRefinementSnapshot`. **Projections** (unbound, or bound to a non-pending snapshot): a `projection_snapshot` is appended with `lens_id` = the new lens, `output = ""`, `output_draft` = `output_raw` = the committed output, `edits = []`, `context_spec` / `resolved_context` = the transcript's latest spec and pinned ids (zero-valued when the session never had a spec), `status = pending_review`, `generated_by_model` = `ResolveRoleFor(RoleSnapshot, parent.generate_with_model)` (a resolution failure leaves it empty), `created_from_refinement_id = {rid}`, `generation_trigger` = the carried trigger, `generated_at = now` — then `ApproveSnapshot` promotes it (copying `output_draft` into `output`, stamping the sequence and `approved_at`, `status = approved`, discarding other pending candidates). **Reflections** publish **nothing** and return an empty id: the previewed window was a sample.
   - The parent's `current_lens_id` is re-pointed to the new lens, `current_context_spec` set to the transcript's latest spec, and `status` set to `active` (a discover-proposed entity becomes active here).
5. After the transaction, for both entity kinds: `deps.Reconcile.EnqueueWave()` — a no-op unless `KALAIDO_AUTO_WAVE` is set (`reconcile.md` § 4). Reflections only, before the response is written: `reflections.RunPendingWindows(deps.Runner, …)` starts one detached goroutine (`boot-and-workers.md` § 3) generating every window the series owes (`PendingWindows`: no approved output and no generation in flight, `windows.md` § 3) as approved at `Background` queue priority (`lifecycle-reflection.md` § 5.3); a window that already has an approved snapshot under the old lens is not regenerated by this pass and is reported `lensOutdated` (`lifecycle-reflection.md` § 9).
6. Response `200 {snapshotId}` — the approved snapshot's id for projections (the bound candidate's own id on the in-place path), `""` for reflections.

The refinement conversation and its messages are not deleted, closed or marked by a commit, and `projection_snapshot_id` keeps pointing at the now-approved snapshot; further turns on the same conversation continue from the same transcript (a further `refine_candidate` then fails with `candidate is not pending review`, and a further apply is a no-op for materialisation), and a second commit creates another lens whose `parent_lens_id` is the first.

## 6. Active-lens resolution

`engine.resolveActiveLens(strat, rec)` loads the row named by the parent's `current_lens_id` from `lens` and returns its `prompt` together with the parent's own `current_context_spec` (decoded leniently; a missing or unreadable spec is the zero spec). A parent without a lens (never committed), or whose lens row cannot be loaded, yields an empty prompt; `engine.GenerateSnapshot` refuses a blank (trimmed) prompt with `ErrLensNotReady` before claiming (`lifecycle-projection.md` § 4.1; the generate routes report it as 409 `This <type>'s lens is still being prepared — try again in a moment.`, the reconcile wave skips the entity, and the pending-window pass logs `no lens yet`). The parent's `prompt` field, which a refinement turn falls back to for its own standing lens (§ 3 step 4), is **not** consulted by generation. Generation therefore executes the **parent's** `current_context_spec` — the spec the commit set, as later rewritten by anything that edits the parent's spec (the colour-delete and upstream-delete scrubs through `engine.ScrubContextSpecs`, `colours.md` § 6; a hand edit that creates an edit fragment, `lifecycle-projection.md` § 4.4) — and `SnapshotCurrency` compares the newest pending-or-approved snapshot's `lens_id` against `current_lens_id`, its `generated_by_model` against the role resolution now (when the snapshot carries one), and its `resolved_context` against that same spec resolved now (`context.md` § 5). A candidate materialised by a preview (§ 3.5) carries a preview lens that is never the parent's `current_lens_id`, so it reads as `lens_changed` until the session commits. The snapshot's `lens_id` is taken from `current_lens_id` on the same record in the same call, so a lens and its scope are always read from one parent row.

## 7. Notices on the transcript

Besides the context parts (`context_spec`, `window`, `pinned_ids`), system messages on a refinement transcript carry notice parts. Each is rendered for the model by `HydrateDeltaHistory` (§ 3 step 5) as its `text` when the part has one, else from its `data`; the rendered strings are `prompts.md` § 2.

| Part | Written by | Data | Rendered as |
|---|---|---|---|
| `data-hand_edit` | `projections.RecordHandEditNotice`, inside the hand-edit transaction (`lifecycle-projection.md` § 4.4), onto the newest `projection_refinement` whose `projection_id` and `projection_snapshot_id` match the edited candidate; silently skipped when none is bound. Message id `hand-edit-<editId>` | `{editId, sequence, before, after}` | `HandEditNotice(before, after)` |
| `data-edit_triage` | `projections.RecordEditTriageNotice`, when an edit's status changes (`lifecycle-projection.md` § 4.4), same conversation lookup. Message id `triage-edit-<editId>-<status>` | `{editId, sequence, status}` | `EditTriageNotice(sequence, status)` |
| `data-refine_target` | the client, on the send that targets a passage; no server writer | `{passage, editId?}` | `RefineTargetNotice(passage)`; `editId` steers `refine_candidate` (§ 3.2) |
| `data-refine_proposal_result` | § 3.2, message id `refine-proposal-<unixnano>` | `{ok, editId?, sequence?, error?}` | `RefineProposalSuccessNotice` / `RefineProposalFailureNotice` |
| `data-regenerate_superseded` | § 3.5, message id `superseded-regen-<unixnano>` | `{sequences, kept}` (older rows: `{startSequence, endSequence}`, expanded to the range) | `RegenerateSupersededNotice(sequences, kept)`; skipped when both lists are empty |
| `data-regenerate_confirm` | the client, on the confirming send (§ 3.4) | — | not rendered (no case in the hydrator); the assistant-side marker of the same type (§ 3.4) is invisible to `Flatten` too |
| `data-regenerate_cancel` | the client | — | `RegenerateCancelledNotice()` |
| `data-context_confirm` | the client, with the new `context_spec` | — | `ContextConfirmedNotice()` |
| `data-context_cancel` | the client | — | `ContextCancelledNotice()` |

A system message carrying only an unrecognised part type yields no text and is dropped from the hydrated transcript; a message ID the client reuses is deduped away by `ExtractNewMessages`. Notices are persisted with an empty `generated_by_model` and are never removed.

## 8. Carry-over between candidates

`refinement.CarryOpenRefinementToCandidate(projection, candidate)` is called by the projection generate route after a successful generation when the request carried both `foldIn` and `preview` (`lifecycle-projection.md` § 4.1); its error is logged as a warning and never reaches the client. It re-points one conversation onto the new candidate:

1. The candidate must be `pending_review` and belong to the projection (a fold-in that settled the approved row in place produces neither, → no-op, `""`).
2. The projection's newest approved snapshot other than the candidate (by `approval_sequence_number`) is located; none → no-op.
3. The newest `projection_refinement` (by `created`) whose `projection_snapshot_id` is that approved snapshot is located; none → no-op. Only one conversation is ever carried.
4. Its transcript is loaded (a load error is returned); when `LatestLensPart` finds a drafted lens (§ 1) the conversation is left on the approved snapshot (logged `fold-in: refinement drafted a lens; leaving it on the approved snapshot`) — a lens-drafting session commits through § 5, and that path would approve the candidate it is bound to.
5. Otherwise `projection_snapshot_id` is set to the candidate and saved. The conversation's messages are untouched; subsequent `refine_candidate` proposals, notices (§ 7) and previews (§ 3.5) land on the new candidate.

No other path moves a conversation between snapshots: a plain regeneration, a wave candidate or an approve leaves every conversation bound where it was, so a conversation bound to a discarded candidate keeps proposing against it (and failing with `candidate is not pending review`).
