## 1. Objects

- A **refinement conversation** is a row in `projection_refinement` or `reflection_refinement` (both: API create/update/delete disabled; list/view require an authenticated request): the parent relation (`projection_id` / `reflection_id`, cascade-deleted with the parent row), for projections optionally the snapshot it was opened from (`projection_snapshot_id`, cascade-deleted with the snapshot), the client's `external_conversation_id` (unique per collection), and `created`. `reflection_snapshot_id` exists on the reflection collection but is never written. Its messages are `chat_message` rows keyed by `projection_refinement_id` / `reflection_refinement_id` (cascade-deleted with the conversation), each storing one UI message (`{id, role, parts}`) in `content` and the producing model in `generated_by_model` (empty for user, system, seed and re-apply rows); `chat.LoadMessages` reads them in `created` order and silently skips rows whose `content` does not decode. Soft-deleting the parent (`lifecycle-projection.md` § 6, `lifecycle-reflection.md` § 8) leaves conversations and messages in place; only a hard delete of the row cascades (`schema.md` § 5).
- A **lens** is an immutable `lens` row: `prompt` (the standing instruction, plain text), `parent_lens_id` (the lens it replaced on the parent — audit lineage only, nothing reads back through it), exactly one of `created_from_projection_refinement_id` / `created_from_reflection_refinement_id`, and `created`. The lens carries **no** context spec: the scope it applies to is the parent's `current_context_spec` (§ 6). The collection has both read and write disabled for API clients. Lens rows are written only by `engine.CommitRefinement` (§ 5), never updated, and never deleted — none of the lens row's own relations carries a cascade, so hard-deleting a refinement conversation, a parent entity or an older lens leaves lens rows in place; the relations pointing at `lens` (`current_lens_id` on the parent, `lens_id` on snapshots) carry none either.
- A lens is **stamped on snapshots** through `lens_id`: every `projection_snapshot` / `reflection_snapshot` written through `engine.applySnapshotSpec` records the lens that produced it (the parent's `current_lens_id` for a generation; the new lens for a commit). Readers compare a snapshot's `lens_id` with the parent's `current_lens_id`: `latestApprovedOutput` refuses to minimise against an approved output of another lens (the regeneration then runs from scratch, `lifecycle-projection.md` § 4.2), `settleApprovedInPlace` refuses to settle onto it, `SnapshotIsCurrent` reports it as not current, `WindowsToGenerate` includes such a window in the set a reflection generate call covers, and `GET /api/reflections/{id}/windows` reports it `lensOutdated` (`lifecycle-reflection.md` § 5.1, § 9).
- The **drafted lens** during a session is not a row: it is the `input.lens` of the newest `tool-update_lens` part on an assistant message. A lens row is created only at commit.
- A refinement conversation has **no model of its own**: both model roles it uses resolve through the parent's `generate_with_model` (§ 3 step 5, § 3.1), read at each turn via `refinement.Parent` — the parent named by `projection_id` / `reflection_id`, else (rows that predate that column) the parent of the snapshot in `<type>_snapshot_id`; a soft-deleted parent resolves to none.

## 2. Opening a session (`POST …/{id}/refinements`)

Projections bind `api.CreateProjectionRefinementRequest` `{clientId, snapshotId?, contextSpec?}`; reflections bind `api.CreateReflectionRefinementRequest` `{clientId, window?, contextSpec?}` — a `snapshotId` sent to the reflection route is not a bound field and is dropped. Malformed body → 400 `invalid request body`; empty `clientId` → 400 `missing clientId`; empty path id → 400 `missing target id`. In one transaction:

1. The conversation row is created with `external_conversation_id = clientId`. **Projections:** the parent must exist and not be soft-deleted (`projections.FindLive`), `projection_id = {id}`; if `snapshotId` is given it is stored in `projection_snapshot_id` and the `projection_snapshot` row loaded — the snapshot's own parent is not checked against `{id}`. **Reflections:** `reflection_id = {id}`, the parent loaded via `reflections.FindLive`. Any failure inside the transaction (missing or soft-deleted parent, missing snapshot, unique-index violation on `clientId`) rolls back and is reported as 500 `failed to create refinement` — never 404.
2. The seeded context spec is chosen: the body's `contextSpec` if present; else (projections) the source snapshot's `context_spec` when it decodes; else (reflections) the parent's `current_context_spec` when it is non-empty, not the literal `null`, and decodes. A projection opened without `snapshotId` and without `contextSpec` is seeded with **no** spec.
3. Reflections only: the target window is the body's `window` if both `start` and `end` are set, else `reflections.DefaultRefinementWindow(parent, now)` (`windows.md` § 7) — nil for an unscheduled reflection. Its `id` is always recomputed server-side (`reflections.WindowID`, `windows.md` § 4); a client-supplied `id` is discarded. Projections never get a window.
4. If a spec or a window exists, one **system** message (id `ctx-<unixnano>`) is persisted carrying, in order: a `context_spec` part (when a spec exists), a `window` part `{id,start,end}` (reflections, when a window exists), and — when a spec exists — a `pinned_ids` part resolved now by `llmcontext.ResolveSpecToIDs` under that window (nil for projections; `context.md` § 2–3, § 5). A resolution error silently drops the `pinned_ids` part; the spec and window parts are still persisted. The message is persisted with an empty `generated_by_model`.
5. Reflections with a `current_lens_id` whose `lens.prompt` is non-blank after trimming: an **assistant** message (id `seed-<unixnano>`) is persisted (`refinement.SeedLensTurn`) carrying a `data-lens_seed {}` marker, a `tool-update_lens` part (`toolCallId` `seed-lens-<n>`, `input {lens}`), and — only when a window was chosen **and** that window has an approved `reflection_snapshot` (newest by `approval_sequence_number`) with non-blank `output` — a `tool-apply_result` part (`seed-apply-<n>`, `input {output}`). An unscheduled reflection (nil window) never receives the apply part even if it has an approved windowless snapshot. A reflection with no lens, a lens row that fails to load, or a projection gets no seed turn.

Response `201 {refinementId, messages}` — the seeded messages exactly as persisted (`messages` omitted when none were seeded). The client must render these ids rather than reconstruct them, or the next turn persists duplicates (`chat.ExtractNewMessages` dedupes by id only). A session with seeded context but no seed turn and no drafting turn cannot be committed (§ 5).

## 3. A drafting turn (`POST …/{id}/refinements/{rid}/chat`)

`handleRefinementChat` (bound per collection by `HandleProjectionRefinementChat` / `HandleReflectionRefinementChat`) rejects an empty `{id}` or `{rid}` with 400 `<type> id and refinement id required`, loads `{rid}` from the route's refinement collection (404 `<type> refinement not found`), and requires `refinement.Parent` to resolve to a live parent whose id equals `{id}` (else 400 `refinement does not belong to specified <type>` — also the answer for a soft-deleted parent). It binds `api.RefinementChatRequest` = `api.ChatRequest` `{id, messages}` (400 `invalid chat request body`); an empty `id` is filled from the conversation's `external_conversation_id`, but nothing downstream reads `id` — `messages` is the whole contract. `HandleChatForRefinement` then runs `refinement.StreamTurn`:

1. Stored messages are loaded (a load error is ignored and treated as an empty transcript); incoming messages whose ids are unknown are the new ones. `chat.ResolveContextSpecs` appends a `pinned_ids` part to each new **system** message carrying a `context_spec` and/or `window` part, resolved against the cumulative (spec, window) pair — the pair starts from the transcript's latest values (`llmcontext.LatestPinnedAndSpec`) and each new system message updates it in order; a `window` part with empty bounds clears the window; a resolution error leaves the message without a `pinned_ids` part. New messages are persisted with an empty `generated_by_model`; a persist failure is logged and the turn continues.
2. The parent is resolved (§ 1) and its `generate_with_model` read; with no parent the override is empty and role defaults apply.
3. **Re-apply check** (§ 4): `ReapplyWindow` — if the new messages contain no `user` message and at least one system message with a bounded `window` part, the turn is a window re-apply and the lens-writer is not consulted. Any other send — including one that carries only a `context_spec` part, or only an unbounded `window` part — proceeds as a drafting turn against the transcript as it stands.
4. The transcript is hydrated by `chat.HydrateDeltaHistory`: every system message renders as one system turn of `WindowNotice(start, end)` (when it carries a bounded `window` part) followed by the context delta between the previous `pinned_ids` and this message's, rendered by one `llmcontext.Hydrator` built from the transcript's final `pinned_ids` and the final spec's mode (`context.md` § 4); a system message that yields no text (a spec part whose resolution failed) is dropped. Non-system messages go through `llmcontext.Flatten` (`context.md` § 7): text parts with mentions expanded, `tool-update_lens` parts echoed as `LensEcho`, everything else invisible. `RefinementSystemPrompt` (`prompts.md` § 2) is prepended. Because the system prompt is always present, the `400 messages required` branch that follows is unreachable.
5. Model = `llm.ResolveRoleFor(RoleRefinement, parent.generate_with_model)` — a non-blank override wins for this role too; no model → 500 `no model configured for refinement`. `llm.CheckPromptFits` over the hydrated transcript's characters refuses with 422 and the guard's text (`context.md` § 6) before the call.
6. `usage.Stream` at `RoleRefinement` (no per-role generation options; `Interactive` queue priority — the request context carries no override) with tools **`update_lens`** (`lens` required, `suggested_name` optional) and **`suggest_name`** (`name` required); `llm-queue-quota.md` § 1. Quota exhaustion → 402 envelope; a classified provider error → its envelope (`llm-queue-quota.md` § 6); any other error → 500 `llm stream failed`. All of these occur before the SSE stream opens; once it is open the handler returns nil whatever happens.
7. The turn streams as an AI-SDK UI-message stream (`chat.BeginSSE`: `Content-Type: text/event-stream`, `x-vercel-ai-ui-message-stream: v1`) opened with `start {messageId: txt-<unixnano>}`; text as `text-start` / `text-delta` / `text-end` under that id, transient `data-inference_rate` parts at most every 250 ms and once at the end, model tool calls as `tool-input-start` / `tool-input-delta` / `tool-input-available` with `dynamic: true` (`explore.md` § 6). Each tool call is persisted as a `tool-<name>` part **as it arrives** through `chat.TurnWriter` — the assistant `chat_message` row is created on the first write and rewritten in place after that — then the final text part plus all tool parts are written. The row's `generated_by_model` is the refinement model. A turn that produces neither text nor a tool call writes no row.
8. **Name-only continuation** (`StreamNameOnlyContinuation`): when the turn has no text, at least one tool call, and no `update_lens` call carrying a non-empty `lens`, a second model call is made on the same open stream: the hydrated transcript plus an assistant echo of the tool names called (`DiscoverEchoToolCalls`, trimmed) and a user message `NameRecordedContinue` (`prompts.md` § 2), with **no tools** advertised, guarded by `CheckPromptFits`. Its text streams under id `<textId>-c1` and is appended to the same persisted message as a `text` part; tool calls in the continuation are dropped. A guard refusal, a call error or an empty reply is logged and the turn ends with only the tool parts; no error reaches the client. A continuation turn never reaches the apply leg (it only runs when no lens was drafted).
9. The **lens** is the `lens` argument of the turn's last `update_lens` call with a non-empty `lens` (`LatestLensArg`; untrimmed). If there is none (a clarifying question, a `suggest_name`-only turn, or a call with an empty lens) the stream finishes; the preview keeps its prior output. Nothing in code counts questions per turn, enforces the interview before the first lens, or checks `suggested_name`/`name` length — those are prompt instructions only (`prompts.md` § 2).
10. **Lint:** `LensCountPin` tries four case-insensitive patterns in order — `<N> in total`, `total of <N>`, `<N> total`, `all <N>` (`<N>` = digits or the number words one–twenty) — and returns the first match; a hit streams and persists a non-transient `data-refine_lint {match}` part on the same message. The apply still runs; nothing is redrafted. Per-item counts (`exactly two bullet points`) do not match.
11. **Apply leg** (§ 3.1) against the transcript's latest `pinned_ids` and `window` (`LatestPinnedAndSpec`: newest system part of each type, the window read even from an unbounded part as nil), then `finish` + `[DONE]`.

### 3.1 The apply leg

`StreamApplyLeg` executes the drafted lens through `refinement.ApplyDraftLens`:

- Source block = `llmcontext.HydrateIDsToText` of the pinned ids — always the **full** (flat) rendering of fragments and upstream snapshots (`context.md` § 4), whatever `wholeScope` mode the spec selects; empty when nothing is pinned (the lens is then applied to no sources).
- Model = `ResolveRoleFor(RoleSnapshot, parent.generate_with_model)`; no model → `data-refine_error {kind: apply_failed, message: "no model configured for generation"}` before any tool event.
- A fabricated tool call named `apply_result` (`toolCallId` `apply-<unixnano>`) is streamed: `tool-input-start` **before** the model call, then a `tool-input-delta` of `{"output":"` and one JSON-string-escaped delta (`JSONStringChunk`) per text chunk as the model produces them, then `"}` and a `tool-input-available` carrying the authoritative trimmed output.
- Prompt = `ApplyPrompt(lens, sourceBlock, windowStart, windowEnd)` as a single user message (`prompts.md` § 2; `engine.WindowBounds` gives zero bounds for a nil window), at `RoleSnapshot` options (temperature 0) and `Interactive` queue priority, via `usage.GenerateStreamMsgs` — no tools. `CheckPromptFits` is applied to the prompt's byte length. A preempted call (`queue.ErrPreempted`), an interrupted stream (the request context cancelled mid-stream), and an empty (whitespace-only) output are all errors.
- **Always from scratch:** the minimal-diff rewrite production regeneration applies when the same lens re-runs over new sources (`lifecycle-projection.md` § 4.2) is never applied to a preview.
- On failure a non-transient `data-refine_error {kind, message}` part is streamed and persisted instead of the apply part: `quota_exhausted` (message `generating the preview failed — send another message to retry`), `context_too_large` (message = the guard's text), or `apply_failed` (same generic message; covers preemption, provider errors, interruption and empty output). Deltas already streamed are not retracted; no `tool-input-available` follows. The message keeps its lens part; the client's preview keeps the last successful output; a commit of this lens is refused (§ 5).
- On success the `tool-apply_result {output}` part is appended to the **same** assistant message as the `tool-update_lens` part and the row rewritten.

The lens-writing model never sees `apply_result`, `suggest_name` or any `data-*` part: `Flatten` echoes only `tool-update_lens` (as `LensEcho`) back into the transcript (`context.md` § 7). The refinement role and the snapshot role are resolved separately and may be different models, though a parent `generate_with_model` override applies to both.

## 4. Window re-apply (reflections)

A send whose new messages contain no `user` message and a system message with a bounded `window` part re-executes the standing lens against that window (`StreamWindowReapply`; the last such part wins when several are new):

- The stream opens with `start {messageId: reapply-<unixnano>}`. The lens is the newest non-blank `tool-update_lens` on any assistant message (`LatestLensPart`, trimmed). If none exists yet, the stream just finishes (the window and its re-resolved `pinned_ids` are already on the transcript and the first drafting turn will use them).
- Otherwise a fabricated assistant turn is streamed and persisted: a `data-window_reapply {start, end}` part, a **replayed** `update_lens` tool call (`tool-input-start` + `tool-input-available` with the same input, id `<original toolCallId>-reapply`) so the lens/output pairing invariant holds on the new message, then the apply leg (§ 3.1) with the transcript's latest `pinned_ids` (already re-resolved under the new window in step 1 of § 3) and the new window. The row's `generated_by_model` is empty. The lint (§ 3 step 10) does not run on a re-apply.
- `Flatten` drops any message carrying `data-window_reapply`, so the lens-writer never sees these turns; `ExtractDraftedLensAndSpec` (§ 5) does see them, so the newest re-apply's output is what a commit pairs with the lens.
- Nothing entity-specific gates this path: a projection conversation that receives a bounded `window` part follows it too.

## 5. Commit (`POST …/{id}/refinements/{rid}/commit`)

1. Empty `{rid}` → 400 `refinement id required`; unknown in the route's collection → 404 `refinement not found`. `refinement.Commit` runs `ExtractDraftedLensAndSpec`: it loads the transcript (error → 500 `failed to commit refinement`), takes the latest `pinned_ids`, `context_spec` and `window` (§ 3 step 11), and scans **assistant** messages newest-first for the first one whose `tool-update_lens` has a non-blank `input.lens`; the trimmed `tool-apply_result.input.output` on **that same message** is the output (the last part of each type on the message wins). Messages without a lens part are skipped; the seed turn (§ 2 step 5) and re-apply turns (§ 4) qualify like any other — a seeded reflection session whose window had an approved output can be committed with zero turns. A transcript with no lens logs a warning listing every `role/partType` scanned.
2. Refusals: no lens on the transcript → 400 `no drafted lens found in chat` (also the zero-turn seeded-session case without a seed turn); lens without output → 409 `the latest lens has no generated preview — send another message to regenerate` (a failed or still-running apply).
3. Parent id = the conversation's `projection_id`/`reflection_id`, else via the source snapshot's parent (§ 1); neither → 400 `refinement missing parent target id`. A non-empty path `{id}` that disagrees with it → 400 `refinement parent target id mismatch`.
4. `engine.CommitRefinement` runs on a context detached from request cancellation (`context.WithoutCancel`), in one transaction; the transcript's window is not passed. Any failure → 500 `failed to commit refinement`.
   - Projections only (`InheritsCandidateTrigger`): if a source snapshot is recorded and is still `pending_review`, its `generation_trigger` is carried forward (an edit mid click-through keeps the speculative-chain mark; refining an approved snapshot does not); a source snapshot that fails to load is ignored.
   - The parent is loaded with `engine.FindLive` (missing or soft-deleted → the transaction fails).
   - A `lens` row is created: `prompt` = the drafted lens, `parent_lens_id` = the parent's previous `current_lens_id` (if any), `created_from_projection_refinement_id` or `created_from_reflection_refinement_id` = `{rid}`.
   - `strat.CommitRefinementSnapshot`. **Projections:** a `projection_snapshot` is appended with `lens_id` = the new lens, `output` = the previewed output, `context_spec` / `resolved_context` = the transcript's latest spec and pinned ids (zero-valued when the session never had a spec), `status = approved`, `generated_by_model` = `ResolveRoleFor(RoleSnapshot, parent.generate_with_model)` (a resolution failure leaves it empty), `created_from_refinement_id = {rid}`, `generation_trigger` = the carried trigger (else the value marked on the context — none here), `generated_at = now` — then `engine.ApproveSnapshot` assigns the next `approval_sequence_number`, sets `approved_at`, and discards the parent's other `pending_review` candidates (`lifecycle-projection.md` § 4.3). **Reflections** publish **nothing** and return an empty id: the previewed window was a sample.
   - The parent's `current_lens_id` is re-pointed to the new lens, `current_context_spec` set to the transcript's latest spec, and `status` set to `active` (a discover-proposed entity becomes active here).
5. After the transaction, for both entity kinds: `deps.Reconcile.EnqueueWave()` — a no-op unless `KALAIDO_AUTO_WAVE` is set (`reconcile.md` § 4). Reflections only, before the response is written: `reflections.RunPendingWindows(deps.Runner, …)` starts one detached goroutine (`boot-and-workers.md` § 3) generating every window the series owes (`PendingWindows`: no approved output and no generation in flight, `windows.md` § 3) as approved at `Background` queue priority, one goroutine per window, retrying a preempted call; a window that already has an approved snapshot under the old lens is not regenerated by this pass and is reported `lensOutdated` (`lifecycle-reflection.md` § 5.3, § 9).
6. Response `200 {snapshotId}` — the new snapshot id for projections, `""` for reflections.

The refinement conversation and its messages are not deleted, closed or marked by a commit; further turns on the same conversation continue from the same transcript, and a second commit creates another lens whose `parent_lens_id` is the first.

## 6. Active-lens resolution

`engine.resolveActiveLens(strat, rec)` loads the row named by the parent's `current_lens_id` from `lens` and returns its `prompt` together with the parent's own `current_context_spec` (decoded leniently; a missing or unreadable spec is the zero spec). A parent without a lens (never committed), or whose lens row cannot be loaded, yields an empty prompt; `engine.GenerateSnapshot` refuses a blank (trimmed) prompt with `ErrLensNotReady` before claiming (`lifecycle-projection.md` § 4.1; the generate routes report it as 409 `This <type>'s lens is still being prepared — try again in a moment.`, the reconcile wave skips the entity, and the pending-window pass logs `no lens yet`). Generation therefore executes the **parent's** `current_context_spec` — the spec the commit set, as later rewritten by anything that edits the parent's spec (the colour-delete and upstream-delete scrubs through `engine.ScrubContextSpecs`, `colours.md` § 6; a candidate edit, `lifecycle-projection.md` § 4.4) — and `SnapshotIsCurrent` compares the newest pending-or-approved snapshot's `lens_id` against `current_lens_id`, its `generated_by_model` against the role resolution now (when the snapshot carries one), and its `resolved_context` against that same spec resolved now (`context.md` § 5). The snapshot's `lens_id` is taken from `current_lens_id` on the same record in the same call, so a lens and its scope are always read from one parent row.
