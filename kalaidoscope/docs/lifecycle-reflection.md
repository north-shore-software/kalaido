**Scope.** The life of one reflection: creation with a schedule, schedule editing, authoring, windowed generation, per-window approval, staleness, soft deletion and restore, and backfill. Shared machinery lives in its own docs — window calculation in `windows.md`, the refinement conversation in `refinement.md`, staleness and the reconcile wave in `rotation.md`, spec resolution in `context.md`; endpoint detail in `api.md` § 6–7, fields in `schema.md` § 2.6, 2.9, 2.11, 2.18. Where behaviour is identical to a projection's (`lifecycle-projection.md`), it is referenced, not repeated.

**Completeness anchor.** 9 reflection routes, all registered in the `// Reflections` block of `RegisterRoutes` in `server/server.go`: `POST /api/reflections`, `PATCH /api/reflections/{id}`, `DELETE /api/reflections/{id}`, `POST /api/reflections/{id}/restore`, `POST /api/reflections/{id}/generate-snapshot`, `GET /api/reflections/{id}/windows`, `POST /api/reflections/{id}/backfill`, `POST /api/reflections/{id}/refinements`, `POST /api/reflections/{id}/refinements/{rid}/commit`. 0 record hooks are bound on `reflection`, `reflection_snapshot`, `reflection_window` or `reflection_refinement` (the binary's only record hooks are on `fragment`, `ingest` and `kalaidoscope_config`). Every route above appears in this document.

## 1. Objects and states

A `reflection` row carries `name`, `status` (`proposed` | `active`), `description`, `current_context_spec`, `current_lens_id`, `generate_with_model` (per-entity model override), `pinned_by`, `created_by_discover_run_id`, `deleted_at` (soft delete, § 8) and `window_spec_versions` — an append-only JSON list `[{versionNumber, effectiveFrom, spec}]` of its schedule (`windows.md` § 2). All four reflection collections have their create/update/delete rules disabled (`DisableWriteOperations`): the collection API can list and view them (auth required) but every write goes through the routes below. Nothing hooks these collections.

Its output is a **time series** of `reflection_snapshot` rows. A row is either *windowed* — `window_start` and `window_end` set to the half-open `[start, end)` it covers — or *windowless* — both empty (an unscheduled reflection). No window key, schedule version or spec is stored on the row: the in-memory key `WindowKey = "{start}_{end}"` (RFC3339 UTC) is rebuilt from the bounds, and the id the API hands out for a window is `md5(reflectionId + start + end)` (`windows.md` § 4). Snapshot statuses are `generating` (the claim row), `pending_review`, `approved`, `discarded`. The active output is derived **per window**: the `approved` row with the highest `approval_sequence_number` among rows with the same `(window_start, window_end)` — enforced by the partial unique index `idx_reflection_snapshot_approval_seq` on `(reflection_id, window_start, window_end, approval_sequence_number) WHERE status = 'approved'`. Windowless rows form their own chain, selected by `window_start = ''`. Other snapshot fields are as for projections (`lens_id`, `output`, `context_spec`, `resolved_context`, `generated_by_model`, `generation_trigger`, `created_from_refinement_id`, `approved_at`, `generated_at`).

`reflection_window` rows (`reflection_id`, `window_start`, `window_end`; unique on the three) record explicitly backfilled windows (§ 9). `reflection_refinement` rows (`reflection_id`, `reflection_snapshot_id`, `external_conversation_id`) are the refinement sessions; their transcript lives in `chat_message.reflection_refinement_id`.

Status at birth by path:

| Path | `status` | `window_spec_versions` v1 | `current_context_spec` |
|---|---|---|---|
| `POST /api/reflections` (§ 2) | `active` | request `windowSpec` (or an all-empty spec), `effectiveFrom` = `startTime` when in the past, else now | unset until a refinement commits |
| discover reflections flow (`discover.md` § 6) | `proposed` | `{startTime: <date floored to midnight UTC>, period, duration = period}`, `effectiveFrom` = that start | `{colourIds}` |

A `proposed` reflection is not evaluated for staleness (`rotation.md` § 1 selects `status = 'active'`) and becomes `active` only when a refinement is committed (§ 4). There is no other activation path. In rotation terms a reflection with no approved snapshot at all is a draft: its status row is zero (§ 7).

## 2. Creation

`POST /api/reflections` binds an anonymous body `{name, description?, windowSpec?}` (the declared `api.CreateReflectionRequest` is not what is bound; its `clientId` is never read). `name` is not required. `description` is trimmed and stored when non-empty. A `windowSpec` `{startTime, period, duration}` (the DTO's `mode` and `endTime` fields are accepted and read by nothing) is validated: an entirely empty spec is allowed (unscheduled); otherwise `period` must parse as a positive `time.Duration`, `duration` if given likewise, `startTime` if given RFC3339 — else `400` with the field-specific message (`windows.md` § 1). Body parse failure → `400 invalid request body`.

In one transaction the row is created with `status = active` and version 1 of the schedule appended (`versionNumber 1`, the spec as given — an all-empty spec when none was sent), with `effectiveFrom` = **`startTime` when it parses and lies before now, else now**. Since a version's lower bound is the later of `effectiveFrom` and `startTime` (`windows.md` § 2), a past `startTime` makes every grid window since that date part of the series — all pending until a lens exists. Save failure → `500 create reflection failed`. Response `201 {reflectionId}`. No lens, no snapshot, no generation; nothing is signalled.

## 3. Schedule editing

`PATCH /api/reflections/{id}` binds `api.UpdateSynthesisRequest` `{name?, pinned?, windowSpec?, generateWithModel?}`; absent fields are untouched. The reflection is loaded with `FindLive`: missing or soft-deleted → `404 reflection not found`.

- `windowSpec`: validated exactly as at creation (`400` on failure). An empty `startTime` inherits the governing version's `startTime` (when a governing version exists) so the grid keeps its origin; the spec is then appended as the next version with `effectiveFrom` = now. Windows already generated under an older version stay in the series (`windows.md` § 6). Nothing is regenerated, discarded or signalled by a schedule edit.
- `name`: set as given (an empty string is stored).
- `generateWithModel`: trimmed and stored in `generate_with_model`; empty clears the override (`lifecycle-projection.md` § 5).
- `pinned`: only when the request is authenticated (`e.Auth != nil`) — adds or removes the caller's user id in `pinned_by`; unauthenticated, the field is silently ignored.

Save failure → `500 update reflection failed`. Response `200 {id}`.

## 4. Authoring: refinement → commit

**Opening.** `POST /api/reflections/{id}/refinements` binds `api.CreateRefinementRequest` `{clientId, snapshotId, window?, contextSpec?}`. `clientId` empty → `400 missing clientId`. For a reflection `snapshotId` is ignored (`reflection_snapshot_id` is never set). Inside one transaction: the parent is loaded with `FindLive` — a missing **or soft-deleted** reflection fails the transaction and is reported as `500 failed to create refinement`; a `reflection_refinement` row is created with `external_conversation_id = clientId`; the seeded context spec is the request's `contextSpec`, else the reflection's own `current_context_spec` (when set and not `null`); the **target window** is the request's `window` when it has both `start` and `end`, else `DefaultRefinementWindow` (`windows.md` § 7) — nil for an unscheduled reflection — with `id` recomputed as `WindowID(reflectionId, window)`. A system message is persisted carrying a `context_spec` part (when a spec exists), a `window` part (when a window exists) and — when a spec exists and its resolution succeeds — a `pinned_ids` part holding the spec resolved **inside that window** (`context.md` § 2.1); a resolution error drops the part silently, and no system message is written when none of the three applies (an unscheduled reflection without a spec). When the reflection already has a lens with a non-empty prompt, an assistant turn is persisted after it: a `data-lens_seed` marker, an `update_lens` tool-call part carrying the current lens, and — when the target window has an approved snapshot with non-empty output — an `apply_result` part carrying that output as the starting preview. Response `201 {refinementId, messages}` with the seeded messages. `refinement.md` § 2 describes the session shape.

**Turns** arrive on `POST /api/chat`, routed to the refinement handler when the conversation id matches a `reflection_refinement.external_conversation_id` (`chat.md` § 1). A turn previews the drafted lens against the fragments the spec resolves to inside the current window; a send carrying only a new `window` part re-applies the standing lens to that window without consulting the lens-writer (`refinement.md` § 3–4). The preview leg hydrates whatever the spec resolves to, snapshots included; the fragments-only rule of § 5.2 is applied at generation, not in the preview. The turn's model follows the reflection's `generate_with_model`; when the parent is soft-deleted the turn still runs, with the workspace default.

**Commit.** `POST /api/reflections/{id}/refinements/{rid}/commit`: `rid` missing → `400`; refinement not found → `404`. The transcript is read for the newest assistant message carrying an `update_lens` part and the `apply_result` paired on that same message (`refinement.md` § 5): no lens → `400 no drafted lens found in chat`; lens without output → `409 the latest lens has no generated preview — send another message to regenerate`. The parent id is `reflection_id` (else derived through `reflection_snapshot_id`); none → `400 refinement missing parent target id`; a URL `{id}` that differs → `400 refinement parent target id mismatch`. `CommitRefinement` runs detached from the request, in one transaction: `FindLive` on the parent (soft-deleted → the commit fails → `500 failed to commit refinement`); a new `lens` row with `prompt`, `parent_lens_id` = the previous `current_lens_id` (lineage only) and `created_from_reflection_refinement_id`; **no snapshot is written** for a reflection — the previewed window was a sample; the parent's `current_lens_id` and `current_context_spec` are set and `status = active`. The transcript's window is passed to the commit and not used. After the transaction `engine.RequestWave()` is called (an automatic wave only under `KALAIDO_AUTO_WAVE`, `rotation.md` § 3), then `RunPendingWindows` starts the background pass (§ 5.3). Response `200 {snapshotId: ""}`.

After a commit every window that already has an approved snapshot reads as `lensOutdated` (§ 9); those windows are regenerated only through the generate route's candidate set (§ 5.1) — neither the background pass (§ 5.3) nor the wave (§ 7) regenerates a window whose approved snapshot merely predates the current lens.

## 5. Generation

`POST /api/reflections/{id}/generate-snapshot` binds `api.GenerateSnapshotRequest` `{preview?, windowId?, all?}` — its `sourceId`, `chatId`, `fragmentIds`, `colourIds`, `messages` fields are accepted and unused, and a body that fails to parse is treated as empty. `preview: true` stores the result as `pending_review`, otherwise as `approved`. `FindLive` → `404 reflection not found` for a missing or soft-deleted reflection. The rotation row for the reflection is computed (`rotation.md` § 1–2); an evaluation error is logged and ignored (the row is then zero), while a non-empty `blockedBy` → `409 upstream dependencies are not up to date; approve them first`.

### 5.1 Which windows

- `windowId` given: it must be the id of a window in the series (`windows.md` § 6) → exactly that window, whatever its state (a re-run of history); unknown → `400 window ID not found in this reflection's windows`.
- Otherwise the candidates, deduplicated by id in series order, are every series window that is **not generating** and either has no approved snapshot or whose approved snapshot's `lens_id` ≠ `current_lens_id`, followed by the rotation row's `staleWindows` (empty when the evaluation failed or the reflection is a draft). None → the **default refinement window** (`windows.md` § 7; a nil, windowless generation only for an unscheduled reflection or one whose first grid point has not passed and whose trailing window is empty). Exactly one, or `all: true` → all of them; several without `all` → `400 multiple pending windows; specify windowId or all=true`.

The generation context is detached from the request (`context.WithoutCancel`). **One window** goes through `GenerateSnapshot` directly; `ErrGenerationInFlight` makes the handler **join** the running generation for that window (`AwaitGeneration`, polling the claim row every 500 ms, bounded by the request context and the 10-minute claim TTL) and, if that generation ends without output, generate afresh. **Several windows** run through `GenerateWindows`: one goroutine per window, each retrying on `llmq.ErrPreempted`, joined before the response; concurrency is bounded only by the scheduler (`llm-queue-quota.md` § 2). No join is attempted on this path — an in-flight window is simply a failed window.

Response `200 {snapshotIds: [...]}` with the successes. When some windows failed and at least one succeeded, the first error is logged and the successes returned. When none succeeded the first error is mapped: `usage.ErrExhausted` → `402` (`llm-queue-quota.md` § 5); `ErrLensNotReady` → `409 This reflection's lens is still being prepared — try again in a moment.`; `ErrGenerationInFlight` → `409 A generation for this reflection is already running.`; `ErrContextTooLarge` → `422`; a classified provider error → its envelope (`llm-queue-quota.md` § 6); an error whose text contains `not found` → `404` (single-window path only); anything else → `500 generate reflection failed`.

### 5.2 One window

`GenerateSnapshot(ctx, reflection, status, window)`, as `lifecycle-projection.md` § 4.1–4.2 with these differences:

1. **Lens and model.** `current_lens_id` must point at a lens with a non-empty prompt, else `ErrLensNotReady`. The model is `RoleSnapshot` resolved against `generate_with_model` (`lifecycle-projection.md` § 5).
2. **Claim.** The claim row (`status = generating`) carries `window_start`/`window_end` from insertion; the lock is per `(reflection, window)`, so different windows generate concurrently while a second generation of the same window gets `ErrGenerationInFlight`. A claim older than 10 minutes is deleted and taken over. Every failure below releases the claim (the row is deleted).
3. **Context.** The lens's spec (`current_context_spec`) is resolved **inside the window** (`context.md` § 2.1). If resolution errors, generation proceeds with an empty source block. If the resolved set contains any upstream snapshot the generation fails with `this context must contain fragments only, but snapshots were provided` (`ReflectionStrategy.EnsureFragmentsOnly`) — a reflection never consumes projections or reflections. The prompt is `ApplyPrompt(lens, sourceBlock, start, end)` with the window bounds (`prompts.md`); `CheckPromptFits` may refuse it (`context.md` § 6); empty model output fails the generation.
4. **Anchor.** The minimal-diff anchor is the newest approved snapshot **of the same window** (windowless chain for a nil window) — but only when it was produced by the current lens. Another lens → generated from scratch; byte-identical output, or a delta of "no changes" → *unchanged*; otherwise the two-turn rewrite, whose failure keeps the raw candidate, whose preemption aborts the whole generation (retried by `GenerateWindows`, the background pass, and the wave), and whose cancellation aborts without persisting.
5. **Settle in place.** *Unchanged* under a wave context (`generation_trigger` set) updates the window's approved row (`context_spec`, `resolved_context`, `generated_by_model`, `generated_at`), discards the window's other `pending_review` rows, releases the claim and returns the approved row's id — no new row, no sequence move. An interactive unchanged generation still stores a new row.
6. **Complete.** The claim row is filled in place: `reflection_id`, `lens_id`, `output`, `context_spec`, `resolved_context`, the window bounds, `status`, `generated_by_model`, `generation_trigger` (from the context), `generated_at`; in the same transaction every other `pending_review` row **of the same window** is set `discarded`. With `status = approved`, `ApproveSnapshot` then assigns `approval_sequence_number` = highest approved sequence within the window + 1, sets `approved_at`, and discards the window's other pending rows again (`lifecycle-projection.md` § 4.3 for the approvability checks).

### 5.3 The background pass

`RunPendingWindows(reflectionId)` runs `GeneratePendingWindows` on a fresh goroutine (`boot-and-workers.md` § 3). Its triggers are exactly two: a reflection refinement commit (§ 4) and `POST /api/reflections/{id}/backfill` (§ 9). Nothing runs it at boot or on a timer. The pass loads the reflection with `FindRecordById` (a soft-deleted reflection is loaded, but every window then fails in `GenerateSnapshot`'s `FindLive`), computes the **pending windows** — series windows with no approved snapshot and no generation in flight, oldest first (`windows.md` § 3) — and generates all of them through `GenerateWindows` as `approved` at `llmq.Background` priority. Per window: `ErrLensNotReady` and `ErrGenerationInFlight` are logged/silently skipped, any other error is logged; a window that failed stays pending for the next trigger. One pass, no loop, no reschedule, no signal on completion. Windows with an approved snapshot under an older lens are not pending and are not touched.

## 6. Approval

There is **no reflection approve route** and no reflection edit route: `handleApproveCandidate` and `handleEditCandidate` are registered under `/api/projections` only, and `engine.ApplyEdit` refuses any non-projection strategy. A reflection snapshot stored with `preview: true` therefore stays `pending_review` until a later generation of the **same window** completes or approves (which discards it) or a wave generation settles that window in place; it can never be promoted. Approvals happen only server-side: an interactive non-preview generation (§ 5), the background pass (§ 5.3) and the wave (§ 7) each approve their own output as it lands, per window, with the sequence rule of § 5.2 step 6.

## 7. Staleness and the wave

Only `active`, live reflections are evaluated (`rotation.md` § 1). A reflection with no approved snapshot is a draft and reports a zero row. With at least one **windowed** approved snapshot it is evaluated per window (`rotation.md` § 2.1): windows owed but never generated (and not generating) are `pendingWindows`; each window's spec resolution inside that window is diffed against that window's approved `resolved_context` (fragment ids only; a window whose resolution errors is skipped), so a backdated fragment flags exactly the windows it falls in as `staleWindows`. On this path `staleDependencies` and `blockedBy` are never computed, so the generate route's `409` upstream guard (§ 5) cannot fire for a windowed reflection. Lens identity is not part of the evaluation: a window whose approved snapshot predates the current lens is neither pending nor stale. With only windowless snapshots the reflection is evaluated like a projection (`rotation.md` § 2) plus `pendingWindows` from the grid. As an **upstream** (another entity's `sourceReflectionIds`) a reflection contributes its newest approved snapshot across all windows — by `approval_sequence_number`, so the ordering across windows is by approval order, not window date — and nothing while soft-deleted (`context.md` § 3).

The reconcile wave (`rotation.md` § 3) generates a reflection's `pendingWindows` and `staleWindows` as **approved**, at background priority, under the `generate_all` trigger (so an unchanged result settles in place, § 5.2 step 5). A scheduled reflection that owes no window is skipped — the wave never produces a windowless snapshot for it. An unscheduled reflection is in the wave's worklist only when its row reports `newFragmentIDs`, `staleDependencies`, `blockedBy` or `pendingWindows`; it is then regenerated windowless unless `SnapshotIsCurrent` says its newest snapshot already reflects the current lens, model and resolved context. Per window the wave retries on preemption and skips on `ErrLensNotReady`/`ErrGenerationInFlight`; any other error ends the wave.

## 8. Deletion and restore

`DELETE /api/reflections/{id}` is a **soft delete**. The row is loaded with `FindRecordById` (missing → `404`); an already-deleted reflection → `204` with no further effect. If a `generating` claim row younger than 10 minutes exists for the reflection — **any** window — → `409 a generation is running for this reflection`. Otherwise, in one transaction: the reflection's id is removed from `sourceReflectionIds` in the `current_context_spec` of every `projection` and every `reflection` whose spec text contains it (matched with `~`, without a live filter — proposed and soft-deleted entities are scrubbed too; frozen snapshot `context_spec`s are not); then `deleted_at` is set to now. Transaction failure → `500 delete reflection failed`. Response `204`.

Nothing else is written: `reflection_snapshot`, `reflection_window`, `reflection_refinement` and `chat_message` rows stay as they are (their `CascadeDelete` relations fire only on a hard delete, which no route performs). Lenses remain. While `deleted_at` is set: `PATCH`, generate, windows, backfill and refinement-open all answer `404`/`500` as stated above (`FindLive`); the rotation evaluator and discover's `list_existing` skip the reflection (`LiveFilter`); its snapshots resolve for no dependent (`reflection_id.deleted_at = ''`, `context.md` § 3); a refinement already open on it can still take turns, and its commit fails `500`. The collection list/view endpoints apply no live filter — a soft-deleted reflection and its children are still readable there.

`POST /api/reflections/{id}/restore`: missing → `404`; otherwise `deleted_at` is cleared (a live reflection is a no-op; save failure → `500 restore reflection failed`) and the response is `200 {id}`. References scrubbed from other entities at delete time are not re-added. No generation, staleness or wave is triggered by either operation.

## 9. Backfill and the windows route

- **`POST /api/reflections/{id}/backfill`** binds `api.BackfillRequest` `{from}`: unparsable body → `400 invalid request body`; `from` not RFC3339 → `400 from must be RFC3339`; `FindLive` → `404 reflection not found`. `MaterializeBackfill` (`windows.md` § 6.1) requires a governing version with a period — otherwise the error (`is not scheduled` / `has no period`) is logged and answered `500 backfill failed`; `from` at or after the governing version's lower bound → `400 backfill start must be before the windows already on the grid`. Every grid window between `from` and that lower bound, phase-aligned with the existing grid, is written as a `reflection_window` row (`reflection_id`, `window_start`, `window_end`); a save rejected by the unique index is tolerated when the row already exists, any other save failure → `500`. Then `RunPendingWindows` (§ 5.3) is started **unconditionally**, even when nothing new was materialised. Response `200 {windows: [{id, start, end}]}` — the windows enumerated for the range (`null` when the range held none), not the generated ones; results arrive as `reflection_snapshot` rows.
- **`GET /api/reflections/{id}/windows`**: `FindLive` → `404`. The series (`windows.md` § 6: current grid, backfilled rows, and every windowed `approved` or `generating` snapshot) is served oldest first as `{windows: [{id, start, end, key, hasApproved, generating, backfilled, stale?, lensOutdated?}], currentWindowId?}`. `stale` is true for windows in the reflection's `staleWindows` from a full rotation evaluation (§ 7) — absent for every window when the evaluation errors or the reflection is a draft; `lensOutdated` = `hasApproved` and the highest-sequence approved snapshot's `lens_id` ≠ `current_lens_id`; `currentWindowId` = the default refinement window's id (`windows.md` § 7), omitted for an unscheduled reflection. `stale`, `lensOutdated` and `currentWindowId` are omitted from the JSON when false/empty.
