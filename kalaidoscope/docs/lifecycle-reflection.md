## 1. Objects and states

A `reflection` row carries `name`, `status` (`proposed` | `active`), `description`, `current_context_spec`, `current_lens_id`, `generate_with_model` (per-entity model override), `pinned_by`, `created_by_discover_run_id`, `deleted_at` (soft delete, § 8) and `window_spec_versions` — an append-only JSON list `[{versionNumber, effectiveFrom, spec}]` of its schedule (`windows.md` § 2). All four reflection collections are declared with `DisableWriteOperations`: their list/view rules are `@request.auth.id != ''` and their create/update/delete rules are nil, so the collection API can read them (auth required) but every write goes through the routes below. Nothing hooks these collections.

Its output is a **time series** of `reflection_snapshot` rows. A row is either *windowed* — `window_start` and `window_end` set to the half-open `[start, end)` it covers — or *windowless* — both empty (an unscheduled reflection). No window key, schedule version or spec is stored on the row: the in-memory key `WindowKey = "{start}_{end}"` (RFC3339 UTC) is rebuilt from the bounds, and the id the API hands out for a window is `md5(reflectionId + start + end)` (`windows.md` § 4). Snapshot statuses are `generating` (the claim row), `pending_review`, `approved`, `discarded`. The active output is derived **per window**: the `approved` row with the highest `approval_sequence_number` among rows with the same `(window_start, window_end)` — enforced by the partial unique index `idx_reflection_snapshot_approval_seq` on `(reflection_id, window_start, window_end, approval_sequence_number) WHERE status = 'approved'`. Windowless rows form their own chain, selected by `window_start = ''` (`Strategy.SnapshotWindowFilter`). Other snapshot fields are as for projections (`lens_id`, `output`, `context_spec`, `resolved_context`, `generated_by_model`, `generation_trigger`, `created_from_refinement_id`, `approved_at`, `generated_at`).

`reflection_window` rows (`reflection_id`, `window_start`, `window_end`; unique on the three via `idx_reflection_window_bounds`) record explicitly backfilled windows (§ 9). `reflection_refinement` rows (`reflection_id`, `reflection_snapshot_id`, `external_conversation_id`, unique) are the refinement sessions; their transcript lives in `chat_message.reflection_refinement_id`.

Status at birth by path:

| Path | `status` | `window_spec_versions` v1 | `current_context_spec` |
|---|---|---|---|
| `POST /api/reflections` (§ 2) | `active` | request `windowSpec` (or an all-empty spec), `effectiveFrom` = `startTime` when it parses and lies in the past, else now | unset until a refinement commits |
| discover reflections flow (`discover.md` § 6.1) | `proposed` | `{startTime: <date floored to midnight UTC>, period, duration = period}` from the cadence table (`daily` 24h, `weekly` 168h, `monthly` 720h, `quarterly` 2160h), `effectiveFrom` = that start | `{colourIds}` |

Discover also writes `description` (the proposal's message) and `created_by_discover_run_id`. A `proposed` reflection is not evaluated for staleness (`reconcile.md` § 1 selects `status = 'active'`) and becomes `active` only when a refinement is committed (§ 4). There is no other activation path. A reflection with no approved snapshot at all is a draft in reconcile terms: its status row is zero (§ 7).

## 2. Creation

`POST /api/reflections` binds `api.CreateReflectionRequest` `{name, description?, windowSpec?}`. `name` is not required. `description` is trimmed and stored when non-empty. A `windowSpec` `{startTime, period, duration}` (the DTO's `mode` and `endTime` fields are accepted and read by nothing) is validated by `WindowSpec.Validate`: an entirely empty spec is allowed (unscheduled); otherwise `period` must parse as a positive `time.Duration`, `duration` if given likewise, `startTime` if given RFC3339 — else `400` with the field-specific message (`windows.md` § 1). Body parse failure → `400 invalid request body`.

In one transaction the row is created with `status = active` and version 1 of the schedule appended (`versionNumber 1`, the spec as given — an all-empty spec when none was sent), with `effectiveFrom` = **`startTime` when it parses and lies before now, else now**. Since a version's lower bound is the later of `effectiveFrom` and `startTime` (`windows.md` § 2), a past `startTime` makes every grid window since that date part of the series — all pending until a lens exists. Save failure → `500 create reflection failed`. Response `201 {reflectionId}`. No lens, no snapshot, no generation; nothing is signalled.

## 3. Schedule editing

`PATCH /api/reflections/{id}` binds `api.UpdateReflectionRequest` `{name?, pinned?, windowSpec?, generateWithModel?}`; absent fields are untouched; parse failure → `400 invalid request body`. The reflection is loaded with `FindLive` first: missing or soft-deleted → `404 reflection not found`. Then:

- `windowSpec`: validated exactly as at creation (`400` on failure). An empty `startTime` inherits the governing version's `startTime` (when a governing version exists) so the grid keeps its origin; the spec is then appended as the next version (`versionNumber` = highest existing + 1) with `effectiveFrom` = now. Windows already generated under an older version stay in the series (`windows.md` § 6). Nothing is regenerated, discarded or signalled by a schedule edit.
- `name`: set as given (an empty string is stored).
- `generateWithModel`: trimmed and stored in `generate_with_model`; empty clears the override (`lifecycle-projection.md` § 5).
- `pinned`: only when the request is authenticated (`e.Auth != nil`) — adds or removes the caller's user id in `pinned_by` (`pbutil.TogglePinnedBy`); unauthenticated, the field is silently ignored.

Save failure → `500 update reflection failed`. Response `200 {id}`.

## 4. Authoring: refinement → commit

**Opening.** `POST /api/reflections/{id}/refinements` binds `api.CreateReflectionRefinementRequest` `{clientId, window?, contextSpec?}` (no `snapshotId`: `reflection_snapshot_id` is never set by this route). Parse failure → `400 invalid request body`; `clientId` empty → `400 missing clientId`. Inside one transaction: a `reflection_refinement` row is prepared with `external_conversation_id = clientId` and `reflection_id = {id}`; the parent is loaded with `FindLive` — a missing **or soft-deleted** reflection fails the transaction and is reported as `500 failed to create refinement`; the row is saved. The seeded context spec is the request's `contextSpec`, else the reflection's own `current_context_spec` (when its raw value is non-empty and not `null`). The **target window** is the request's `window` when it has both `start` and `end`, else `DefaultRefinementWindow` (`windows.md` § 7) — nil for an unscheduled reflection — with `id` recomputed as `WindowID(reflectionId, window)`. A system message is persisted carrying a `context_spec` part (when a spec exists), a `window` part (when a window exists) and — when a spec exists and its resolution succeeds — a `pinned_ids` part holding the spec resolved **inside that window** (`context.md` § 2.1); a resolution error drops the part silently, and no system message is written when none of the three applies (an unscheduled reflection without a spec). When the reflection's `current_lens_id` points at a lens with a non-empty prompt, an assistant turn is persisted after it (`SeedLensTurn`): a `data-lens_seed` marker part, an `update_lens` tool-call part carrying the current lens, and — when a target window exists and its highest-sequence approved snapshot has non-empty output — an `apply_result` tool-call part carrying that output as the starting preview. Response `201 {refinementId, messages}` with the seeded messages. `refinement.md` § 2 describes the session shape.

**Turns** arrive on `POST /api/reflections/{id}/refinements/{rid}/chat`, binding `api.ChatRequest` `{id, messages}` (parse failure → `400 invalid chat request body`; an empty `id` defaults to the refinement's `external_conversation_id`). The refinement is loaded by `rid` (`404 reflection refinement not found`); its parent is resolved through `refinement.Parent`, which returns nil for a missing **or soft-deleted** reflection — nil, or an id other than the URL `{id}` → `400 refinement does not belong to specified reflection`. A turn drafts the lens and previews it against the fragments the spec resolves to inside the current window; a send carrying only a new `window` part re-applies the standing lens to that window without consulting the lens-writer (`refinement.md` § 3–4). The preview leg hydrates whatever the spec resolves to, snapshots included; the fragments-only rule of § 5.2 is applied at generation, not in the preview. Both the drafting model (`RoleRefinement`) and the preview model (`RoleSnapshot`) resolve against the parent's `generate_with_model`. Stream errors: no messages → `400 messages required`; no model → `500 no model configured for refinement`; quota exhausted → `402`; a classified provider error → its envelope; context too large → `422`; anything else → `500 llm stream failed`. The explore route (`explore.md` § 1) does not dispatch to refinements.

**Commit.** `POST /api/reflections/{id}/refinements/{rid}/commit`: `rid` missing → `400 refinement id required`; refinement not found → `404 refinement not found`. The commit runs under `context.WithoutCancel` of the request. The transcript is read (a load failure → `500 failed to commit refinement`) for the newest assistant message carrying an `update_lens` part and the `apply_result` paired on that same message (`refinement.md` § 5): no lens → `400 no drafted lens found in chat`; lens without output → `409 the latest lens has no generated preview — send another message to regenerate`. The parent id is `reflection_id` (else derived through `reflection_snapshot_id`); none → `400 refinement missing parent target id`; a non-empty URL `{id}` that differs → `400 refinement parent target id mismatch`. `engine.CommitRefinement` then runs in one transaction: `FindLive` on the parent (soft-deleted → the commit fails → `500 failed to commit refinement`); a new `lens` row with `prompt`, `parent_lens_id` = the previous `current_lens_id` when there was one (lineage only) and `created_from_reflection_refinement_id`; **no snapshot is written** for a reflection (`Strategy.CommitRefinementSnapshot` returns an empty id) — the previewed window was a sample; the parent's `current_lens_id` is re-pointed, `current_context_spec` is set to the transcript's latest `context_spec` part, and `status = active`. The transcript's `pinned_ids` receipt and `window` are read and not used by the commit. After the transaction the handler calls the reconcile worker's `EnqueueWave` (a no-op unless the automatic-wave policy is on, `reconcile.md` § 4), then `RunPendingWindows` starts the background pass (§ 5.3). Response `200 {snapshotId: ""}`.

After a commit every window that already has an approved snapshot reads as `lensOutdated` (§ 9); those windows are regenerated only through the generate route's candidate set (§ 5.1) — neither the background pass (§ 5.3) nor the wave (§ 7) regenerates a window whose approved snapshot merely predates the current lens.

## 5. Generation

`POST /api/reflections/{id}/generate-snapshot` and its alias `POST /api/reflections/{id}/snapshots` share one handler. It binds `api.GenerateReflectionSnapshotRequest` `{preview?, windowId?, allWindows?}` — the legacy JSON key `all` is accepted as `allWindows` by a custom `UnmarshalJSON`, and `sourceId`, `chatId`, `fragmentIds`, `colourIds`, `messages` are accepted and unused; a body that fails to parse → `400 invalid request body`. `preview: true` stores the result as `pending_review`, otherwise as `approved`. `FindLive` → `404 reflection not found` for a missing or soft-deleted reflection. The reflection's status row is computed by a full evaluation pass (`reconcile.EvaluateEntity`, `reconcile.md` § 1–2); an evaluation error is logged and ignored (the row is then zero), while a non-empty `blockedBy` → `409 upstream dependencies are not up to date; approve them first`.

### 5.1 Which windows

`WindowsToGenerate` first rejects `windowId` together with `allWindows` (`400 cannot specify both windowId and allWindows=true`), then:

- `windowId` given: it must be the id of a window in the series (`windows.md` § 6) → exactly that window, whatever its state (a re-run of history); unknown → `400 window ID not found in this reflection's windows`.
- Otherwise the candidates, deduplicated by id in series order, are every series window that is **not generating** and either has no approved snapshot or whose highest-sequence approved snapshot's `lens_id` ≠ `current_lens_id`, followed by the status row's `staleWindows` (empty when the evaluation failed or the reflection is a draft). None → the **default refinement window** (`windows.md` § 7; a nil, windowless generation only for an unscheduled reflection or one whose first grid point has not passed and whose trailing window is empty). Exactly one, or `allWindows: true` → all of them; several without `allWindows` → `400 multiple windows are pending; pass allWindows=true to generate them all`.

The generation context is detached from the request (`context.WithoutCancel`). Both paths go through the worker manager, which first **yields the wave**: when no live claim exists for the reflection (any window), a running reconcile wave is cancelled after its current entity; when one does, nothing is cancelled and the request joins or fails as below. **One window** goes through `Manager.GenerateReflectionSnapshot` → `engine.GenerateOrJoin`: `ErrGenerationInFlight` makes the handler **join** the running generation for that window (`AwaitGeneration`: woken by the in-process claim hub when the claim settles, otherwise re-reading the claim row every 500 ms, bounded by the request context and the 10-minute claim TTL) and, if that generation ends without output (claim released, or discarded while awaited), generate afresh once. **Several windows** run through `Manager.GenerateReflectionWindows` → `reflections.GenerateWindows`: one goroutine per window, each retrying on `queue.ErrPreempted`, joined before the response; concurrency is bounded only by the scheduler (`llm-queue-quota.md` § 2). No join is attempted on this path — an in-flight window is simply a failed window. After either path the manager calls `EnqueueWave` when it cancelled a wave or when at least one window was produced with `status = approved` (`coordination.md`).

Response `200 {snapshotIds: [...]}` with the successes. When some windows failed and at least one succeeded, the first error is logged and the successes returned. When none succeeded the first error is mapped by `WriteGenerateError`: `usage.ErrExhausted` → `402` (`llm-queue-quota.md` § 5); a classified provider error → its envelope (`llm-queue-quota.md` § 6); `ErrContextTooLarge` → `422`; `ErrLensNotReady` → `409 This reflection's lens is still being prepared — try again in a moment.`; `ErrGenerationInFlight` → `409 A generation for this reflection is already running.`; an error whose text contains `not found` → `404 reflection not found`; anything else (including a cancelled join and a model-resolution failure) → `500 generate reflection failed`.

### 5.2 One window

`engine.GenerateSnapshot(ctx, app, reflectionId, status, reflections.Strategy{}, window)`, as `lifecycle-projection.md` § 4.1–4.2 with these differences:

1. **Lens and model.** `FindLive` first (a soft-deleted reflection fails with a `not found` error). `current_lens_id` must point at a lens with a non-empty prompt, else `ErrLensNotReady`. The model is `RoleSnapshot` resolved against `generate_with_model` (`lifecycle-projection.md` § 5); a resolution error fails before any claim.
2. **Claim.** The claim row (`status = generating`) carries `window_start`/`window_end` from insertion; the lock is per `(reflection, window)` (`Strategy.SnapshotWindowFilter`), so different windows generate concurrently while a second generation of the same window gets `ErrGenerationInFlight`. A claim older than 10 minutes (`GenerationClaimTTL`) is deleted and taken over. Every failure below releases the claim (the row is deleted if still `generating`) and wakes any joiner.
3. **Context.** The lens's spec (`current_context_spec`) is resolved **inside the window** (`context.md` § 2.1). If resolution errors, generation proceeds with an empty source block and an empty receipt. If the resolved set contains any upstream snapshot the generation fails with `this context must contain fragments only, but snapshots were provided` (`Strategy.EnsureFragmentsOnly`) — a reflection never consumes projections or reflections. A hydration error is ignored (empty source block, receipt kept). The prompt is `ApplyPrompt(lens, sourceBlock, start, end)` with the window bounds (`prompts.md` § 2); `CheckPromptFits` may refuse it (`context.md` § 6); empty model output fails the generation.
4. **Anchor.** The minimal-diff anchor is the highest-sequence approved snapshot **of the same window** (windowless chain for a nil window) — but only when it was produced by the current lens. Another lens → generated from scratch; none → first generation; byte-identical output, or a delta of "no changes" → *unchanged*; otherwise the two-turn rewrite, whose failure keeps the raw candidate, whose preemption aborts the whole generation (retried by `GenerateWindows`, the background pass, and the wave), and whose cancellation aborts without persisting.
5. **Settle in place.** *Unchanged* under a wave context (`generation_trigger` set on the context) updates the window's highest-sequence approved row (`context_spec`, `resolved_context`, `generated_by_model`, `generated_at`), discards the window's other `pending_review` rows, releases the claim and returns the approved row's id — no new row, no sequence move. When that approved row is no longer the current lens's (the anchor moved), nothing is written and the candidate is stored as usual. An interactive unchanged generation still stores a new row.
6. **Complete.** The claim row is filled in place: `reflection_id`, `lens_id`, `output`, `context_spec`, `resolved_context`, the window bounds, `status`, `generated_by_model`, `generation_trigger` (from the context), `generated_at`; in the same transaction every other `pending_review` row **of the same window** is set `discarded`, and joiners are woken after the commit. With `status = approved`, `ApproveSnapshot` then assigns `approval_sequence_number` = highest approved sequence within the window + 1, sets `approved_at`, and discards the window's other pending rows again (`lifecycle-projection.md` § 4.3 for the approvability checks; a row that already carries a sequence is left untouched).

### 5.3 The background pass

`RunPendingWindows(runner, app, reflectionId)` runs `GeneratePendingWindows` on a goroutine of the server's tracked runner (cancelled and awaited at shutdown, `boot-and-workers.md` § 3). Its triggers are exactly two: a reflection refinement commit (§ 4) and `POST /api/reflections/{id}/backfill` (§ 9). Nothing runs it at boot or on a timer, and it does not pass through the worker manager (no wave yield, no `EnqueueWave` afterwards). The pass loads the reflection with `FindRecordById` (a soft-deleted reflection is loaded, but every window then fails in `GenerateSnapshot`'s `FindLive` and is logged as a failed window), computes the **pending windows** — series windows with no approved snapshot and no generation in flight, oldest first (`windows.md` § 3) — and returns silently when there are none; otherwise it generates all of them through `GenerateWindows` as `approved` at `queue.Background` priority (`llm-queue-quota.md` § 2.1). Per window: `ErrLensNotReady` is logged at warn, `ErrGenerationInFlight` is silently skipped, any other error is logged at error; a window that failed stays pending for the next trigger. One pass, no loop, no reschedule, no signal on completion. Windows with an approved snapshot under an older lens are not pending and are not touched.

## 6. Approval

There is **no reflection approve route** and no reflection edit route: `HandleApproveCandidate` and `HandleEditCandidate` are registered under `/api/projections/{id}/candidates/{rid}/…` only, and `projections.ApplyEdit` is projection-specific. A reflection snapshot stored with `preview: true` therefore stays `pending_review` until a later generation of the **same window** completes or approves (which discards it) or a wave generation settles that window in place; it can never be promoted. Approvals happen only server-side: an interactive non-preview generation (§ 5), the background pass (§ 5.3) and the wave (§ 7) each approve their own output as it lands, per window, with the sequence rule of § 5.2 step 6.

## 7. Staleness and the wave

Only `active`, live reflections are evaluated (`reconcile.md` § 1). A reflection with no approved snapshot (in any window) is a draft and reports a zero row. With at least one **windowed** approved snapshot it is evaluated per window (`reconcile.md` § 2.1): series windows with no approved snapshot and no generation in flight are `pendingWindows`; for each window with an approved snapshot the spec resolved inside that window is diffed against that window's highest-sequence approved `resolved_context` — one-way, fragments resolved now but absent from the receipt (`PinnedIDs.Diff`); a window whose resolution errors is skipped — so a backdated fragment flags exactly the windows it falls in as `staleWindows`, and the union of those fragments is `newFragmentIds`. When nothing is pending or stale, `upToDateSnapshotId` is the approved snapshot of the window with the latest `end`. On this path `staleDependencies` and `blockedBy` are never computed, so the generate route's `409` upstream guard (§ 5) cannot fire for a windowed reflection. Lens identity is not part of the evaluation: a window whose approved snapshot predates the current lens is neither pending nor stale. With only windowless snapshots the reflection is evaluated like a projection (`reconcile.md` § 2) plus `pendingWindows` from the series. As an **upstream** (another entity's `sourceReflectionIds`) a reflection contributes its newest approved snapshot across all windows — by `approval_sequence_number`, so the ordering across windows is by approval order, not window date — and nothing while soft-deleted (`context.md` § 3).

The reconcile wave (`reconcile.md` § 3.1) generates a reflection's `pendingWindows` then `staleWindows`, in that order, as **approved**, at background priority, under the `generate_all` trigger (so an unchanged result settles in place, § 5.2 step 5). A reflection deleted since the wave was evaluated is skipped. A scheduled reflection (a non-empty current grid) that owes no window is skipped — the wave never produces a windowless snapshot for it. An unscheduled reflection is in the wave's worklist only when its row reports `newFragmentIds`, `staleDependencies`, `blockedBy`, `pendingWindows` or `staleWindows`; it is then regenerated windowless unless `SnapshotIsCurrent` says its newest snapshot already reflects the current lens, model and resolved context. Per window the wave retries on preemption and skips the entity on `ErrLensNotReady`/`ErrGenerationInFlight`; any other error ends the wave.

## 8. Deletion and restore

`DELETE /api/reflections/{id}` is a **soft delete**. The row is loaded with `FindRecordById` (missing → `404 reflection not found`); an already-deleted reflection → `204` with no further effect. If a `generating` claim row younger than 10 minutes exists for the reflection — **any** window — → `409 a generation is running for this reflection` (the check runs before, not inside, the transaction; a query failure → `500`). Otherwise, in one transaction: the reflection's id is removed from `sourceReflectionIds` in the `current_context_spec` of every `projection` and every `reflection` whose spec text contains it (matched with `~`, without a live filter — proposed and soft-deleted entities are scrubbed too; frozen snapshot `context_spec`s are not; a row whose spec fails to unmarshal is skipped); then `deleted_at` is set to now. Transaction failure → `500 delete reflection failed`. Response `204`.

Nothing else is written: `reflection_snapshot`, `reflection_window`, `reflection_refinement` and `chat_message` rows stay as they are (their `CascadeDelete` relations fire only on a hard delete, which no route performs). Lenses remain. While `deleted_at` is set: `PATCH`, generate, windows, backfill and refinement-open all answer `404`/`500` as stated above (`FindLive`); a refinement turn answers `400` (§ 4) and its commit fails `500`; the reconcile evaluator, the wave and discover's `list_existing` skip the reflection (`LiveFilter`); its snapshots resolve for no dependent (`reflection_id.deleted_at = ''`, `context.md` § 3). The collection list/view endpoints apply no live filter — a soft-deleted reflection and its children are still readable there.

`POST /api/reflections/{id}/restore`: missing → `404 reflection not found`; otherwise `deleted_at` is cleared (a live reflection is a no-op; save failure → `500 restore reflection failed`) and the response is `200 {id}`. References scrubbed from other entities at delete time are not re-added. No generation, staleness evaluation or wave is triggered by either operation.

## 9. Backfill and the windows route

- **`POST /api/reflections/{id}/backfill`** binds `api.BackfillRequest` `{from}`: unparsable body → `400 invalid request body`; `from` not RFC3339 → `400 from must be RFC3339`; `FindLive` → `404 reflection not found`. `MaterializeBackfill` (`windows.md` § 6.1) requires a governing version with a positive period — otherwise the error (`is not scheduled` / `has no period`) is logged and answered `500 backfill failed`; `from` at or after the governing version's lower bound → `400 backfill start must be before the windows already on the grid`. Every grid window ending after `from` and at or before that lower bound, phase-aligned with the existing grid (the origin is the version's `startTime`, else the lower bound, shifted back by whole periods), is written as a `reflection_window` row (`reflection_id`, `window_start`, `window_end`); a save rejected by the unique index is tolerated when the row already exists, any other save failure → `500 backfill failed`. Then `RunPendingWindows` (§ 5.3) is started **unconditionally**, even when nothing new was materialised. Response `200 {windows: [{id, start, end}]}` — the windows enumerated for the range (`null` when the range held none), not the generated ones; results arrive as `reflection_snapshot` rows.
- **`GET /api/reflections/{id}/windows`**: `FindLive` → `404 reflection not found`. The series (`windows.md` § 6: current grid, backfilled rows, and every windowed `approved` or `generating` snapshot) is served sorted by `start` then `end` as `{windows: [{id, start, end, key, hasApproved, generating, backfilled, stale?, lensOutdated?}], currentWindowId?}`. `stale` is true for windows in the reflection's `staleWindows` from a full evaluation pass (§ 7) — absent for every window when the evaluation errors or the reflection is a draft; `lensOutdated` = `hasApproved` and the highest-sequence approved snapshot's `lens_id` ≠ `current_lens_id`; `currentWindowId` = the default refinement window's id (`windows.md` § 7), omitted for an unscheduled reflection. `stale`, `lensOutdated` and `currentWindowId` are omitted from the JSON when false/empty.
