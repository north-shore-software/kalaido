**Scope.** The life of one reflection: creation with a schedule, schedule editing, authoring, windowed generation, per-window approval, staleness, deletion, and backfill. Shared machinery lives in its own docs — window calculation in `windows.md`, the refinement conversation in `refinement.md`, staleness in `rotation.md`; endpoint detail in `api.md` § 6–7, fields in `schema.md`. Where behaviour is identical to a projection's (`lifecycle-projection.md`), it is referenced, not repeated.

---

## 1. Objects and states

A reflection extends the projection shape (`name`, `status`, `model` override, `current_context_spec`, `current_lens_id`, `pinned_by`, discover provenance) with `window_spec_versions` — an append-only history of its schedule (`windows.md` § 2). Its output is a **time series**: `reflection_snapshot` rows, each either *windowed* (carrying `resolved_window {start, end}`, `window_key = "{start}_{end}"`, `window_spec`, and `window_spec_version_number`) or *windowless* (no window fields; the empty key). Snapshot statuses are as for projections (`generating`, `pending`, `approved`, `discarded`). The active snapshot is derived **per window key**: the approved snapshot with the highest `approval_sequence_number` within that key (partial unique index on `(reflection_id, window_key, approval_sequence_number)`); windowless snapshots form their own series under the empty key. `reflection_window` rows record explicitly backfilled windows (§ 9).

## 2. Creation

`POST /api/reflections` `{name, windowSpec?}`. The spec is validated (`windows.md` § 1): an entirely empty spec is allowed (unscheduled); otherwise `period` must be a positive duration, `duration` if given likewise, `startTime` if given RFC3339 — else 400. Version 1 is appended with `effectiveFrom` = **`startTime` when it lies in the past, else now** — so "summarise from <date>" makes every grid window since that date pending once a lens exists. Created `active`. Response `201 {reflectionId}`. A draft in rotation terms until its first approved snapshot.

## 3. Schedule editing

`PATCH /api/reflections/{id}` `{name?, pinned?, model?, windowSpec?}`. A `windowSpec` is validated as at creation and appended as a new version effective **now**; an empty `startTime` inherits the governing version's so the grid stays phase-aligned. Nothing is regenerated by an edit; windows already generated under an older version stay in the series (`windows.md` § 6). `name`, `pinned`, `model` behave as for projections (`lifecycle-projection.md` § 7). Response `200 {id}`.

## 4. Authoring: refinement → commit

A refinement session (`refinement.md` § 2) on a reflection ignores `snapshotId`, seeds the reflection's own `current_context_spec`, binds a **target window** (the request's, else the current window, `windows.md` § 7; none for an unscheduled reflection), and — when the reflection already has a lens — seeds an assistant turn carrying that lens and the window's approved output as the starting preview. Turns preview the drafted lens against the window's fragments; a window-only send re-applies the standing lens to another window (`refinement.md` § 4).

**Commit** installs the lens and `current_context_spec`, sets `status = active`, and publishes **nothing**: the previewed window was a sample. Every existing window snapshot now reads as produced by an older lens (`lensOutdated`, § 9). Then `RunPendingWindows` starts a background pass generating every window the series owes as **approved** (§ 5.2). Response `200 {snapshotId: ""}`.

## 5. Generation

`POST /api/reflections/{id}/generate-snapshot` `{preview?, windowId?, all?}`. `preview: true` → pending, else approved. The `blockedBy` check applies as for projections (409).

### 5.1 Which windows

- `windowId` given: it must be a window of the series (`windows.md` § 6) → exactly that window; unknown → 400.
- Otherwise the candidates are every series window that is not generating and either has no approved snapshot or whose approved snapshot's `lens_id` ≠ `current_lens_id`, plus the windows rotation reports stale. None → the **default refinement window** (`windows.md` § 7; nil — a windowless generation — only for an unscheduled reflection). Exactly one, or `all: true` → all of them; several without `all` → 400 (`multiple pending windows; specify windowId or all=true`).

Several windows generate concurrently, one goroutine each, joined before the response; the scheduler caps in-flight calls. Response `200 {snapshotIds: [...]}` listing the successes; with some failures the first error is logged and the successes returned; with none, the first error is mapped as for projections.

### 5.2 One window

As `lifecycle-projection.md` § 4.1–4.2 with these differences: the claim row carries `window_key`; the lens spec is resolved **inside the window** (`context.md` § 2.1); a spec resolving to any upstream snapshot is refused (`this context must contain fragments only` — reflections may not consume projections or reflections); `ApplyPrompt` receives the window bounds; the minimal-diff anchor is the newest approved snapshot **of the same window key** produced by the same lens; the completed row gets `window_spec` (the governing version's spec), `window_spec_version_number`, `resolved_window`, `window_key`; other pending candidates **of the same key** are discarded. A preempted generation is retried by `GenerateWindows` and by the background pass until it lands.

`GeneratePendingWindows` (background, after commit or backfill): every pending window (`windows.md` § 6), generated as approved at Background priority; `ErrLensNotReady` and `ErrGenerationInFlight` are logged/skipped; a failed window stays pending for the next pass. Nothing loops or reschedules.

## 6. Approval

There is **no reflection approve route**: `handleApproveCandidate` is registered for projections only. A reflection snapshot generated with `preview: true` is stored `pending` and can never be promoted through the API; it stays pending until a later generation of the same window key discards it. Non-preview generations and the background pass approve their own output as they land, applying the per-key sequence rule (`lifecycle-projection.md` § 4.3).

## 7. Staleness

`rotation.md` § 2.1: a reflection with any windowed approved snapshot is evaluated **per window** — each window's spec resolution inside that window diffed against that window's approved `resolved_context`; a backdated fragment flags exactly the windows it falls in as `staleWindows`; windows owed but never generated are `pendingWindows`. A reflection with only windowless snapshots is evaluated like a projection, plus `pendingWindows` from the grid. Upstream edges are never built for reflections' own dependents' sake — a reflection may be an upstream (`sourceReflectionIds`), and its newest approved snapshot across all keys is what resolves.

## 8. Deletion

`DELETE /api/reflections/{id}` → 204. Cascades: `reflection_snapshot`, `reflection_window`, `refine_refl_snapshot_conversation` (and their messages). Lenses remain. Other entities' `sourceReflectionIds` are not scrubbed.

## 9. Backfill and the windows route

- **`POST /api/reflections/{id}/backfill`** `{from}` (RFC3339, else 400): `MaterializeBackfill` (`windows.md` § 6.1) writes a `reflection_window` row per grid window between `from` and the point the governing version already covers, phase-aligned to the existing grid; `from` at or after that point → 400 (`backfill start must be before the windows already on the grid`); an unscheduled reflection → 500. Then `RunPendingWindows`. Response `200 {windows: [{id, start, end}]}` — the materialised windows, not the generated ones; results arrive as snapshot rows.
- **`GET /api/reflections/{id}/windows`**: the series oldest first as `{windows: [{id, start, end, key, hasApproved, generating, backfilled, stale, lensOutdated}], currentWindowId}`. `stale` comes from a full rotation evaluation (empty on error); `lensOutdated` = has an approved snapshot whose `lens_id` ≠ `current_lens_id`; `currentWindowId` = the default refinement window's id, absent for an unscheduled reflection.
